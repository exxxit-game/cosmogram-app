# Автоопределение верхнего safe-area на Android-WebView Telegram: честный ноль vs мёртвый ноль (14.09.2026)

> Владелец: у игры застарелая проблема — верхний безопасный отступ меню (`--sat-menu`) должен
> подстраиваться под вырез/статус-бар/шапку Telegram каждого устройства игрока сам, но на части
> реальных Android-телефонов внутри Telegram (WebView, не системный Chrome) ДВА независимых
> способа измерения (`env(safe-area-inset-top)` и `Telegram.WebApp.contentSafeAreaInset.top`/
> `.safeAreaInset.top`) одновременно возвращают ноль, хотя вырез/статус-бар физически есть.
> Задача 1 — найти реальные, поимённые, документированные решения именно этого класса бага
> (Android WebView/Telegram Mini Apps/гибридные контейнеры), макс. глубина, все релевантные
> языки. Задача 2 — спроектировать (не кодировать) систему, которая на реальном устройстве
> даёт надёжный отступ без ручной подстройки владельцем, с явным ответом на «как отличить
> честный ноль от мёртвого».

## Часть 1. Находки (задача 1)

### 1.1 Что уже читает Cosmogram — для сверки, не по памяти
Живой код (`index.html:158-165`, `core.js` `tgInsetsSync()`/`satProbe()` ~895-970) уже комбинирует
через `max()`: `env(safe-area-inset-top)` → мостовые CSS-переменные Telegram
(`--tg-safe-area-inset-top`, `--tg-content-safe-area-inset-top`) → `--js-sat`/`--js-sat-real`
(собственный JS-запас). `viewport-fit=cover` в `<meta name="viewport">` уже стоит (index.html:3) —
это предусловие для `env()` уже выполнено, не пробел. Сегодня же (14.09.2026) в Сервисный центр
добавлено живое переизмерение `satProbe()`/`contentSafeAreaInset` (`#diagSatRow`, index.html
~3112-3118) и временный ползунок `--menu-buf` (`#diagBufSlider`) — это уже готовый канал измерения
на реальном устройстве, на который стоит опереться в задаче 2, а не изобретать новый.

### 1.2 Официальный `@telegram-apps/sdk` — не новый источник данных, но полезная модель событий
`viewport.safeAreaInsets()`/`viewport.contentSafeAreaInsets()` (реактивные сигналы, telegram-apps.org)
переиздаются на нативных событиях `viewportChanged`, `themeChanged`, `safeAreaChanged`,
`contentSafeAreaChanged` — но оборачивают ТЕ ЖЕ САМЫЕ значения `Telegram.WebApp.safeAreaInset`/
`contentSafeAreaInset`, которые Cosmogram уже читает напрямую. Подключать SDK как npm-зависимость
не даёт новых данных — проект и так без сборки, добавлять его не за что.
Источники: [Viewport | Telegram Mini Apps](https://docs.telegram-mini-apps.com/platform/viewport),
[Viewport | tma-js-sdk](https://docs.telegram-mini-apps.com/packages/tma-js-sdk/features/viewport).

Важная деталь именно в этой модели — событие `contentSafeAreaChanged`/`safeAreaChanged` доступно
и БЕЗ npm-пакета, напрямую через `Telegram.WebApp.onEvent(...)` (штатный vendor-мост, уже в игре).
Это даёт готовый триггер «платформа что-то сказала», не только «объект существует и читается
нулём» — ключевая деталь для задачи 2 (см. 2.3).

### 1.3 Третий, независимый от JS-моста канал — Telegram сам пишет CSS-переменные
Помимо JS-объекта `Telegram.WebApp.safeAreaInset`, нативный клиент Telegram САМ инжектирует в
документ CSS-переменные `--tg-safe-area-inset-top/bottom/left/right` и
`--tg-content-safe-area-inset-top/bottom/left/right` (core.telegram.org/bots/webapps). Это третий,
структурно отдельный путь доставки числа — не через `env()` (зависит от движка WebView) и не
через чтение JS-объекта (зависит от моста), а прямая запись в CSS нативным кодом. **Cosmogram уже
читает эти переменные внутри `max()` для `--sat`/`--sat-menu` (index.html:160,165)** — но
`tgInsetsSync()` в `core.js` их обратно в JS не читает (останавливается на
`t.contentSafeAreaInset||t.safeAreaInset`, core.js:921). Расхождение между значением из JS-моста и
значением из CSS-переменной — само по себе диагностический сигнал (см. 2.4).
Источник: [Telegram Bot API — Web Apps](https://core.telegram.org/bots/webapps).

### 1.4 Bot API changelog — зрелый, замороженный API, без итераций
`safeAreaInset`, `contentSafeAreaInset`, события `safeAreaChanged`/`contentSafeAreaChanged` и
fullscreen-API (`requestFullscreen`/`exitFullscreen`/`isFullscreen`/`fullscreenChanged`) введены
ОДНИМ пакетом в **Bot API 8.0, 17 ноября 2024**. С тех пор в changelog ни одной правки по этим
полям — почина от площадки ждать не стоит, обходной путь придётся строить самим.
Источник: [core.telegram.org/bots/api-changelog](https://core.telegram.org/bots/api-changelog).

### 1.5 GitHub issues официальных трекеров — подтверждён паттерн «ноль», но с уклоном в iOS
- `Telegram-Mini-Apps/telegram-apps` **#870** — утечка ссылки на внутренний объект в
  `viewport.safeAreaInsets()`/`contentSafeAreaInsets()`: если внешний код случайно делает
  `insets.top = 0`, портится кэш SDK для всех последующих чтений (Android и iOS). Не тот же баг,
  что у Cosmogram (там нативное значение УЖЕ ноль), но стоит перепроверить, что нигде в коде
  игры не мутируется полученный объект таким образом.
  [github.com/Telegram-Mini-Apps/telegram-apps/issues/870](https://github.com/Telegram-Mini-Apps/telegram-apps/issues/870)
- `Telegram-Mini-Apps/issues` **#42** («ios safe area constant invalid») и **#39** («Mini App
  scrolls by iOS device's safe-area at bottom») — подтверждённые репорты `env()`/`constant()`
  safe-area, резолвящиеся в 0 внутри Mini App WebView — тот же КЛАСС симптома, что у Cosmogram,
  но на iOS, не Android. Android-репорта с тем же ярлыком в этом трекере не нашлось.
  [issue #42](https://github.com/Telegram-Mini-Apps/issues/issues/42),
  [issue #39](https://github.com/Telegram-Mini-Apps/issues/issues/39)
- `Telegram-Mini-Apps/TelegramUI` **#93** — значение схлопывается в 0 после смены фокуса/навигации
  «назад» на iPhone, пока его не «подтолкнёт» посторонний ре-рендер — тот же паттерн «падает в
  0 и требует толчка», снова iOS.
  [github.com/Telegram-Mini-Apps/TelegramUI/issues/93](https://github.com/Telegram-Mini-Apps/TelegramUI/issues/93)

Официальная документация (`docs.telegram-mini-apps.com/platform/viewport`) **не упоминает вообще
никакой Android-специфичной оговорки** про ноль в `safeAreaInset`/`contentSafeAreaInset` — этот
класс бага существует только в найденном ниже коде реальных приложений, не в документации.

### 1.6 `window.visualViewport` — проверенная техника, но НЕ для этой задачи (важный отрицательный результат)
`window.visualViewport.offsetTop`/`.height` против `window.innerHeight` — подтверждённый,
многократно встреченный (яп. zenn.dev/scrapbox, рус. Habr, кит. CSDN, яп. teratail) способ
измерить «скрытую» зону, НО везде он используется для клавиатуры и скрытия/показа адресной строки
браузера, ни разу — для статус-бара/выреза. Причина, подтверждённая напрямую в источниках: на
Android статус-бар в обычном (не edge-to-edge) WebView занимает место ВНЕ обоих вьюпортов —
она физически не создаёт зазор между layout- и visual-viewport, так что формула для нашей задачи
структурно неприменима. Дополнительно подтверждено живым багрепортом Capacitor (issue #8181):
на Android <15 с жестовой/трёхкнопочной навигацией и открытой клавиатурой `visualViewport.height`
и `innerHeight` сами путают клавиатуру/навбар — то есть источник ненадёжен даже для того, для чего
его обычно и используют.
Источники: [MDN Visual Viewport API](https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API),
[MDN VisualViewport.offsetTop](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport/offsetTop),
[zenn.dev/catnose99](https://zenn.dev/catnose99/scraps/e9b1de4ddf2181),
[Habr (рус.)](https://habr.com/ru/companies/dododev/articles/966804/),
[CSDN (кит.)](https://blog.csdn.net/sophiafei_2000/article/details/78143636),
[teratail (яп.)](https://teratail.com/questions/0p3iomyhnmyo99),
[capacitor issue #8181](https://github.com/ionic-team/capacitor/issues/8181).

### 1.7 Как тот же класс бага решают ДРУГИЕ гибридные контейнеры — универсальный паттерн подтверждён
- **`@capacitor-community/safe-area`** — читает реальное значение на нативной стороне через
  Android `WindowInsetsCompat`, затем (потому что версии Android WebView до Chromium 140 несут
  известный баг с `env(safe-area-inset-*)`) **инжектирует параллельные CSS-переменные**
  `--safe-area-inset-top/right/bottom/left` — намеренно НЕ пытаясь переопределить сам `env()`
  (он read-only и не переопределяется), а подставляя альтернативную переменную для CSS игры.
  На Chromium ≥140 доверяет нативному `env()` — баг там как класс уже устранён у Google.
  Переизмеряет также при смене видимости клавиатуры.
  [github.com/capacitor-community/safe-area](https://github.com/capacitor-community/safe-area)
- **`cordova-plugin-android-notch`** — нативный мост `window.AndroidNotch` с асинхронными
  `hasCutout()`/`getInsetTop()`/`getInsetRight()`/`getInsetBottom()`/`getInsetLeft()`; штатный
  паттерн использования — веб-страница сама вызывает мост и пишет
  `document.documentElement.style.setProperty('--notch-inset-top', px+'px')` — ровно тот же приём
  «мост → CSS-переменная», что уже держит `--js-sat` в Cosmogram.
  [github.com/tobspr/cordova-plugin-android-notch](https://github.com/tobspr/cordova-plugin-android-notch/issues/3)
- **`cordova-plugin-statusbar`** — на Android при `overlaysWebView(true)` САМ не отдаёт значение
  инсета — известный, до сих пор не закрытый пробел; сообщество комбинирует его с
  `cordova-plugin-android-notch` отдельно.
  [github.com/apache/cordova/discussions/585](https://github.com/apache/cordova/discussions/585)
- **React Native WebView** — подтверждён ТОТ ЖЕ САМЫЙ класс бага в СОВЕРШЕННО ДРУГОМ хост-приложении:
  `env(safe-area-inset-*)` «недоступен до какого-то произвольного момента после загрузки страницы»
  внутри `<WebView>`, хотя нативные RN-view (`react-native-safe-area-context`) получают инсеты
  верно. Давний баг (`facebook/react-native#22362`, перенесён в
  `react-native-webview/react-native-webview#155`), новый репорт **#3828** — та же регрессия на
  Chromium 138+ (т.е. независимое подтверждение версионной привязки бага, помимо Capacitor-находки
  про Chromium 140). Готового моста-плагина нет — разработчики вручную комбинируют
  `injectedJavaScript` + `window.ReactNativeWebView.postMessage`. Ни в одном источнике не нашлось
  опубликованной реализации retry-with-backoff/двойного `requestAnimationFrame` именно для доставки
  инсетов — это подтверждённый пробел, не только у Cosmogram.
  [facebook/react-native#22362](https://github.com/facebook/react-native/issues/22362),
  [react-native-webview#155](https://github.com/react-native-community/react-native-webview/issues/155),
  [react-native-webview#3828](https://github.com/react-native-webview/react-native-webview/issues/3828)
- **Установленные Android PWA** — консенсус: `env(safe-area-inset-*)` родился в iOS Safari и там
  всегда работал надёжно; на Android имплементация была новее и версионно-нестабильна, завязана
  на переход Chrome к edge-to-edge-рендерингу (обязателен с Android 15/API 35 для приложений,
  нацеленных на SDK 35+). Ни один источник не подтвердил, что установленное Android PWA надёжно
  чинит эту проблему — остаётся версионно-зависимым, а не гарантией, как на iOS.
  [developer.chrome.com — edge-to-edge](https://developer.chrome.com/docs/css-ui/edge-to-edge)

**Сквозной вывод по 1.7**: универсальная архитектура во ВСЕХ проверенных экосистемах одна и та
же — нативные инсеты читаются на своей стороне → пробрасываются в WebView как CSS-переменные
(никогда не пытаясь переопределить сам `env()`) → приложение читает `var()` с фолбэком. Это
структурно ТО ЖЕ САМОЕ, что уже делает `--js-sat` в Cosmogram — подтверждает, что общая архитектура
выбрана верно, слабое место — именно уровень доверия/распознавания (задача 2), не сама идея моста.

### 1.8 Мультиязычный обзор сообщества — главные находки живут в шипнутом коде, не в статьях
Общий паттерн, подтверждённый широким поиском (веб + GitHub code/issue search на 10 языках):
статьи/форумы почти полностью молчат об этом конкретном симптоме («Telegram Mini App Android
safeAreaInset = 0») практически на всех проверенных языках — баг чинили прямо в коммитах/PR без
публикаций. GitHub code/issue search оказался продуктивнее общего веб-поиска для такого узкого
симптома.

**Русский/украинский — самые предметные находки:**
- **gregoryKot/schema-telegram-botnest, PR #284** — причина: приложение вызывает `expand()`,
  а не `requestFullscreen()`, поэтому `isFullscreen` остаётся false, и «`contentSafeAreaInset`
  клиенты часто возвращали нулём вне fullscreen» — явно ПОДТВЕРЖДЕНО автором как баг НЕ только
  iOS: «на Android кнопки виснут так же». Фикс: доверять `contentSafeAreaInset` только когда
  клиент реально отдал НЕНУЛЕВУЮ content-полосу, иначе — гарантированный фолбэк.
  [pull/284](https://github.com/gregoryKot/schema-telegram-botnest/pull/284)
- **Тот же репозиторий, PR #136** — в fullscreen-режиме на части клиентов Telegram
  `contentSafeAreaInset` вообще не присылается. Двухуровневый фикс: (1) точный расчёт, когда ОБА
  инсета реально пришли; (2) щедрый фолбэк, когда их нет: **iOS: устройство + 76px, минимум
  100px. Android: устройство + 48px.** Флаг доверия завязан на то, реально ли СРАБОТАЛО событие
  `contentSafeAreaChanged`, а не просто на однократное чтение значения.
  [pull/136](https://github.com/gregoryKot/schema-telegram-botnest/pull/136)
- **Maximusvin/void-saga-tma, PR #44** — важнейшая находка: прежний код брал
  `max(safeAreaInset.top, contentSafeAreaInset.top)` вместо СУММЫ. На Android
  (`safeAreaInset.top=28`, `contentSafeAreaInset.top=46`) это давало HUD-отступ только в 28px
  (высота статус-бара), хотя плавающие кнопки Telegram требовали полных ~74px — `max()` брал
  только большее из двух РАЗНЫХ, а не альтернативных перекрытий (вырез устройства и отдельно —
  собственная шапка/кнопки Telegram). Таблица из PR: Android fullscreen было 46px → стало 74px
  (нужно ≥74px); iPhone с чёлкой — 105px; обычный режим — 6px (без переплаты). Там же поймана
  вторая беда: `Math.max(1, 0)` на нулевой `viewportStableHeight` буквально писал «1px»,
  схлопывая весь интерфейс в полоску — паттерн «API вернул 0 → наивный clamp делает хуже, а не
  лучше», стоит проверить у себя, не как подтверждённую находку, а как гипотезу для проверки.
  [pull/44](https://github.com/Maximusvin/void-saga-tma/pull/44)
- **Golicenko/telegram-market, PR #49** и **Undermove/TraleBot, PR #91** — «пояс и подтяжки»:
  используют И `safeAreaInset`/`contentSafeAreaInset`, И системные CSS safe-area одновременно,
  конвертируют в CSS-переменные на sticky-шапках — та же архитектура, что уже в Cosmogram, новых
  чисел не добавляют.

**Английский — рабочий прецедент с диагностическим оверлеем:**
- **rog199494-creator/mobile-inventory, PR #23 → PR #28** — фолбэки ДВАЖДЫ пересматривались
  вверх после того, как оказались недостаточны на реальных устройствах: iOS 100→130→160px,
  Android 80→110→130px, веб/TDesktop 56→60px. Структурная правка: ушли от CSS-паддинга к
  физическому DOM-спейсеру (`safe-area-spacer`), потому что CSS-переменная «продолжала оказываться
  ненадёжной на разных устройствах». Встроен диагностический оверлей по `?debug=safe-area` —
  показывает фолбэк и реально применённое значение РЯДОМ, на самом устройстве — **тот же принцип,
  что новый `#diagSatRow` Cosmogram, добавленный сегодня же, 14.09.2026, независимо**.
  [pull/23](https://github.com/rog199494-creator/mobile-inventory/pull/23),
  [pull/28](https://github.com/rog199494-creator/mobile-inventory/pull/28)
- dev.to/nimaxin — общие грабли TMA-вёрстки (100vh, схлопывание скролла), не про инсеты
  конкретно; отмечает, что Bot API 7.7+ сделал `disableVerticalSwipes()` штатным, обходной
  скролл-хак больше не нужен на актуальных клиентах.
  [dev.to/nimaxin](https://dev.to/nimaxin/how-to-fix-the-telegram-mini-app-scrolling-collapse-issue-a-handy-trick-1abe)
- Adsgram blog — общий совет «применяй оба инсета» без конкретики по Android/нулю.
  [adsgram.ai/blog](https://adsgram.ai/blog/adsgram/telegram-mini-app-tma-development-mistakes-and-how-to-avoid-them)

## Часть 2. Архитектура автоопределения (задача 2, проектирование, без кода)

Ниже — план на бумаге, дополняющий уже существующую цепочку (`env()` → мост Telegram →
эвристика touch-устройства 28px → назначенные константы 96/44px), а не переписывающий её с нуля.
Ядро (`core.js`/`render.js`/…) не трогается без отдельного разрешения владельца — это план,
что именно стоило бы туда внести, когда владелец скажет «да» отдельно на эту работу.

### 2.1 Не подключать `@telegram-apps/sdk`
Подтверждено исследованием (1.2) — SDK не даёт новых данных сверх того, что игра уже читает
напрямую через `Telegram.WebApp`, а npm-зависимость запрещена правилами проекта. Полезная часть
SDK (событийная модель `safeAreaChanged`/`contentSafeAreaChanged`) доступна и без пакета — эти
события уже штатно шлёт `Telegram.WebApp.onEvent(...)`, тот же vendor-мост, что уже в игре.

### 2.2 Добавить четвёртый, независимый канал чтения — CSS-переменные Telegram обратно в JS
Сейчас `--sat`/`--sat-menu` в CSS уже читают `--tg-safe-area-inset-top`/
`--tg-content-safe-area-inset-top` через `max()` (index.html:160,165), но `tgInsetsSync()` в
`core.js` эти же переменные не перечитывает обратно в JS — останавливается на
`t.contentSafeAreaInset||t.safeAreaInset`. Предлагается: `tgInsetsSync()` дополнительно читает
`getComputedStyle(document.documentElement).getPropertyValue('--tg-content-safe-area-inset-top')`
как отдельный, независимый источник. Если он расходится со значением из JS-объекта — само
расхождение диагностически ценно (доказывает, что мост CSS и мост JS не синхронизированы на
конкретном устройстве), и его стоит выводить в `#diagSatRow` отдельной строкой, а не скрывать.

### 2.3 Событие как триггер доверия, а не только как повод перечитать число
Сейчас `tgInsetsSync()` вызывается в фиксированных точках (resize, показ экрана и т.п.) —
однократное чтение в момент вызова. Предлагается: слушать `Telegram.WebApp.onEvent('safeAreaChanged', ...)`
и `onEvent('contentSafeAreaChanged', ...)` явно, и держать флаг «событие срабатывало хотя бы раз
с момента загрузки» отдельно от самого числа. Это прямая параллель шипнутому фиксу
`schema-telegram-botnest` PR #136 (1.8) — там доверие к значению завязано именно на факт
срабатывания события, а не на однократное чтение объекта.

### 2.4 Честный ноль vs мёртвый ноль — ключевая развилка, предлагаемое решение
Вместо того чтобы пытаться угадать по одному сигналу (как сейчас: touch-устройство + не-fullscreen
→ считать вырез вероятным), предлагается держать по каждому источнику **три независимых бита**,
а не одно число:
1. **`env()`-проба** (`satProbe()`) — уже есть, но её «ноль» САМ ПО СЕБЕ НИКОГДА не диагностичен:
   ни один источник в исследовании не нашёл способа отличить у неё честный и мёртвый ноль
   изнутри — она в принципе не самодиагностируется. Использовать только как один из голосов,
   никогда как решающий.
2. **Флаг «событие Telegram сработало хотя бы раз»** (2.3) — самый весомый из трёх сигналов.
   Если `contentSafeAreaChanged`/`safeAreaChanged` не сработало НИ РАЗУ с момента загрузки —
   это состояние «платформа ничего не сказала», а не «платформа сказала ноль». Если событие
   сработало и принесло 0 — это состояние «платформа ПОДТВЕРДИЛА ноль» (честный ноль: например,
   десктоп-класс устройства, планшет, телефон без выреза).
3. **Эвристика touch-устройства** (уже в коде, core.js:922, 28px) — оставить, но понизить в ранге:
   использовать её и текущие назначенные константы (96/44px) ТОЛЬКО когда пункты 1 и 2 оба
   вернули «неизвестно», а не как равноправный третий голос.

Итоговая развилка (план, не код): `env()=0` И JS-мост=0 И CSS-переменная моста (2.2)=0 И
событие ни разу не срабатывало → считать «неизвестно», идти по существующей цепочке эвристика→
назначенные числа. Если хотя бы один из независимых каналов отдал ненулевое значение, ИЛИ
событие сработало и подтвердило именно 0 — считать это честным числом и не накладывать сверху
запасные константы. Это превращает «а платформа вообще что-то ответила?» в главный переключатель,
которого не хватает в сегодняшней логике (она сегодня различает только по touch+fullscreen, не
по факту события).

### 2.5 Сумма vs максимум — открытый вопрос владельцу, не готовое решение
`void-saga-tma` PR #44 (1.8) показывает реальный кейс, где `safeAreaInset.top` (вырез/статус-бар
устройства) и `contentSafeAreaInset.top` (собственная плавающая шапка/кнопки Telegram) —
это ДВА РАЗНЫХ перекрытия, которые должны СКЛАДЫВАТЬСЯ, а не выбираться через `max()`. Формула
`--sat` в Cosmogram сегодня берёт `max()` по всем источникам сразу, включая эти два (index.html:160)
— по правилу проекта («любая геометрическая формула — проверь численно», «не додумывать
конкретику») это НЕ вносится как готовый фикс: нужны реальные пары `safeAreaInset.top`/
`contentSafeAreaInset.top`, снятые на устройстве владельца через доработанный `#diagSatRow`
(2.6), прежде чем менять формулу — сегодняшний `max()` мог визуально устраивать ровно потому,
что на устройстве владельца оба числа пока совпадают или одно из них честно ноль.

### 2.6 Сначала диагностика, потом алгоритм — расширить уже добавленный сегодня `#diagSatRow`
Владелец уже сегодня добавил живое переизмерение в Сервисный центр. Предлагается достроить ту же
панель (не новый экран) до вида, буквально повторяющего прецедент `mobile-inventory`
`?debug=safe-area` (1.8, PR #23/28) — таблица side-by-side на самом устройстве:
`env() сырое` / `JS-мост сырое (safeAreaInset.top, contentSafeAreaInset.top отдельно)` /
`CSS-переменная моста сырое (2.2)` / `событие срабатывало: да/нет` / `итоговое --js-sat`.
Только после того как владелец посмотрит на эту таблицу на 2-3 реальных устройствах (своём +
хотя бы одном чужом с жалобой «тесно»/перекрытие) — переносить логику 2.2-2.5 в `tgInsetsSync()`
как настоящий код, отдельным явным разрешением на правку `core.js`. Это тот же принцип «один шаг —
одна проверка», не блочный переход к алгоритму вслепую.

### 2.7 Физический DOM-спейсер — про запас, не сейчас
`mobile-inventory` (1.8) в итоге ушёл от CSS-паддинга к физическому DOM-элементу-спейсеру, потому
что переменная в CSS «продолжала оказываться ненадёжной». Cosmogram сегодня целиком построен на
`calc()`/CSS-переменных для отступов по всей игре — переход на спейсер-элементы был бы гораздо
более крупной, затрагивающей ядро правкой (`render.js`/вёрстка всех экранов), и по правилам
проекта требует отдельного явного разрешения, не входит в объём этой задачи. Держать в уме как
следующий шаг, если после 2.2-2.6 проблема на части устройств всё равно останется.

### 2.8 Что НЕ предлагается
- Не предлагается убирать существующие назначенные константы (96px/44px) — они остаются
  нижним, проверенным на реальных жалобах, слоем цепочки на случай честного «неизвестно».
- Не предлагается менять `--sat`/`--sat-menu` формулу в CSS прямо сейчас (см. 2.5).
- Не предлагается убирать временный ползунок `--menu-buf` этим планом — это отдельная, уже
  идущая задача владельца («ВРЕМЕННО», index.html ~3098-3111), закрывается его словом, не этим
  исследованием.
