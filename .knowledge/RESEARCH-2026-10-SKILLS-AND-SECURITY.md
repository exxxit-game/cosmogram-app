## 2. Что не брать

- Плагины с хуками, самообновлением и повышенными правами (`security-guidance`: пять типов хуков и скачивание пакета; Semgrep Guardian: закрытые файлы и вход в аккаунт; `claude-mem`, `kyzdes/clarity-skill`, наборы на 60 хуков; `securitymaxxing`): конфликтуют с набором из 12 хуков и с «новых хуков без слова владельца нет».
- Наборы, требующие одобрения каждого шага (Claude-Code-Game-Studios, часть `superpowers`): противоречат «внутри понятной темы действовать без остановок».
- Всё, что запускает чужой код при установке (`npx skills add`, `npx degit`, `uvx mcp-scan`): копировать нужные текстовые файлы руками.
- `supabase-pentest-skills`: достаёт ключи и создаёт пользователей, только на тестовой копии и по слову владельца.
- Без лицензии: читать можно, копировать в проект нельзя.
- Из-за непроверенных данных: Bot API 10.2 «запрещает вызовы с чужих доменов» (блог adsgram), Telegram-мосты от частных лиц.
- Признаки опасного скилла: `!` в начале команд, `allowed-tools: Bash(*)`, `curl`, `base64`, папки `hooks/` и `bin/`, самообновление по расписанию, запись в общие папки. По исследованию Snyk 36,8% из 3984 скиллов имеют хотя бы одну уязвимость.

## 3. Проверено в нашем коде (02.10.2026)

- CSP (`index.html:30`): `script-src 'self' 'unsafe-inline'` — встроенные скрипты разрешены, защита от подмены скриптов слабая (по документации MDN из отчёта).
- Вызовов `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`: около 140 (`ui.js` 90, `forge.js` 26, `partitura.js` 12). Сколько из них берут чужой текст, не разобрано.
- Хостинг: есть `CNAME`, заголовки сервера на нём настроить нельзя, поэтому `frame-ancestors` и режим report-only недоступны через meta-CSP.
- Подпись Telegram на сервере уже проверяется (`sync.js`, окно 5 минут, по словам помощника).

## 4. Чек-листы для аудита игры (каждый пункт — вопрос к коду, не вывод)

### 4а. Вход (Telegram, Discord, Google, Supabase)
1. Подпись initData только на сервере; `initDataUnsafe` не доверять.
2. Ключ: HMAC с ключом `"WebAppData"` над токеном бота (не `SHA256(bot_token)`: так считается старый Login Widget). Сверять с документацией, блоги путают.
3. В строку не включать `hash`/`signature`; строки сортировать, соединять `\n`, сравнение за постоянное время.
4. Свежесть `auth_date`: подпись её не доказывает. Срок выбирает владелец (tma.js по умолчанию сутки, блоги ~5 минут).
5. Повторная отправка старого initData: размен на свою короткую сессию, по возможности одноразово.
6. Токен бота и `client_secret` только на сервере; не в логах.
7. Launch-параметры в `location.hash`: убрать `history.replaceState` после старта.
8. Токены не в `localStorage`, если можно иначе (OWASP); источники спорят, исследование TENET нашло утечки токенов у 30 из 37 Mini App; Telegram даёт SecureStorage.
9. OAuth: код авторизации с PKCE S256, не implicit; в supabase-js по умолчанию `flowType: 'implicit'`, задавать явно.
10. `state`: случайный, одноразовый, привязан к браузеру; без него возможна принудительная привязка чужого профиля.
11. `redirect_uri`: точное совпадение, без масок; в Supabase не оставлять `**` в продакшене; никаких `?next=` с чужим адресом.
12. Google не пускает вход во встроенном браузере Telegram (`disallowed_useragent`): открывать внешний браузер и возвращаться ссылкой с одноразовым кодом (последнее — мой вывод).
13. Страница callback: без сторонних скриптов, `Referrer-Policy: no-referrer`.
14. ID-токен проверять целиком (подпись, `iss`, `aud`, `exp`, `nonce`); человека определять по `sub`, не по почте.
15. Discord: почта может быть с `verified: false`; опираться на Discord-id.
16. Автосвязывание по почте только при подтверждении с обеих сторон; ручное `linkIdentity` только из вошедшей сессии.
17. Действие «привязать аккаунт» защищать как вход (`state` привязан к игроку).
18. После входа новая сессия, короткий срок, выход обнуляет серверную сторону.
19. Edge Function с `verify_jwt=false` или `service_role`: вызывающего проверять внутри; `user_metadata` не для прав; удаление пользователя не отзывает токен.
20. Секреты (бот, `client_secret`, `service_role`) только на сервере; перед коммитом сканировать.
Слабые источники: пункты 5, 7, 12; спорный: 8. Не выяснено: поддерживает ли Discord PKCE официально.

### 4б. Защита рекордов и античит (приёмы по убыванию пользы)
1. Таблицы закрыты от прямой записи; счёт принимает только функция на сервере. Секреты подписи в JavaScript бесполезны (Gamee в Telegram взломали одним вызовом из консоли).
2. Старт забега выдаёт сервер: одноразовый номер, зерно, время, версия игры; срок короткий.
3. Сверка времени по часам сервера: заявленная длина полёта ≈ время между стартом и отправкой.
4. Проверка правдоподобия записи: скорость за шаг, скачки, точки внутри поля, число точек по длительности, счёт выводится из точек.
5. Верхний предел счёта по замыслу игры; близкие к пределу в лог.
6. Ограничение частоты и размера (в самой базе, без внешних сервисов).
7. Полный повтор полёта на сервере только для претендентов (Небо месяца, рекорды, дуэли, эстафета): нужен общий код симуляции; дорого; ядро только по отдельной просьбе.
8. Детерминизм под повтор: фиксированный шаг, своё зерно, свои `sin`/`cos`; на разных движках `Math.*` не обязан совпадать (проверять цифрами на Safari, Telegram WebView, Deno).
9. Сервер сам выбирает зерно и уровень.
10. Статистика выбросов раз в сутки (отклонение от медианы больше 3,5 MAD, скачок места, новый аккаунт в топ-10) в очередь на разбор.
11. Ловушка (honeypot): данные и функции, которых честный клиент не трогает.
12. Статус «на проверке» вместо удаления.
13. initData проверяется (подтверждает, кто пишет, не счёт).
14. Версия игры в токене.
15. Анализ интервалов ввода — самый слабый.
Что нельзя: сервер проверяет согласованность, не то, что играл человек; бот с правдоподобным вводом проходит любую проверку записи. Источники: dev.to «Don't Trust the Score» (Gowtham R), PR SysCommander #8, PR Asherbinyy #40, Хабр «История взлома всех игр в Telegram», OWASP Game Security Framework 0.5.1.

### 4в. Ошибки у игроков
1. Отдельные обработчики `error` и `unhandledrejection` (в игре есть в `blackbox.js`, `skymail.js`).
2. Чужие скрипты дают «Script error.»; сейчас скриптов не чужих.
3. Отправка через `sendBeacon` (до 64 КиБ) при `visibilitychange` hidden; запасной `fetch` с `keepalive`.
4. Группировка по отпечатку: хеш из типа ошибки, текста без цифр и 2–3 верхних функций стека без номеров строк (моя сборка по принципам Sentry).
5. Новое или регрессия: версия игры к каждой записи.
6. Считать устройства, не события; лимит на клиенте.
7. Не видят обработчики: ошибки в чужих обёртках, утечки памяти без исключений: нужны свои счётчики.
8. Reporting API / `ReportingObserver`: в слабых WebView Telegram не проверено.
9–10. Приватность: не собирать полный адрес страницы (в `location.hash` лежат данные запуска), тела запросов, куки, значения переменных из стека, содержимое хранилища, IP; псевдоидентификатор устройства.
11. Серверная таблица с RLS: только добавление через функцию с лимитом частоты.

### 4г. Безопасность веб-игры
1. Всё не из кода игры (имена, письма, облако, названия из Конструктора) вставлять через `textContent` или `createElement`; `innerHTML` только из констант.
2. Всё с сервера и из облака недоверенное (`sync.js`, «Почта неба»).
3. CSP: убрать `unsafe-inline` (хеши inline-скриптов, отказ от `onclick=`).
4. В meta-CSP не работают `frame-ancestors`, `report-to`, `sandbox`, report-only; хостинг без заголовков.
5. Trusted Types (только Chromium; через meta не проверено).
6. Сторонние скрипты: только с `integrity`; урок polyfill.io.
7. `connect-src` на один домен Supabase (так и есть); каждый новый адрес осознанно.
8. Секреты: в клиенте только публичный ключ; `gitleaks` по всей истории; утёкшие ключи менять.
9. Подпись Telegram и свежесть (см. 4а).
10–14. RLS на каждой таблице; права по умолчанию отзывать (`ALTER DEFAULT PRIVILEGES … REVOKE`); `SECURITY DEFINER` с `search_path = ''` и проверкой `auth.uid()`; представления с `security_invoker = true`; `user_metadata` не в политиках; у `UPDATE` оба условия.
15. Ограничение частоты записи (особенно «Почта неба» и ошибки) через функцию в базе.
16. Service worker: готовый «самоуничтожающийся» `sw.js` под рукой; не кешировать личное; регистрация только своего домена.
17. `localStorage` целиком крадётся при XSS: токены не держать.
18. `window.open` и новые окна с `noopener,noreferrer`.
19. Версии библиотек и lockfile.
20. Чужие скиллы — тоже цепочка поставки: читать целиком до установки.

### 4д. Скорость и память (замерять прежде, чем менять)
1. Замерять на настоящем телефоне: USB-отладка, Performance, Frame rendering stats; три прогона, медиана; запись экрана сама роняет FPS.
2. Мерить плавность по доле пропущенных кадров и 95-му процентилю (web.dev/smoothness), не по среднему.
3. Автоснижение разрешения: уже есть (`render.js` `qualityTick`, потолок плотности в `core.js`); проверить на A03 и Oppo.
4. Класс устройства Telegram (LOW/AVERAGE/HIGH): уже читается.
5. Убрать `shadowBlur` и `ctx.filter` из кадра (≈24 и 4 места): замедление процессора в DevTools видеочип не замедляет, на компьютере проблему не увидеть.
6. Неподвижное рисовать один раз: офскрин, кэш (38 `createElement('canvas')`, 17 `OffscreenCanvas`); каждый буфер весит ширина×высота×4 байта.
7. Останавливать цикл и анимации невидимых экранов (8 `visibilitychange`).
8. Освобождать холсты ушедших экранов.
9. Не создавать мусор в кадре (пулы, переиспользование массивов).
10. Тест «открыть-закрыть экран 200 раз» по узлам и слушателям (идея denodell/playwright-soak-test, пакет не ставить).
11. SVG/CSS-анимации: двигать только `transform`, `opacity` (≈81 мест); менять эмблемы только через макет.
12. 30 к/с для эффектов или на классе LOW: число и порог решает владелец.
13–16. Группировать смены состояния контекста; кэшировать надписи; `getImageData` не в кадре; `alpha:false` для непрозрачных холстов.
17–18. Замедление процессора (`Emulation.setCPUThrottlingRate` 4–6) как сито в тестах; бюджет кадра на худших экранах.
19–20. Перерисовка только изменённых прямоугольников и `OffscreenCanvas` в потоке: дорого, рискованно, второе трогает ядро.

## 6. Поиск на языках мира (82 запроса, 20 языков; прочитано целиком 5 источников, остальное в пересказе WebFetch)

Главные находки (проверять перед применением; имена настроек из Qiita не подтверждены в официальной документации):
1. **Бюджет списка описаний скиллов.** Список описаний, который видит ассистент, ограничен (около 8000 знаков запасное значение, 1% окна), на один скилл потолок 1536 знаков (описание + when_to_use); лишнее молча выбрасывается (docs: code.claude.com/docs/en/skills; Qiita suwa_nobu 14.09.2026). Для нас: 16 своих описаний были 5282 знака (теперь 4207) плюс десятки скиллов плагинов. Проверка: `/doctor`, `/skill-doctor`. Лечение чужих: режим `name-only` в `skillOverrides` (настройка, только по слову владельца).
2. **`claude plugin eval`** (версия 2.1.269+): прогон случаев 3 раза с плагином и без, проверка `tool_used: Skill` (вызвался ли скилл на человеческую фразу). Официальная страница про evals (корейская версия прочитана целиком).
3. **Принудительная оценка скиллов хуком** (velog devty, 160 прогонов: подсказка 20–50%, принудительная ~84%, `/имя` ~100%; правка описания +23–28 пунктов). Хуки без слова владельца не добавляем.
4. **Метод описания (Qiita toarusyakaijin, iTech/cnblogs):** описание писать «настойчиво», объяснять причину вместо «ВСЕГДА/НИКОГДА»; не писать в описание шаги выполнения (модель идёт по ним и не читает SKILL.md); для проверки 20 запросов, 8–10 из них не должны срабатывать; «почти попадающие» запросы ценнее простых; 3 прогона; деление 60/40; до 5 кругов правки.
5. **Раздел «Ловушки» (Gotchas) в скилле** (Zenn tadkud 05.06.2026: у 32 из 54 скиллов завели, реальные записи у 3; корень — статья Thariq из Anthropic): дата, причина, решение, как заметить. Совпадает с журналом `razbor-promaha`.
6. **CLAUDE.md не раздувать** (Zenn pepabo: 114 847 → 19 232 токенов на старте; TabNews: у каждого временного исключения `EXPIRES: ГГГГ-ММ-ДД`; Zenn dely_jp: после 3 одинаковых ошибок предлагать правило, критерий «если убрать строку, ошибётся ли Claude?»).
7. **Безопасность чужих скиллов** (Tencent Zhuque: 50 000+ скиллов; Snyk ToxicSkills: 36,8% из 3 984 с проблемами; Datadog: команды в стиле `!` выполняются до того, как модель прочтёт скилл).
