# 🎬 Архитектура «Кино полёта»: Replay-to-Video через виртуальную камеру

> **Стандарт:** Fixed-Timestep Replay Rendering (WebCodecs + Replay Camera)  
> **Миссия:** Никакого захвата экрана в реальном времени. Рендер эталонного видео 9:16 (1080×1920) прямо из детерминированной ленты.
>
> **⚠️ Статус (26.08.2026): пайплайн ниже не построен.** Ни в `cosmogram-app`, ни в
> `cosmogram-crew` нет ни строки `VideoEncoder`/`mp4-muxer` — это план, а не код. Единственное,
> что реально существует — зонд совместимости (`js/beacon.js`, `webcodecsProbe()`), который
> спрашивает браузер «сможешь ли ты?» и шлёт ответ телеметрией, ничего не строя. Раздел 0 ниже —
> живые числа с этого зонда; они меняют раздел 2, поэтому читайте его первым.

## 0. Живые данные зонда (сверка 26.08.2026)

Зонд `webcodecsProbe()` проверял только H.264 с 24.08.2026 — живые данные (несколько
устройств, десятки проб за два дня) показали **0% успеха**, и на hw, и на sw, независимо от
версии WebView. 26.08.2026 зонд расширен на VP8/VP9/AV1 (`js/beacon.js`, коммент
«v1.473.0 + правка 26.08.2026»). Результат (25 проб, версии 1.477.3–1.477.8):

| Кодек | Аппаратно (`prefer-hardware`) | Программно (`prefer-software`) |
| :--- | :---: | :---: |
| **H.264** (`avc1.42001E`) | 0% (0/25) | 0% (0/25) |
| **VP8** (`vp8`) | 0% (0/25) | **100%** (25/25) |
| **VP9** (`vp09.00.10.08`) | 0% (0/25) | **100%** (25/25) |
| **AV1** (`av01.0.04M.08`) | 0% (0/25) | 84% (21/25) |

**Оговорка о выборке:** судя по постоянным `360x800 dpr3` и версиям, идущим в темпе правок
этой же сессии — похоже, это **одно устройство** (Adreno 610, tier 2), не широкий парк.
Раньше (до 26.08.2026) H.264-only зонд успел собрать пробы с нескольких устройств за два
дня — там тоже 0%, это подтверждено надёжно. А вот сравнение VP8/VP9/AV1 между собой пока
держится на одном образце — нужно больше устройств, прежде чем окончательно выбирать кодек
для пайплайна.

**Что это значит для плана ниже:**
1. Аппаратного ускорения нет вовсе — ни у одного кодека, на этом устройстве. Пайплайн, если
   его строить сейчас, будет программным (`prefer-software`), не аппаратным.
2. H.264 недоступен для кодирования на устройстве — а Telegram Stories (раздел 3) требует
   именно H.264 в контейнере. Это прямое противоречие плану «закодировать H.264 на клиенте»:
   либо кодировать VP8/VP9 на клиенте и перекодировать в H.264 на сервере (Cloudflare Worker
   в `cosmogram-crew`, отдельная работа и отдельная стоимость), либо ждать более широких
   данных на случай, если у части парка устройств H.264 всё-таки работает.
3. «До 10× быстрее реального времени» (раздел 1) — обещание, привязанное к аппаратному
   энкодеру. На программном энкодере это не подтверждено и, скорее всего, оптимистично.

## 1. Концепция Replay Camera против Screen-Record

| Параметр | Запись экрана (Screen-Record) ❌ | Кино полёта (Replay-to-Video) ✅ |
| :--- | :--- | :--- |
| **Кадрирование** | Привязано к форме экрана игрока (узкое/широкое) | Эталонный вертикальный формат 9:16 (1080×1920) |
| **Скорость экспорта** | 1:1 в реальном времени (60с = 60с) | До 10× быстрее реального времени через WebCodecs |
| **Чистота кадра** | Захватывает интерфейс, табло, лаги FPS | Чистый кинематографический кадр без мусора |
| **Детерминизм** | Зависит от просадок кадров устройства | Байт-в-байт идентичный рендер из `seed + input log` |

## 2. Пайплайн генерации видео

**Черновик ниже устарел на шаге кодирования** (раздел 0) — H.264 недоступен на клиенте,
аппаратного ускорения нет вовсе. Два реальных варианта вместо старого шага 3, ни один не
выбран:

```text
┌─────────────────────────────────────────────────────────────┐
│            Детерминированная лента (Seed + Input)           │
└─────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────┐
│  Headless симуляция в OffscreenCanvas(1080, 1920) (Worker)  │
└─────────────────────────────────────────────────────────────┘
                               ↓
        ┌──────────────────────┴───────────────────────┐
        ↓                                                ↓
┌───────────────────────────┐          ┌───────────────────────────────────┐
│ Вариант А: программный     │          │ Вариант Б: программный VP8/VP9 на  │
│ VP8/VP9 (VideoEncoder,     │          │ клиенте → перекодировка в H.264 на │
│ prefer-software) на        │          │ сервере (cosmogram-crew, отдельная │
│ клиенте — прямиком в MP4   │          │ работа и стоимость транскода)      │
│ невозможно (Stories хотят  │          │                                     │
│ H.264), нужен контейнер    │          │                                     │
│ WebM или сервер поверх     │          │                                     │
└───────────────────────────┘          └───────────────────────────────────┘
        ↓                                                ↓
┌─────────────────────────────────────────────────────────────┐
│     Упаковка в MP4 (mp4-muxer) → Upload CDN → shareToStory  │
└─────────────────────────────────────────────────────────────┘
```

Старый шаг «Аппаратный энкодер WebCodecs (VideoEncoder + H.264)» убран целиком — живые данные
(раздел 0) показывают 0% поддержки H.264 на всех замерах в базе (25 новых многокодечных проб
26.08.2026 + минимум 15 более ранних H.264-only проб 24-25.08.2026, `select * from beacons
where msg like 'webcodecs_probe%'`), hw и sw, ни одного исключения. Решение
между вариантом А и Б — отдельный вопрос с явными компромиссами (сложность/скорость/охват
устройств), не додумывается здесь.

## 3. Требования Telegram Stories (`shareToStory`)

- **Формат:** MP4 (H.264 / AAC), 30 FPS, разрешение 1080×1920 (9:16). Это требование самого
  Telegram, не наш выбор — и именно оно конфликтует с разделом 0 (H.264-энкодер недоступен на
  клиенте). Смотри варианты А/Б в разделе 2.
- **Безопасные зоны (Safe Zones):**
  - Верхние 14% (~250 px): аватар и индикаторы историй.
  - Нижние 20% (~340 px): поле ввода ответа и реакции.
  - Центральная активная зона: 1080×1330 px.
- **Интеграция:** Метод `Telegram.WebApp.shareToStory(media_url, params)` принимает HTTPS URL с CDN.
