# ⚡ Cosmogram — Performance Engineering & Optimization

> **Target:** Solid 60/120 FPS on all devices (from Redmi 9A / Android Go to 4K Pro Displays)  
> **Frame Budget:** 16.666 ms total (4ms logic update + 10ms render + 2.666ms headroom)  
> **Memory Allocation:** Zero Garbage Collection allocations during active gameplay tick

---

> **Подтверждение из научного материала:** согласно статье
> `memory-management-gc` (ARTICLES/), использование статических пулов
> объектов (pool‑pattern) гарантирует zero‑allocation в горячих циклах,
> что полностью соответствует правилу §1 и исключает случайные GC‑списки.
> **Дополнительное подтверждение из мобильного опыта (Tencent Cloud/CSDN):**
> В sandbox-средах (WeChat Mini Games, мобильные Safari/Chrome) основная причина GC‑фризов — утекшие текстуры при смене ориентации экрана или смены сцен. Обязательно вызывайте `.clear()` или обнуляйте ссылки на неиспользуемые `ImageBitmap` / `OffscreenCanvas` *снаружи* игрового цикла, чтобы GC мог их уничтожить.

### Базовые правила

1. **Никаких `new` и `{}` в цикле:** Запрещено создавать временные объекты, массивы или замыкания. Все объекты берутся из статических пулов (`poolOb`, `poolStar`, `poolPart`, `poolPop`).
2. **Многослойный рендеринг (Layered Canvases):**
   - *Фоновый слой:* Звездный фон и туманности предрендерятся на Offscreen Canvas один раз или обновляются на низком FPS.
   - *Игровой слой:* Динамические объекты (самолётик, астероиды, бонусы).
   - *Слой эффектов:* Частицы и взрывы.
   - *Слой HUD:* DOM/CSS или отдельный легковесный Canvas без перерисовки мира.
3. **Целые координаты в `drawImage`:** Использовать `Math.floor(x)` или битовый сдвиг `x | 0`. Дробные координаты включают субпиксельный антиалиасинг, нагружая GPU.
4. **Отказ от `ctx.shadowBlur`:** Свечение создается предрендеренными спрайтами с аддитивным смешиванием (`globalCompositeOperation = 'lighter'`).
5. **Минимизация `save()` / `restore()`:** Стек состояний Canvas дорог. Выполняется группировка (батчинг) отрисовки по стилям и типам спрайтов.
6. **Кэширование `Path2D` для астероидов:** Силуэт каждого камня генерируется единожды при спавне в `Path2D`. Это экономит ~6000 вычислений `Math.sin`/`Math.cos` в секунду.
7. **`alpha: false` для основного контекста:** Контекст Canvas создается с `{ alpha: false }`, исключая ненужное композитирование страницы под ним.
8. **Occlusion Culling:** Объекты и частицы вне зоны видимости (`y > fieldB() + 200` или `y < fieldT() - 200`) исключаются из цикла отрисовки.
9. **DPR Scaling & Потолок листа:** Холст масштабируется под DPR экрана, но ограничен максимум 2560 px по длинной стороне, чтобы не перегружать 4K экраны.
10. **Спящая пауза (Sleeping Pause):**
    - В активном полете: 60/120 FPS.
    - В меню/витринах: ~30 FPS.
    - На паузе после 2 сек: переход на ~4 FPS (экономия 95% CPU/батареи).

### Дополнено 2026 (детали и замеры)

### 2.11 Батчинг и группировка операций рисования
- **Замер:** Комбинирование операций рисования вместо чередования даёт рост с 1611 до 20 942 итераций/с (≈13×). Группировка по `fillStyle` вместо чередования цвета на каждой фигуре — +27% (Tizen/Samsung, 2012, подтверждено современными источниками).  
- **Наш случай:** 10 315 записей `strokeStyle` и `lineWidth` в секунду — явный признак рисования звёзд по одной с переключением состояния. Группировка звёзд по толщине/цвету в один `Path2D` или один `stroke()` может дать заметный выигрыш.  
- **Рекомендация:** Рисовать все объекты одного стиля за один вызов `beginPath`/`stroke`/`fill`; избегать чередования стилей в цикле.

### 2.12 Использование Path2D для статичных форм
- Силуэт астероида вычисляется заново каждый кадр (~6000 пар `cos/sin`/с). Форма не меняется после спавна.  
- **Решение:** Построить `Path2D` один раз при спавне и использовать `ctx.fill(path)` или `ctx.stroke(path)` в кадре.  
- Это также даёт дешёвый `isPointInPath` для хит-тестинга.

**Код (перенесён сюда 25.08.2026 из дублирующего раздела в конце файла — тот же факт, тот же приём, был описан дважды):**
```javascript
const rockPath = new Path2D();
rockPath.moveTo(verts[0].x, verts[0].y);
for (let i = 1; i < verts.length; i++) {
  rockPath.lineTo(verts[i].x, verts[i].y);
}
rockPath.closePath();
// В кадре:
ctx.fill(rockPath); // До 10× быстрее перестроения путей
```

### 2.13 Отказ от shadowBlur
- `shadowBlur` — дорогая операция свёртки; при высоком DPR (3×) цена растёт квадратично.  
- **Альтернатива:** предрендеренные спрайты свечений с `globalCompositeOperation = 'lighter'`.

### 2.14 alpha: false и desynchronized: true
- `Устанавливайте alpha: false` при создании контекста, если фон непрозрачен (наше небо всегда непрозрачно). Это отключает композитинг с фоном страницы.
- `desynchronized: true` снижает задержку ввода (полезно для управления), но требует осторожности (может вызвать разрывы кадра на некоторых устройствах). Проверяйте на целевых устройствах.

### 2.15 Ограничение DPR
- При DPR=3 заливка в 9 раз больше, чем при DPR=1.  
- На слабых устройствах ограничивайте DPR до 2 (или адаптивно по измеренному fill rate).  
- Дробные DPR (2.625, 2.75) встречаются на некоторых Android-устройствах — округляйте до целого или проверяйте артефакты.

### 2.16 Избегайте лишних слоёв canvas
- Каждый слой — дополнительный полноразмерный буфер. При высоком DPR и без `alpha:false` это увеличивает нагрузку на композитор.  
- Используйте слои только если статика и динамика действительно разделены и вы измеряете выигрыш.

### 2.17 Замеряйте не среднее, а хвост распределения
- Используйте 95-й перцентиль и худший случай в скользящих окнах по 1 секунде (web.dev).  
- Используйте Long Animation Frames API для атрибуции долгих кадров к конкретным функциям в проде.  
- Для симуляции слабых устройств используйте калиброванный CPU-троттлинг в DevTools (апрель 2025), но помните, что он не моделирует GPU-нагрузку.

### 2.18 Осторожно с программным рендерингом
- На некоторых устройствах/драйверах Canvas 2D может переключиться на программный рендеринг, что даёт падение FPS в 30–80 раз.  
- Проверяйте на целевых Android WebView (внутри Telegram) наличие аппаратного ускорения.  
- Избегайте `getImageData` без `willReadFrequently: false` — два вызова могут отключить GPU-ускорение (недокументированное поведение Chrome).

### 2.19 Пулы памяти: Zero-GC — закон, а не совет

Для Cosmogram это не совет — это закон: **Zero-GC в тике обязателен всегда** (STYLE-GUIDE §1, §6 п.1). Исключение не обсуждается.

| Пул | Cap | Назначение |
|-----|-----|------------|
| `poolOb` / `poolStar` | 64 / 64 | Препятствия, звёзды |
| `poolPw` | 16 | Бонусы |
| `poolPart` | 120–220 | Частицы (по тиру: low 120, mid 180, high 220) |
| `poolPop` | 32 | Всплывающие очки |

**Инвариант возврата в пул** (обязателен):
```javascript
give(o) {
  if (free.length < maxCap) {
    o._tint = null;
    o._path = null;
    o._tg = null;
    o._tgk = undefined;
    free.push(o);
  }
}
```

### 2.20 Интерполяция остатка (alpha)
- При фиксированном шаге 60 Гц и частоте рендера 120+ Гц рисование позиции последнего тика даёт микро-дёрганье.  
- Используйте линейную интерполяцию между предыдущим и текущим состоянием с коэффициентом `alpha = accumulator / STEP`. Это не меняет детерминизм физики, только визуал.

### 2.22 Детерминизм: Rune.ai patching, fixed-point, idle-генерация

- **Rune.ai patching Math.sin/cos (альтернатива LUT).** Rune.ai патчит `Math.sin/cos`
  на этапе загрузки — заменяя их на поиск в 3600-ячейковой `Float32Array`-таблице с
  линейной интерполяцией. Даёт bit-perfect кросс-платформенную детерминизм без рефакторинга.
  Для Cosmogram: ваш LUT в `SIN_LUT`/`COS_LUT` (360° дискретность) работает, но Rune
  подходит, если нужна **любая** транцендентная функция. Выбирайте один путь — не смешивайте.
- **Fixed-point (16.16) вместо float.** Альтернатива LUT для полной детерминизма:
  все арифметические операции через целые числа (`x * SCALE >> 16`). Идеально, когда
  нужна не тригонометрия, а именно гарантированная идентичность вычислений на всех CPU.
  [ДОК] пример реализации: https://github.com/…/fixed-point-math
- **`requestIdleCallback` для генерации контента.** «Трасса дня», «Кузница», прочие
  процедурные порции — не блокируют рендер. Работают в idle-циклах с `timeout: 2000`,
  выдавая по ~20 объектов за раз через `timeRemaining() > 2`.

### 2.23 Видео-экспорт: Replay-to-Video через WebCodecs

- **Принцип:** Никогда не screen-record. Рендерим из детерминированной ленты через отдельную «кино-камеру».
- **Эталонный формат:** 1080×1920 (9:16), 30 fps, H.264/AAC, ≤60 сек.
- **Технология:**  
  1. Headless симуляция в `OffscreenCanvas(1080,1920)` в Web Worker.  
  2. `VideoEncoder` (аппаратный) + `mp4-muxer` → до **10× faster-than-realtime**.  
  3. Fallback: `MediaRecorder + canvas.captureStream()` → `ffmpeg.wasm` (real-time only, WebM).
- **Детерминизм:** Симуляция идёт по **frame-index**, а не wall-clock. Любая случайность — через seed (уже покрыто mulberry32).  
- **Telegram-специфика:** `shareToStory(media_url, {text})` принимает URL, не Blob. Safe zones: top ~14%, bottom ~20%.  
- **Server-side (v2 опционально):** seed + tape → headless Chromium/Native + FFmpeg → байт-в-байт идентичный MP4 на всех устройствах.
- **Контраст со screen-record:**  
  | | Screen-Record | Кино полёта |  
  |---|---|---|  
  | Кадрирование | Экран игрока | Эталон 9:16 |  
  | Скорость | 1:1 | До 10× быстрее |  
  | Чистота | UI, лаги | Чистый кадр |  
  | Детерминизм | Зависит от FPS | Байт-в-байт |

### 2.24 Современные браузерные паттерны (2024–2026)

| Паттерн | Суть | Применение в Cosmogram |
|---------|------|------------------------|
| **Struct of Arrays (SoA)** | TypedArrays (`posX`, `posY`, `active`) вместо массивов объектов | Заменяет пулы объектов на плоские буферы для препятствий, звёзд, частиц — исключает скрытые аллокации, позволяет SIMD-векоризацию V8 |
| **ImageBitmap + Transferable** | `createImageBitmap()` + `postMessage(..., [bitmap])` — zero-copy передача текстур из Web Worker | Подготовка спрайтов/градиентов в воркере, передача в основной поток без копирования памяти |
| **WebCodecs API** | `VideoDecoder` + `decodeVideoFrame()` с HW-ускорением, `drawImage()` zero-copy | Кино-экспорт (§2.23): аппаратный декод/энкод, байт-в-байт детерминизм |
| **Инкрементальный GC-friendly буферы** | Единый `ArrayBuffer` + TypedArrays = один компактный массив для V8 | Рассмотреть для единого игрового состояния (seed, tape, entities) — снижает частоту minor/major GC |

> **Подтверждение из `memory-management-gc` (ARTICLES/):** статические пулы объектов (pool-pattern) гарантируют zero-allocation в горячих циклах. SoA — следующая ступень: убирает даже накладные расходы на управление пулом.

> **Подтверждение из мобильного опыта (Tencent Cloud/CSDN):** в sandbox-средах (WeChat Mini Games, Safari/Chrome) основная причина GC‑фризов — утекшие текстуры при смене ориентации/сцены. Обязательно `.clear()` ссылок на `ImageBitmap` / `OffscreenCanvas` *снаружи* игрового цикла.

## 3. Специфика Telegram Mini Apps (Web Vitals & WebView Limits)

### LCP (Largest Contentful Paint) — Быстрый взлет:
- **Preload в `<head>`:** Предзагрузка `telegram-web-app.js`, `core.js` и шрифтов Exo 2.
- **CSS-скелетон фона:** Мгновенный показ градиента неба до инициализации JS.
- **`font-display: swap`:** Текст меню показывается мгновенно без блокировки.

### INP (Interaction to Next Paint) — Мгновенный руль:
- В обработчиках `touchmove` / `pointermove` происходит **только запись координат цели** (`targetX = e.touches[0].clientX`). Никакой физики внутри событийного потока.
- Вся физика и расчеты выполняются синхронно в тике `requestAnimationFrame`.
- Слушатели событий вешаются с `{ passive: true }`, кроме мест, где требуется блокировка свайпа закрытия.
- `touchstart` — единственное исключение из `passive:true`: он подписывается `{passive:false}` с `preventDefault()` (закон К36).

### Ограничения памяти (WKWebView / Android WebView):
- **Лимит памяти iOS:** При превышении ~256-512 МБ WebView перезагружает страницу молча.
- **Статический пул спрайтов:** Запрещено создавать новые `OffscreenCanvas` во время забега. Все градиенты и свечения переиспользуют фиксированный пул буферов.
- **Капы по тирам устройств:**
  - Android Go / Low-End: `PARTICLE_CAP = 120`
  - Mid-Range: `PARTICLE_CAP = 180`
  - Flagships / Ultra: `PARTICLE_CAP = 220`

## 5. HiDPI Canvas & Ресайз

> Раздел из «Masterclass»-приложения (Production Canvas 2D Engineering), слитого в общую
> нумерацию файла 25.08.2026 — раньше был отдельным документом со своими §1/§2/§3,
> пересекавшимися с основной нумерацией.

```javascript
class HiDPICanvas {
  static setup(canvas, ctx, logicalWidth, logicalHeight) {
    const dpr = Math.min(window.devicePixelRatio || 1, 2); // Ограничение потолком 2 для слабых GPU
    canvas.width = (logicalWidth * dpr) | 0;
    canvas.height = (logicalHeight * dpr) | 0;
    canvas.style.width = logicalWidth + 'px';
    canvas.style.height = logicalHeight + 'px';
    ctx.scale(dpr, dpr);
    canvas._dpr = dpr;
  }
}
```

## 6. VisibilityGuard (защита от скачков dt при сворачивании)

```javascript
class VisibilityGuard {
  constructor() {
    this.MAX_DELTA = 0.25; // Защита от спирали смерти
    document.addEventListener('visibilitychange', () => {
      if (document.hidden) {
        Game.pause();
        AudioManager.suspend();
      } else {
        AudioManager.resume();
        Game.resume();
        requestAnimationFrame((now) => Game.lastTime = now);
      }
    });
  }
  clampDelta(rawDelta) {
    if (document.hidden) return 0;
    return Math.min(rawDelta, this.MAX_DELTA);
  }
}
```
