# Аудит тихих отказов — весь код игры (angle 1 of 4, соло)

18.09.2026. Первый заход этой ночи разобрал один файл (`js/cinema.js`) враждебным чтением и
нашёл три реальных бага (guards 301-303, cosmogram-crew). Владелец попросил применить тот же
метод ко всей остальной игре: `js/game.js`, `js/render.js`, `js/input.js`, `js/ui.js`,
`js/forge.js`, `js/sync.js`, `js/card.js`, `js/gyro.js`, `js/core.js`. Чтение — только чтение,
без единой правки. Метод — для каждого `catch(e){}`/`catch(e){return X}` и каждого незащищённого
`await`: если это реально сработает в бою, узнает ли кто-то (тост игроку или
`BEACON.signal`)? Комментарий рядом читается ПЕРЕД тем, как что-то флагать — этот проект
дисциплинированно документирует, почему конкретная тишина безопасна, и большинство найденных
`catch` оказались именно такими, не находками.

## Находки, ранжированные по реальному влиянию

### 1. «Опубликовать в Галерее» — тихий отказ без тоста, хотя вся остальная Мастерская давно получила этот фикс (`js/forge.js:828-843`)

```js
function mapAskPublish(code, name){
  ...
  const go=()=>{ workshopSubmit(code, name).then(res=>{
    if(res && res.ok) toast(L.forgePublished||'Опубликовано в Галерее','rgba(255,215,106,.5)');
  }).catch(()=>{}).finally(()=>{ _mapPublishBusy=false; }); };
```

Сценарий: игрок пролетел свою трассу по-настоящему (`forgeIsVerified`), нажал «Поделиться»,
подтвердил «Опубликовать в Галерее — увидят все?» — и в этот момент либо нет сети, либо сервер
(`cosmogram-workshop`) отклонил публикацию (модерация, антифлуд, что угодно). `res` придёт
`null` или `{ok:false}` — и НИЧЕГО не происходит: нет тоста, нет `BEACON.signal`, кнопка просто
перестаёт быть занятой (`_mapPublishBusy=false`, страж 273 это честно проверяет — двойной тап не
дублирует отправку). Игрок не знает, опубликовано ли его небо, и либо решает, что «опубликовано»
(текст диалога это обещал), либо тыкает кнопку снова без единой подсказки, что в первый раз не
получилось.

**Почему это находка, а не гипотеза**: то же самое действие («подтвердил диалог → сеть могла не
дойти») в ЭТОМ ЖЕ файле получило ровно этот фикс шесть раз за последние две недели, каждый раз с
одинаковым комментарием-уроком:
- `workshopVote()` (лайк), `forge.js:1650-1655` — 13.09.2026, владелец: «не могу поставить лайк,
  даже когда прошёл небо» → добавлен `if(!res || !res.ok){ toast(L.syncOffline...); return; }`.
- `workshopNotice()` («Показать в Случайных»), `forge.js:1693-1699` — 18.09.2026, тот же приём.
- `workshopList()` (сама витрина), `forge.js:1362-1370` — 15.09.2026 «аудит #7»: тот же класс
  («тихий `null` схлопывался в то же сообщение, что честная пустая категория») починен явным
  различением `offline` от «треков правда нет».
- `deleteMyData()`, `ui.js:3806-3813` — `else { toast(L.accDeleteFail...); }`.
- `charterSign()`, `ui.js:4202-4205` — `if(!r || !r.ok){ toast(L.chSignOffline...); return; }`.
- `syncGratitudeCreateInvoice()`, `ui.js:4386-4387` — та же форма.

`mapAskPublish()` — единственный из этого семейства (`grep` по всему `js/`: `if(res && res.ok)`
встречается только тут, без единого `else`), который эту защиту не получил, хотя структурно
устроен идентично и хотя double-tap-фикс того же дня (страж 273) сидит в той же функции — правку
внесли рядом с багом, но не в него самого.

**Второй проверочный заход**: `guard.mjs` (cosmogram-crew) — страж 273 проверяет только защиту
от повторного тапа (`grep 'mapAskPublish'` — единственное совпадение). Ни одного стража на
`workshopSubmit()` возвращающий `{ok:false}`/`null` нет. Не задокументировано ни в
`KNOWN-BUGS.md`, ни в `AI-DECISION-REGISTRY.md`.

### 2. Модерация Мастерской (закрепить/скрыть/«Выбор автора») — тот же класс тишины, три места подряд (`js/forge.js:1712-1714, 1726-1731, 1737-1739`)

```js
workshopModerate(code, next).then(function(res){
  if(!res || !res.ok) return;      // «pin» (закрепить) — 1712-1714
  ...
});
...
workshopModerateFeatured(code, next).then(function(res){
  if(!res || !res.ok) return;      // «pickstar» («Выбор автора») — 1726-1731
  ...
});
...
workshopModerate(code, next).then(function(res){
  if(!res || !res.ok) return;      // «hide» (скрыть) — 1737-1739
  ...
});
```

Буквально та же форма, что у `mapAskPublish` (п.1) — `grep -n "if(!res || !res.ok) return;"
js/*.js` во всём проекте находит РОВНО эти три строки, нигде больше. Отказ сервера (сеть, либо
сервер честно отверг — сам код рядом напоминает «сервер всё равно проверяет `OWNER_ID`») тихо
ничего не делает: значок остаётся в прежнем визуальном состоянии, тоста нет, `BEACON.signal` нет.

**Влияние ниже, чем у находки 1** — по коду и комментариям («кнопка здесь лишь скрыта для
остальных игроков», «сервер сам проверяет `OWNER_ID` ещё раз») эти три действия видны только
владельцу студии как модератору собственной Мастерской, не рядовым игрокам — не находка уровня
«игрок теряет данные», но тот же пробел в диагностике, тем же почерком, и тому, кто и должен
заметить сбой (сам разработчик, разбирающий жалобы на витрину), сейчас неоткуда узнать, что тап
не подействовал.

**Второй проверочный заход**: `grep -n "workshopModerate\|pickstar" cosmogram-crew/tests/
guard.mjs` — единственный страж (у 8437+) мокает `workshopModerateFeatured` только счастливым
путём (`Promise.resolve({ok:true,...})`), путь отказа не проверен ни разу.

### 3. `sync.js` — ни одного `BEACON.signal` во всём файле (структурное наблюдение, не однозначный баг)

`grep -c BEACON.signal js/sync.js` → 0, при том что это самый сетевой файл проекта (16 разных
Edge-Function-обёрток). Это **не** тихий баг в духе находок 1-2 — почти все функции файла
осознанно устроены как очередь-с-растущей-паузой (`syncBackoffFail`/`syncBackoffReady`,
18.09.2026 «Нарастающая пауза», см. шапку файла) и текст в файле прямо говорит: «Тихая: никаких
тостов/ошибок игроку» (`syncSubmit()`, комментарий строка 274) — это осознанное решение для
пути рекордов конкретно, не забытый случай. Но 15 других действий в этом же файле
(`workshopSubmit`, `charterSign`, `syncBuySkinInvoice`, `syncGratitudeCreateInvoice`,
`deleteMyData` и т.д.) тоже никогда не зовут `BEACON.signal` сами — они полагаются целиком на
UI-слой (ui.js/forge.js), который читает `null`/`{ok:false}` и уже решает, тостить или нет (и,
как показывают находки 1-2, иногда забывает). Отмечаю как наблюдение для дальнейшей архитектурной
дискуссии, не как отдельный баг: если бы `syncPost()`/`workshopPost()` сами сигналили в BEACON на
5xx/сетевой отказ (не на 4xx — те содержательные), находки 1 и 2 стали бы видны в телеметрии даже
без починки каждого вызывающего места по отдельности. Решение не принимаю сам — это архитектурная
правка общего файла (`sync.js`), не однострочный фикс.

## Проверено и НЕ находка (второй заход подтвердил безопасность)

- **`feedbackSend()` (`ui.js:2852-2872`)** — `await BEACON.feedback(text, photos)` без try/catch
  вокруг всей функции выглядело как риск «busy-флаг навсегда» (тот самый класс, что уже находили
  у `angarBuyPremium`/`grSendBtn`, guards 271-272). Проверено до конца: `BEACON.feedback()`
  (`skymail.js:518-547`) сама обёрнута в try/catch/finally и ВСЕГДА резолвится объектом
  `{ok,...}` (`catch(e){ return {ok:false, reason:'net'}; }`), никогда не реджектится — `await`
  безопасен, `feedbackSending`/`btn.disabled` гарантированно снимутся. Ложная тревога, отклонена
  вторым заходом (чтение реализации `BEACON.feedback`, не только сигнатуры).
- **`gyroUnlockBtn`/`diagFixSensor()`/`tiltBtn` (`ui.js`, `gyro.js`)** — все три пути к
  `DeviceOrientationEvent.requestPermission()` держат `try{...}catch(e){ r=''; }` — отказ и
  техническая неудача разбираются как один честный исход («молча работаем пальцем дальше»,
  комментарий в `gyro.js:76`), с таймаутом-сторожем 7с на молчание датчика
  (`gyroOverUnlock()`, `gyro.js:83-86`). Ничего не найдено, специально проверено.
- **`js/game.js`** — прочитан целиком на предмет catch/async: НИ ОДНОГО `catch` и НИ ОДНОЙ
  `async function` во всём файле (`grep` подтверждает 0/0). Файл работает только с уже
  безопасным `Store.get/set` (сам `Store` — см. ниже) и синхронной физикой — класс «тихий отказ
  I/O» сюда структурно неприменим. Ничего не найдено.
- **`js/render.js`** — 5734 строки, ровно один `catch` во всём файле
  (`render.js:2283`, телеметрия `skin_perf`, безопасно обёрнута). Главный цикл `loop()`
  (`render.js:5677-5732`) НЕ обёрнут в try/catch, но `rafId=requestAnimationFrame(loop)` —
  первая строка функции, ДО любой логики кадра: если что-то внутри кадра бросит, следующий кадр
  всё равно уже поставлен в очередь браузером — не «зависшая игра», а один пропущенный кадр с
  необработанным исключением в консоли. Тот класс («Script error.» без адреса, мост Telegram не
  пропускает такие исключения в `window.onerror`) уже задокументирован в `KNOWN-BUGS.md`
  (раздел про `[fps:X lvl:Y tier:Z] Script error.`, 03.09.2026) — не переоткрываю.
- **`js/input.js`, `js/gyro.js`, `js/core.js`** — прочитаны построчно по каждому найденному
  `catch` (полный список см. в истории поиска этой сессии). Все укладываются в два безопасных
  паттерна: (а) заведомо необязательное действие (`navigator.vibrate`, `history.pushState`,
  `tg.BackButton.show`) — падение никак не важно и не должно быть видно; (б) уже
  задокументированный урок с датой и объяснением, почему тишина здесь безопасна (например,
  `core.js:254-262`/`316-329` — хранилище: разбор `Store._load`/`Store._write` показывает
  необычно тщательную защиту от тихой потери данных, включая сохранение битого сырья
  в `cosmogram_v2_broken` и разгрузку нетяжёлых ключей ПЕРЕД тем, как признать переполнение
  реальным — читать стоит целиком, не по одному catch, прежде чем флагать что-то в этом блоке).
- **`js/card.js`** — уже дважды в аудите этого месяца (первый видео-аудит + пасс-2,
  коммит `ebeb070` только что починил `toBlob()===null`). Единственное необязательное
  наблюдение низкого приоритета: `cardShare()` (`card.js:347`) —
  `if(!navigator.canShare({files:[file]})) return;` внутри самого `toBlob`-колбэка тоже без
  тоста/BEACON, хотя соседняя строка (344) только что получила именно этот фикс для соседнего
  условия. Гонка редкая (`canShare` уже проверялся в `cardShareGate()` при открытии карточки) —
  не поднимаю до отдельной находки, справочно.
- **Ангар/покупки скинов за Stars (`ui.js:2700-2745`)** — уже целиком починено 18.09.2026
  (комментарии «сквозная проверка, найдено при поиске похожих дыр в игре целиком») — busy-флаг
  снимается даже при синхронном throw `openInvoice()`, `syncPremiumOwned()` при сетевом отказе
  не роняет только что подтверждённую покупку. Читано, ничего нового.
- **Топ/ранг/дуэль-подгрузки (`ui.js:1266-1270, 2942-2955, 3961-3975`)** — тихий `null` на
  сетевом отказе здесь не переписывает и не удаляет ничего, только не показывает необязательную
  цифру (место в топе, статус дуэли) — при явном офлайне уже есть отдельное сообщение
  (`ui.js:3964-3965`). Ниже порога «находка», не критично по природе (read-only виджет, не
  action с подтверждением).

## Честный итог

Пять из девяти файлов (`game.js`, `render.js`, `input.js`, `gyro.js`, `core.js`) прочитаны
целиком по каждому catch/async — реальных находок в них нет: это либо чистая синхронная логика,
либо код, уже прошедший через несколько предыдущих раундов именно этого же аудита (видно по
плотности комментариев с датами и словом «сквозная проверка»). Основная находка (п.1,
`mapAskPublish`) и её более мелкий систематический близнец (п.2, три модерационных действия) —
в `forge.js`, и оба подтверждены вторым независимым способом: не просто «выглядит подозрительно»,
а прямое сравнение с шестью соседними местами того же файла/сессии, где ровно этот же класс
тишины уже был найден и исправлен в предыдущие несколько дней, но не долетел досюда. Это ровно
то, что просил владелец — не гипотеза «похоже на баг», а системная брешь, подтверждённая
повторением одного и того же кода без одного и того же уже принятого решения.
