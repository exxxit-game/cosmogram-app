## 🔴 Реальная, подтверждённая дыра — не гипотеза (05.09.2026)

Проверено через `get_advisors` (штатный линтер Supabase) + прочитаны тела функций
через `execute_sql`, не угадано по описанию.

**4 SECURITY DEFINER функции в public-схеме доступны напрямую через REST API
любому анониму, в обход Edge Function и её проверки личности/лимитов:**

| Функция | Что делает | Реальная эксплуатация |
|---|---|---|
| `increment_workshop_plays(p_code)` | `plays = plays+1` без единой проверки внутри | Любой может дёргать `/rest/v1/rpc/increment_workshop_plays` напрямую с любым кодом — накрутка «Играли больше всех» до бесконечности, без Telegram-аккаунта вообще |
| `check_rate_limit(key, window, limit)` | Общий анти-спам счётчик (используется в cosmogram-daily/sync) | Ключ — просто строка, приходит от вызывающего. Аноним может слать чужие ключи (если они угадываемы) и искусственно исчерпывать лимит НАСТОЯЩЕГО игрока — тихий отказ в обслуживании |
| `check_and_use_nonce(nonce, player_id)` | Анти-replay (одноразовые токены) | Аноним может заранее «сжечь» нужный nonce за игрока — его настоящий следующий легитимный запрос откажет как «уже использовано» |
| `rls_auto_enable()` | Служебный event-trigger (сам чинит RLS на новых таблицах) | Скорее всего просто упадёт с ошибкой при прямом вызове вне event trigger — но зря выставлен наружу |

Все четыре — с `SECURITY DEFINER`, что и делает их доступными по RPC широкому
кругу ролей по умолчанию. Штатный фикс (тот же, что рекомендует линтер Supabase):
`REVOKE EXECUTE ON FUNCTION ... FROM anon, authenticated;` — Edge Function'ы
продолжат работать как ни в чём не бывало (у них свой `service_role`-ключ, доступ
к функциям не через эти роли). Это не «додумывание параметра», это бинарная
починка без изобретаемых чисел — но живая правка прав в проде, поэтому спрашиваю,
не делаю тихо.

**Остальные ~20 предупреждений линтера ("RLS enabled no policy" на каждой
таблице) — проверено и это НЕ дыра**: RLS включён, политик нет → PostgREST
никому ничего не отдаёт напрямую по этим таблицам ни для anon, ни для
authenticated. Ровно то состояние, которое нам и нужно — все чтения/записи
идут только через service_role внутри Edge Function. Один пункт всё же спорный:
`forge_workshop_view` — вид с `SECURITY DEFINER` (уровень ERROR у линтера,
не INFO). Раз им пользуется только наш же Edge Function через service_role —
эксплуатации сейчас нет, но при RLS-без-политик-на-таблице это ровно тот
паттерн, который линтер просит проверить в первую очередь (`security_invoker`).

## 🟡 Общие категории — проверено по каждой, что у нас уже есть, а чего нет

### 1. «Никогда не доверяй клиенту»
Базовый принцип бэкендов игр: клиент можно модифицировать целиком — память,
трафик, память рантайма — сервер обязан быть единственным источником истины
по критичным решениям ([Hacker News: Never trust the client](https://news.ycombinator.com/item?id=11583008), [Imperva: fundamental security concepts for game devs](https://www.imperva.com/blog/fundamental-security-concepts-and-best-practices-every-game-developer-should-know/)).
**У нас уже так** для Мастерской (bad-word фильтр дублирован на сервере,
05.09.2026, это ровно та находка, что запустила всю сессию багхантинга). Дыра
из раздела выше — тот же класс, только зашедший с неожиданной стороны (не через
Edge Function, а в обход неё через голый RPC).

### 2. Специфика Telegram Mini Apps
Свежее (2026) исследование безопасности мини-приложений TENET: 57% проверенных
приложений хранят реплеемые токены сессий в открытом виде; частая причина —
разработчик отключает проверку `initData` на этапе разработки и забывает включить
обратно ([arXiv TENET](https://arxiv.org/html/2608.17538)). Общая рекомендация
индустрии — окно валидности `auth_date` ~5 минут против replay-атак ([QuillAudits](https://www.quillaudits.com/blog/web3-security/telegram-mini-apps-security), [DEV: validate initData](https://dev.to/serhii_a9c08345ac360cf5c8/validate-telegram-mini-app-initdata-in-php-hmac-sha-256-timing-safe-compare-and-authdate-expiry-4c92)).
**У нас**: `AUTH_MAX_AGE_SEC = 7*86400` (7 дней) в каждой Edge Function —
заметно шире отраслевых «пяти минут». Это не случайная ошибка (сама механика
`initData` не одноразовая и переиспользуется клиентом в рамках одной сессии
Telegram, не для одного запроса), но разница с общепринятой практикой достаточно
большая, чтобы владельцу стоило явно решить: сокращать окно или оставить —
отдельный вопрос, не додумываю сам.

### 3. Платежи Stars — идемпотентность и возвраты
Стандартная практика: хранить `telegram_payment_charge_id` с уникальным
ограничением в базе — при повторном событии `successful_payment` (Telegram
иногда шлёт дубликаты) второй insert должен упасть на UNIQUE и вернуть уже
существующую запись, не начислять товар дважды; тот же id нужен позже для
`refundStarPayment` ([Telegram Bot Payments API](https://core.telegram.org/bots/payments-stars), [n8n: Stars refund workflow](https://n8n.io/workflows/2461-telegram-payment-invoicing-and-refund-workflow-for-stars/)).
**У нас**: реальные Stars-покупки ещё не запущены (монетизация отложена как
отдельный разговор, см. [[project_monetizatsiya_dosug_obsuzhdenie]]) — но таблица
`premium_purchases` уже существует в базе. Когда монетизация дойдёт до кода —
это готовый чек-лист на день реализации, не сейчас.

### 4. Ограничение частоты / накрутка ботами
Слой должен быть не один: IP — это минимум, для авторизованных API работает
лучше привязка к identity + поведенческие сигналы; нужен и «взрывной» лимит на
короткий всплеск, и «длинный» на суммарное использование ([Stytch: API rate limiting](https://stytch.com/blog/api-rate-limiting/), [Zuplo: protect APIs from bots](https://zuplo.com/learning-center/how-to-protect-your-apis-from-automated-bots-and-attacks)).
**У нас**: `check_rate_limit`/`MIN_SUBMIT_INTERVAL_MS`/`DAILY_SUBMIT_LIMIT`
есть для публикации трасс — но у `vote`/`played` в Мастерской лимита нет вообще
(частично компенсируется тем, что vote — уникальный ключ игрок+код, а played
до сегодняшней проверки был вообще без всякой защиты — см. дыру выше).

### 5. Рост таблиц без архивации
Стандартная рекомендация — не хранить бесконечно, архивировать историю отдельно
от рабочих данных заранее, не когда база уже разрослась ([OneNine: database growth issues](https://onenine.com/common-database-growth-issues-and-fixes/), [AppSignal: table bloat](https://blog.appsignal.com/2022/02/03/how-to-keep-database-table-sizes-down-and-prevent-data-bloat.html)).
**У нас**: `forge_workshop`, `track_votes`, diag-скриншоты — уже отмечено в
памяти как «пересмотреть при росте в 10 раз» ([[project_diag_shot_cost_cleanup]]) —
осознанное решение, не забытое, менять сейчас не нужно.

### 6. Резервное копирование / восстановление после сбоя
PITR (point-in-time recovery) называется «самой важной» настройкой на случай
сбоя — без неё теряются все записи между последним бэкапом и инцидентом
([TigerData: PostgreSQL backups](https://www.tigerdata.com/blog/database-backups-and-disaster-recovery-in-postgresql-your-questions-answered)).
**Не проверено мной** — это настройка тарифного плана Supabase-проекта, не
видна через доступные мне инструменты (SQL/advisors её не показывают). Честно:
не знаю, включён ли PITR на `cwpijvgdrrvnvldhnmbj» — это смотрится в Supabase
Dashboard → Database → Backups владельцем напрямую, я туда доступа не имею.

### 7. Service Worker — что если новая версия зависает у части игроков
Частая ловушка — HTML закэширован Cache First, из-за чего update невидим
пользователю сколько угодно долго; лечится версионированием кэша по билду и
явной очисткой старых кэшей на `activate` ([Hasura: SW caching strategies](https://hasura.io/blog/strategies-for-service-worker-caching-d66f3c828433), [Infinity Interactive: taming PWA cache](https://iinteractive.com/resources/blog/taming-pwa-cache-behavior)).
**Проверено, у нас уже правильно**: `sw.js` делает `skipWaiting()` на install
и чистит все чужие ключи кэша на `activate` — ровно рекомендуемый паттерн,
чинить нечего.

### 8. GDPR-K / COPPA (дети 3+)
Апрель 2026 — обновлённые правила COPPA вступают в силу, требования к
родительскому согласию и сбору данных ужесточаются ([gamesbeat: updated COPPA rules](https://gamesbeat.com/understanding-the-updated-coppa-rules-and-their-impact-on-child-safety/), [SuperAwesome: COPPA/GDPR-K for game devs](https://www.superawesome.com/blog/5-things-game-developers-need-to-know-about-coppa-and-gdpr-k/)).
**У нас**: контентная политика 3+ уже есть ([[feedback_content_policy_kids]]),
но это про КОНТЕНТ, не про СБОР ДАННЫХ — а телеметрия (`beacons`) собирается
по умолчанию всем. Это ровно тот пункт, что уже стоит открытым в реестре решений
как S12 «нужен юрист» ([[project_telemetriya_opt_in_status]]) — не новая
находка, но эта самая юридическая тема прямо перекликается с COPPA-апрелем.
Не додумываю юридический вывод сам — это открытый вопрос реестра, не мой звонок.

### 9. Соло/маленькая команда — типичные организационные мины
Почти каждый разбор провала инди-команды начинается с масштаба фичи, а не
с бага: команда без роадмапа реагирует на срочность вместо приоритета
([itch.io post-mortems index](https://danbruno.net/notes/games/failure-postmortems/), [GameDeveloper: 9 common indie mistakes](https://www.gamedeveloper.com/design/the-9-common-mistakes-every-indie-game-studio-should-avoid)).
Это не техническая мина, это процессная — не моя зона (я не решаю приоритеты),
просто фиксирую саму категорию как честно найденную по просьбе.
