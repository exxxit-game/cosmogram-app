## 2. Фаза 1 — инженерный фундамент (Неделя 1)

1. **AI Profiler** — 4 ч, $200. Файл `js/vendor/ai-profiler.js`. Метрики после каждого коммита (frameTime, drawCalls, objectCount, gcPauses); ИИ находит регрессии («коммит X добавил 2 мс из-за лишних save/restore»), сравнение «до/после» автоматически.
2. **Utility AI для бонусов** — 3 ч, $150. Файл `js/game/bonus-utility.js`. Оценка 0–100: дистанция до самолёта, редкость, синергия (щит при щите — минус), опасность соседних астероидов.
3. **Few-shot контекст** — 1 ч, $50. 2–3 канонических примера кода Cosmogram (zero-allocation пулы, детерминированный withTrack) в системных инструкциях.

## 3. Фаза 2 — режимы и социальный слой (Неделя 2)

4. **Комментатор «Театра призраков»** — 5 ч, $250. Детекция near-miss и красивых уклонений; LLM-реплики с фолбэком на заготовленные фразы.
5. **Семантический сейв «Кузницы»** — 3 ч, $150. Сжатые base64-коды `CG1.*` с текстовым паспортом сложности.
6. **Топ-режимы из 6 слоёв:** Штурман, Загадка неба (Wordle-отрезок 200 м), Перемотка (3 отката по 3 с), Фонарь, Полярность (Ikaruga-стиль).

## 4. Фаза 3 — доступность и автобаланс (Неделя 3)

## 5. Техники работы с ИИ

**До генерации:** Few-shot (2–3 примера хорошего кода); Chain-of-Thought (объяснение шаг за шагом); Self-Consistency (2–3 варианта, выбор лучшего).
**После генерации:** Reflexion (анализ ошибок коммита); валидация (JSON Schema/zod, линтер); тесты красный → зелёный ×3.
**В контекст всегда:** текущие метрики кадра, последние 3 ошибки из логов, структура файлов.

### К п.1 «AI Profiler»
- **GC-паузы через `PerformanceObserver({entryTypes:['gc']})` — недоступно в браузере.** Это
  API Node.js (`perf_hooks`), не веба — план придётся строить без него.
- **Long Animation Frames API** — только Chrome/Edge 123+, ни Firefox, ни Safari/WKWebView —
  на iOS-стороне Telegram не сработает вообще.
- **Реалистичная замена GC-сигналу — эвристика по остатку кадра**: `frameDt − сумма 6 уже
  измеренных секций frameProfile` = «неучтённое». Пока физика не выделена отдельной секцией
  (собственный комментарий в `render.js:102`: «физика ни разу не измерялась») — сигнал будет
  смешивать физику и GC, подписывать его «GC» нельзя, только «неучтённое».
- **`drawCalls`/`objectCount` — не трогая ядро.** Обёртка методов
  `CanvasRenderingContext2D.prototype` (`fill`/`stroke`/`drawImage`) счётчиком — устоявшийся
  приём (Impact.js `drawCount`), делается целиком в новом `js/vendor/ai-profiler.js`, не в
  `render.js`. `objectCount` — просто `.length` уже существующих массивов пулов.
- **Найдено попутно, не по заданию:** `frameProfileSnapshot()` сейчас отдаёт только средние
  значения (`.../n`), хотя `PERFORMANCE.md §2.17` сам требует мерить хвост распределения
  (p95/worst), не среднее — собственное противоречие документа с кодом.
- **Хранение истории/автоматизация**: локальный JSONL-файл (одна строка на прогон) +
  маленький Node-скрипт сравнения последних двух записей, по образцу `tests/guard.mjs` — не
  полноценный CI. Отдельный вопрос владельцу: хранить файл истории в git или локально
  (несколько несвязанных копий папки на машине — уже известная проблема окружения).

### К п.2 «Utility AI для бонусов»
- **Правильная формула — не сумма и не чистое произведение, а произведение с
  компенсирующим фактором** (Infinite Axis Utility System, Dave Mark) — чистая сумма
  маскирует плохой фактор хорошими (не даёт эффекта «вето» для «щит при щите»), чистое
  произведение чрезмерно давит итог с ростом числа факторов.
- **Сохранить взвешенно-случайный розыгрыш, не переходить на строгий максимум** — The Sims
  намеренно берёт случайный вариант из топа, не argmax, чтобы не выглядеть роботом. Нынешняя
  лотерея Cosmogram (веса 3/3/2/1/1/1) уже структурно ближе к этому, чем к строгому выбору —
  эволюция: вычислять веса по контексту, оставить сам розыгрыш случайным.
- ⚠️ **Подтверждено 27.08.2026 (было гипотезой, теперь факт по коду и истории проекта) —
  реальный конфликт с «Трассой дня», не мнимый.** `withTrack(kind,fn)` (`core.js:125-129`)
  на каждый вызов пересеивает `mapRNG` заново по `mapSeedKey·kind·mapSeq[kind]++` — то есть
  сам факт лишних вызовов `mapRNG()` внутри `fn` не рушит детерминизм МЕХАНИЧЕСКИ. Настоящий
  риск другой: **страж 51** (`guardTrackIsSameForEveryone`, `guard.mjs:1872-1878`) существует
  именно как защита от «поле зависит от того, как играл конкретный игрок» — его собственное
  описание бага, который он ловит: «волну поднимали очки... разные виды преград тратят разное
  число обращений к кубику. Одно расхождение — и поля двух игроков расходятся навсегда».
  Комментарий на `weights=[3,3,2,1,1,1]` в `spawnPowerup()` (`game.js:300`, «фиксированный
  диапазон: состояние игрока не сдвигает весь seed-поток») — уже намеренная защита ровно от
  этого для бонусов, просто страж 51 её пока не проверяет (покрывает только `spawnObstacle`).
  Факторы Utility AI из роадмапа — «дистанция до самолёта», «опасность соседних астероидов» —
  оба зависят от того, как именно летит КОНКРЕТНЫЙ игрок. Применённые к «Трассе дня» (общий
  сид), они дадут двум игрокам РАЗНЫЕ виды бонусов в одной и той же точке трассы — то же самое
  расхождение, которое страж 51 уже один раз ловил и чинил, просто для другого кода.
  **Вывод, не додумываю решение:** либо Utility AI ограничен режимами без общего сида (Классика
  вне Трассы дня/Дуэлей), либо факторы считаются только из общей для всех части состояния (не
  из позиции конкретного самолётика) — какой вариант выбрать, отдельный вопрос владельцу.
  **Готовый прецедент того же решения уже есть в коде** (найдено 27.08.2026): `Adaptive`
  («Мозг неба», `js/adaptive.js`) — уже существующая система, подстраивающая плотность/скорость
  под конкретного игрока (по среднему времени жизни и причинам смерти) — намеренно ограничена
  ТОЛЬКО режимом «Своя трасса» (`S.mode==='custom'`), с явным комментарием в файле: «В Классике/
  Bullet/Трассе дня/Дуэлях это сломало бы честность сравнения между игроками — тут ломать
  нечего, зачёта и так нет». Ровно та же формула scoping, что нужна Utility AI — не изобретать
  заново, а последовать уже принятому в проекте правилу.
- Конкретные веса/степени/пороги — отдельный вопрос владельцу.

### К п.4 «Комментатор Театра призраков»
- **Детекция «красивого» момента уже реализована и работает** — `o.nm`/`isReceding`/`S.combo`
  (`game.js:764-813`). Ничего нового изобретать не нужно, вопрос только в том, чтобы прогнать
  ту же проверку при воспроизведении теневой ленты.
- **Живой LLM-вызов во время геймплея — нереалистичен**: ключ нельзя класть в клиент (нужен
  прокси через Supabase Edge Function — новый эндпоинт и новый живой биллинг, не бесплатное
  переиспользование); задержка (даже у самых быстрых провайдеров — сотни мс до 1-2с) не
  укладывается в момент, который на 60fps проходит меньше секунды; реальные примеры
  спортивных комментаторов (NBA2K/FIFA-класс) — банки заготовленных фраз с условной логикой,
  не живой ИИ-вызов, даже у студий с несравнимо большим бюджетом.
- **Рекомендация — начать с чисто процедурной системы**: банк вариантов фраз, ключуемый по
  типу события и величине `S.combo` (грамматика в духе Tracery, или проще — массив вариантов),
  переиспользуя уже существующий паттерн `L`-объекта локализованных строк из `i18n.js`. Нулевая
  новая инфраструктура, нулевой риск задержки.
- Если LLM всё же понадобится — реалистично только как предгенерация на паузе/экране итогов
  (не в момент события), например через уже используемый в проекте Supabase Edge Function как
  прокси к Claude Haiku 4.5 (дешёвая, но интегрированный путь) — конкретный выбор провайдера и
  момента вызова — отдельный вопрос владельцу.

### К п.5 «Семантический сейв Кузницы»
- **Техника — бакетизация уже существующих числовых полей конфига** в 1-2 словесных слота
  (`d`→«Разрежённая/Плотная/…», `e`→«Однообразная/Пёстрая/…» и т.п.), детерминированно и БЕЗ
  сохранения отдельно — прецедент: тот же принцип, что у мнемонических фраз BIP39 и генераторов
  читаемых имён (Docker container names) — «слово выводится из данных, не хранится отдельно».
- **Компромисс A vs B, не додумываю решение:** (A) чистая функция от расшифрованного конфига —
  ноль новых байт в коде, работает даже для уже разошедшихся старых кодов задним числом; (B)
  отдельное поле в массиве с вручную подобранной формулировкой — богаче текстом, но раздувает
  код и требует bump версии схемы при правке словаря.
- **Прецедент того же паттерна бакетизации уже в бою** (найдено 27.08.2026): `achTier(a)`
  (`ach.js:91`) — `a.rw>=400?'mGold':(a.rw>=100?'mSilver':'mBronze')`, ровно схема «число →
  словесный тир» одной строкой, уже проверена для наград достижений. Тот же приём (`gfxTier()`/
  `tgPerfClass()` в `core.js` — LOW/AVERAGE/HIGH из числа) применяется и для тира графики. Не
  изобретать паттерн бакетизации заново — применить уже отточенный к полям Кузницы.
- Число слотов, конкретные словари, пороги бакетизации, выбор A/B — отдельный вопрос владельцу.
- Побочная находка, не по заданию: код `CG1.*` сейчас без контрольной суммы — повреждённый код
  тихо становится `null` (`forge.js:92`). Не рекомендация действовать, просто наблюдение.

### К п.6 «Топ-режимы» (Штурман / Загадка неба / Перемотка / Фонарь / Полярность)
Оценка сложности реализации, от простого к сложному (по совокупности находок, не решение за
владельца):
1. **Фонарь** — почти бесплатно: тот же паттерн, что уже работает в `vignetteSprite()`
   (`render.js`) — офскрин-канвас с радиальным градиентом, кэшируется один раз, на кадре только
   позиционируется через `drawImage`, не пересоздаётся. Уже проверен на памяти WKWebView.
2. **Полярность** — один булев гейт в уже существующей ветке столкновений по `kind`
   (`game.js:738-800`). Прецедент переноса Ikaruga-механики именно на препятствия/платформы
   (не только на снаряды шутера) — Housemarque, «Outland».
3. **Загадка неба** — вся сидовая инфраструктура (`mapSeedKey`, `trackDayKey`, `withTrack`,
   изолированные потоки по категориям) уже спроектирована ровно под это. Нужна одна новая
   чистая функция-валидатор достижимости (generate-and-validate, как в процедурной генерации),
   через целочисленный LUT, не тригонометрию (запрет `Math.sin/cos` в спавне уже в силе).
4. **Штурман** — кодек морзянки и тактильный мост уже в бою (`core.js`), но как разовое
   уведомление по `setTimeout`, не непрерывный игровой канал. Нужен новый паттерн — очередь
   команд, синхронизированная через `withTrack` для одинакового расписания у обоих экранов.
5. **Перемотка** — самая неопределённая, НО найден реальный путь в обход проблемы (27.08.2026,
   найдено в диалоге с владельцем, проверено по коду). Идея наивного кольцевого буфера снэпшотов
   объектов (техника отката в Braid, Jonathan Blow GDC 2010) разбивается о то, что препятствия/
   звёзды возвращаются в пул и переиспользуются прямо во время полёта (`killIdx()`/
   `poolOb.take()`, `game.js:738-800`) — откат рискует «воскресить» чужой объект с чужими полями.
   Ни один найденный источник по rewind-механикам эту проблему не решает — специфика архитектуры
   Cosmogram, не общее место.

   **Обходной путь, а не решение в лоб: не хранить снэпшоты объектов вообще.** Проверено по
   коду (`game.js:568-596`): спавн препятствий уже устроен как детерминированный таймер
   `spawnT`, тянущий из изолированного потока `withTrack('ob', ...)` — вид и параметры каждого
   препятствия целиком выводятся из состояния потока, не хранятся отдельно. Это ровно тот же
   принцип, на котором уже держится Театр призраков (лента хранит только позицию самолётика,
   препятствия для повтора не сохраняются — рождаются заново из того же сида, `ARCHITECTURE.md`
   §8). Значит для отката не нужно откатывать объекты пула — нужно откатить только горстку
   чисел: состояние самолётика (x,y,vx,vy,combo,score), внутреннее состояние потоков
   `ob`/`st`/`pw` и таймеров `spawnT`/`starT`/`powT`, в кольцевом буфере без аллокаций. Текущие
   препятствия/звёзды при откате чисто возвращаются в пул (страж 109 уже держит контракт «из
   пула — только чистым»), а дальше игра сама заново спавнит те же объекты в тех же местах по
   тому же детерминированному потоку — идентичность объекта не нужно сохранять, потому что он
   рождается заново тем же способом, что и в первый раз.

   **⚠️ Владелец прямо не согласен считать это готовым решением — записаны оба варианта
   продолжения, ни один не выбран:**
   - **Вариант А, «естественное дозаполнение».** Просто восстановить числа и таймеры, очистить
     текущие объекты — дальше игра доспавнит поле сама по расписанию. Дёшево технически, но
     сразу после отката экран на долю секунды может быть частично пустым (пока таймер спавна не
     досчитает до нуля) — то есть мир не мгновенно выглядит «как было», а сначала обеднён,
     затем дозаполняется. Владелец отметил это как нежелательный нюанс — вариант зафиксирован
     как **ненадёжный, требует более внимательной проработки**, не как принятое решение.
   - **Вариант Б, «тихая прокрутка вперёд».** От восстановленной точки молча (без рендера)
     проиграть симуляцию заново вперёд, до текущего момента, чтобы объекты оказались на местах
     сразу, без видимой пустоты. Убирает нюанс варианта А, но добавляет свою сложность: нужно
     решить, как именно «быстро прокрутить» игровой цикл без рендера и без побочных эффектов
     (столкновения/очки в эти призрачные кадры не должны засчитываться), и какова стоимость
     такой прокрутки на слабом устройстве при частом использовании отката.
   - Ни один из двух вариантов не выбран владельцем — оба записаны для дальнейшего обсуждения,
     это архитектурное решение с реальными компромиссами, не техническая деталь для додумывания.
- Тайминги морзянки под игровую задержку, кривая радиуса фонаря, частота переключения
  полярности — везде отдельные вопросы владельцу, ни один источник конкретных чисел не даёт
  (даже у самого osu! кривая Flashlight нигде не документирована официально).

### К п.8 «Генетическая автобалансировка»
- **Реальные техники для непрерывных параметров**: генотип — плоский массив чисел (не битовая
  строка), кроссовер BLX-α (родительский диапазон ± коэффициент), мутация — случайный сдвиг
  одного гена. Реализуемо на чистом JS без библиотек (соответствует запрету на npm-зависимости).
- **Метрика — Statistical Parity, [0,1], где 0.5 = сбалансировано** — та же шкала, что и
  «проходимость 50/50» из формулировки этого пункта.
- ⚠️ **Предостережение, найденное в источниках напрямую (Rupp, AIIDE 2025):** «randomness is
  optimized out» — чистая оптимизация под ровно целевой процент имеет тенденцию вымывать
  вариативность/остроту, потому что ровный монотонный паттерн проще стабильно держать у
  целевого числа, чем «пилообразный» с пиками и разрядкой. **Это тот же класс проблемы, что уже
  была пройдена и решена руками владельца** — удаление «Дыхания неба» (v1.284.17, «скучно»,
  подтверждено `ochnaya-stavka.mjs`). Настраивать балансировщик нужно на допустимый диапазон
  вокруг цели, а не на «идеальные» 50.000% — конкретный допуск не додумываю, отдельный вопрос.
- **Только офлайн-батч встретился во всех найденных источниках** (Hom & Marks 2007, GEEvo 2024,
  Square Enix Grimm Notes CEDEC 2017) — ни одного примера продолжающейся эволюции на статистике
  живых игроков после релиза для команд такого масштаба. Это не конфликтует с уже принятым
  решением «детерминированный ритм, общий для всех» (`ARCHITECTURE.md §12`) — один фиксированный
  результат для всех, не персонализация.
- **План поверх уже существующей инфраструктуры**: `tests/ochnaya-stavka.mjs` уже гоняет
  headless Playwright с ручными тиками `update(1/60)` без rAF — детерминированный батч-прогон
  тысяч секунд игры за секунды реального времени уже работает. Нужен третий тип бота (рядом с
  «пилот-столб» и синусоидой) — простое эвристическое правило уклонения без ML/pathfinding
  (прецедент устройства такого агента — arXiv 2605.01783, два простых геометрических агента
  без обучения).
  **Формулу не нужно искать снаружи — она уже в бою** (найдено 27.08.2026): преследование мины/
  ловца (`game.js:700-711`) — `o.vx = lerp(o.vx, clamp((plane.x-o.x)*k, -1,1), rate)`,
  пропорциональное наведение на цель, уже отлажено и проверено в реальной физике игры.
  Бот-уклоняльщик — та же формула с обратным знаком (отталкивание от ближайшей преграды вместо
  притяжения к самолётику), не новый алгоритм с нуля.
- Границы генотипа (какие именно константы в `difficulty()`/`spawnObstacle()`), метрика успеха,
  допуск вокруг 50% — отдельные вопросы владельцу, явно НЕ трогать веса видов препятствий
  (`waveDistTarget` и подобное уже защищены отдельными решениями в `AI-DECISION-REGISTRY.md`).
- Обязателен финальный человеческий плейтест перед принятием результата — ни один источник не
  считает автоматическую метрику достаточной саму по себе.
