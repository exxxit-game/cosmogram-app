# 🌐 Защита честности счёта/лидерборда: многоязычное исследование (13.09.2026)

> Задача: реальный опыт малых/соло-команд по защите счёта в играх с клиентской физикой
> и лёгкой серверной проверкой (наш случай: Cosmogram — клиент считает полёт, сервер
> получает финальный счёт + range-check, полной server-side симуляции не тянем).
> Искали на японском, корейском, немецком, французском, испанском/португальском —
> именно в этих языках, не переводы английских статей. Метод: WebSearch на каждом
> языке отдельными запросами (не «перевод одного запроса»), затем WebFetch самых
> предметных находок для деталей и цитат.

## Итог одной строкой

**Япония и Корея дали реальные, предметные, применимые к маленькой команде находки**

(проверено 3+ отдельными заходами на разные формулировки на каждом из этих языков).

## 🇯🇵 Япония — лучший улов, применимо напрямую

### 1. Spicy Soft Co. — защита HTML5-рейтинга без регистрации пользователей (Qiita)
Источник: 山田元康 (Motoyasu Yamada), **スパイシーソフト株式会社** —
qiita.com/motoyasu-yamada/items/9b91008e579282d3c016
(статья помечена автором как «в процессе написания», но конкретика уже есть)

Контекст ровно как у Cosmogram: **без регистрации пользователей, HTML5, минимальный
серверный бюджет** — то есть это не теоретический AAA-пример, а разбор именно
маленького-проекта случая.

Конкретные техники:
- **Многоуровневая блокировка по IP**: приватные адреса → адреса дата-центров
  (по открытым спискам, например с GitHub) → сеть Tor → чёрные списки прокси.
- **Server-side генерация userID при старте** с ограничением на массовую генерацию
  с одного IP (защита от скриптовой накрутки «100500 фейковых игроков»).
- Разделение реакции на подозрительный трафик: **автоматические временные баны**
  vs **ручные постоянные баны** после разбора вручную.

Применимо к Cosmogram: прямо применимо — у нас тоже нет полноценной регистрации
(Telegram id + опционально OAuth), и лёгкий rate-limit/IP-эвристика на Edge Function
дешевле, чем кажется.

### 2. note.com — «Оживи игру рейтингом»: гайд соло-разработчика для новичков
Источник: zero, **個人ゲームクリエイター** (соло-геймдев-крейтор) —
note.com/plus00/n/nefbc5297cf2c

Это именно позиция «я один», не студия. Три уровня защиты, которые автор считает
реалистичными для соло-разработчика:
1. **Детекция аномалий** — «スコアや順位が不自然に高い場合» (когда счёт/место
   неестественно высоки — вручную или простым порогом).
2. **Репорт от игроков** — кнопка «пожаловаться» на подозрительный результат
   (краудсорсинг модерации, ноль инфраструктуры).
3. **Санкция** — удаление результата или бан аккаунта, применяется постфактум,
   не как gate до публикации.

Автор прямо признаёт: «полная профилактика невозможна» — интересно, что это
признание идёт от практикующего соло-разработчика, а не абстрактный тезис.
(Инфраструктурная деталь статьи — сервис NCMB — устарела, закрылся 31.03.2024,
не переносить.)

### 3. Qiita — parameter tampering счёта через URL query (общая веб-безопасность)
qiita.com/shimada_slj/items/a8ebc171154568f49586

Прямой пример: «攻撃者はスコアのパラメータを改ざんして高得点を送信し、ランキング
に影響を与えることを試みます» (атакующий подделывает параметр счёта в URL-запросе,
чтобы отправить завышенный результат). Решение: критические данные — только через
тело POST-запроса, не GET/query string; **CSRF-токен**. Автор честно уточняет:
«GET/POSTでは根本的な解決にはなりません» — сам по себе выбор метода не даёт полной
защиты, это лишь убирает самый тривиальный вектор (руками подставить URL в адресной
строке).

Применимо: у Cosmogram счёт уже уходит через Edge Function (не query string),
это на практике уже закрыто — но стоит явно сверить, что нигде в отладочном/legacy
коде счёт не мог случайно пойти через GET.

### 4. note.com — гайд по серверному дизайну для «нечестных» RESTful-игр
Ogawa — note.com/ogawa_ramo/n/n1180b5aaa852

Самая техническая из японских находок, набор конкретных приёмов:
- **Не доверяй клиенту**: все значимые вычисления (лут, начисление очков, списание
  валюты) — только на сервере; клиенту — только результат.
- **Валидация каждого параметра запроса** на сервере, включая проверку несуществующих
  ID и запрещённых комбинаций (пример: нельзя купить лимитированный предмет за
  «неправильную» валюту).
- **Одноразовый токен вместо прямой передачи цены/ID валюты от клиента** — «ユーザー
  がトークンを盗み見ても、内容を勝手に変えることはできません» (даже если пользователь
  подсмотрит токен, содержимое подделать не может).
- **Двойная проверка баланса перед списанием**: читать текущий баланс из БД с
  блокировкой строки (FOR UPDATE), проверить достаточность, только тогда — транзакция.
- **HMAC-подпись запроса**: `подпись = HMAC(secret, тело_запроса + timestamp)`,
  сервер проверяет целостность.
- **Nonce против replay-атак**: сервер хранит использованные nonce, повтор — отказ.
- Логирование подозрительных запросов и ошибок для последующего разбора (сам автор
  признаёт, что не раскрывает деталей — «важность» указана, метод — нет).

Применимо: HMAC+timestamp+nonce — это ровно тот уровень, который малая команда
может себе позволить без полной server-side симуляции; идейно близко к тому, что
уже есть в `cosmogram-sync` (AUTH_MAX_AGE_SEC — но это про подпись Telegram initData,
не про сам счёт; вопрос, защищён ли сам submit счёта аналогичной схемой — отдельная
техническая проверка, не в рамках этого исследования).

## 🇰🇷 Корея — сильная практическая находка + типичный локальный контекст

### 5. GitHub issue — реальный соло-разработчик, конкретные границы валидации счёта
rohdaeyoung/stroop-game, issue #35 — «백엔드 변경사항 반영 — 에러 코드 추가 +
점수 제출 검증» (bilingual issue tracker корейского разработчика, публичный репозиторий)

Это ровно наш масштаб: простая браузерная игра (Stroop-эффект), соло/малый разработчик,
лёгкая серверная проверка диапазона — **живой пример того же паттерна, что уже
использует Cosmogram**, с конкретными числами:

| Поле | Допустимый диапазон | Смысл |
|---|---|---|
| `score` | 0–300 000 | отсечь нереальные значения |
| `wrongCount` | 0–3 | игра завершается после 3 ошибок |
| `playTimeMs` | 0–70 000 мс | 60 сек игры + 10 сек запаса |
| `nickname` | 1–10 символов, не только пробелы | базовая гигиена |

Ключевая цитата, которая прямо совпадает с духом задачи: разработчик пишет, что это
**«조작 방지가 아니라 앱 버그로 인한 이상한 값 저장을 막는 안전망»** — «это не защита
от накрутки, а страховка от того, что баг в приложении запишет мусорное значение».
Честное признание границ лёгкой валидации диапазона — она ловит баги и совсем грубую
подделку, не ловит правдоподобный чит. `playTimeMs` намеренно с запасом (+10 сек),
потому что сворачивание приложения в фон и подобные легитимные паузы могут раздуть
время — если делать диапазон слишком жёстким, банишь честных игроков, не читеров.

### 6. DCInside, галерея 인디 게임 개발 (индstruct-геймдев) — сообщество малых разработчиков
- **«치트엔진 방지하는법 간단히»** (gall.dcinside.com/mgallery/board/view/?id=game_dev&no=14597):
  главная техника на форуме — **XOR-шифрование переменных в памяти клиента** (счёт,
  здоровье): `hp = 100 ^ global.key`, ключ — рандомный при старте, **паттерн меняется
  каждый кадр**, чтобы Cheat Engine (сканер памяти) не мог отследить один и тот же адрес.
  Форум сам предупреждает: применять не ко всем переменным — просадка производительности,
  и метод работает **только для локальных игр без сервера** (для клиент-серверной защиты
  бесполезен сам по себе, это защита от «читерства в моменте», не от подделки итогового
  результата).
- **Общий тон корейской инди-тусовки** (DCInside game_dev, множество тредов): рекомендация
  для соло/малых команд — не городить свою серверную инфраструктуру с нуля, а брать
  готовый BaaS. Чаще всего называют **뒤끝 (Backnd)** — бесплатен примерно до ₩100 000/мес
  трафика, чего с запасом хватает на лидерборд масштаба «несколько сотен игроков».
- Общий принцип, повторяющийся в нескольких корейских источниках (включая MapleStory
  Worlds Creator Center для крейторов и AppSealing case-study по инди-играм): **даже если
  клиент уже проверил условие, сервер обязан перепроверить его ещё раз** для любых
  значимых данных — не полагаться на «клиент уже посчитал правильно».

Оценка применимости: XOR-трюк из корейской инди-тусовки — это защита клиентской памяти
от Cheat Engine во время игры (актуально не для Cosmogram напрямую, у нас нет угрозы
«читер редактирует память во время полёта ради визуального читерства» — угроза именно
в подделке итогового submit), но сам паттерн «двойная проверка на сервере» и практика
«не изобретай сервер сам, возьми готовый BaaS» — подтверждают уже принятое в проекте
решение (Supabase Edge Function + range-check).

## 🇩🇪 Германия — одна предметная находка, дальше общие принципы

### 7. Game Maker Domäne — форум GameMaker-разработчиков, «Cheatsicherheit» для онлайн-хайскора
gm-d.de/wbb/index.php/Thread/18770 — именно хобби/соло-масштаб (GameMaker — типичный
движок для маленьких проектов, аудитория форума — любители и малые команды)

Конкретные приёмы из обсуждения:
- **Двойная переменная**: реальный счёт (`real_score`) хранится отдельно от отображаемого
  (`displayed_score`), связь — через математическое преобразование (например,
  displayed = real × 3, реальный вычисляется обратно). Смысл: если читер найдёт в памяти
  переменную «очевидного» вида, она не совпадёт напрямую с тем, что видно на экране.
- **Пароль/секрет при отправке на PHP-сервер**: без него — заголовок «любой, кто узнает
  URL скрипта хайскора, может слать поддельные значения» — то есть буквально то, с чего
  начинается любая защита: не полагаться на «security through obscurity» одного лишь URL.
- **Проверка диапазона по разрядам**: пример из треда — заведомо узкий диапазон значений
  (123 400 000–123 499 999) как приём затруднить подбор «правдоподобного» значения без
  анализа исходного кода — по сути тот же принцип, что и корейский range-check, но поданный
  как «security by obscurity узкого диапазона», а не «честная игровая граница».
- Форумчане прямо указывают на слабое место двойной переменной — если оба значения
  совпадают/линейно связаны, memory-scan всё равно раскрывает связь: нужна именно
  нетривиальная трансформация, не просто вторая копия.

### Общие принципы (не специфика, но с немецкого форума получены явно, не переводом)
- itsicherheit-online.com — деление на **клиентский user-mode анти-чит** (дёшево
  реализовать, сравнение с базой сигнатур), **обфускацию кода**, **hash-проверку файлов
  игры** (для чистого клиента без сервера) — и отдельно **community-модель**: сохранять
  записи подозрительных партий и давать честным игрокам оценивать их «как жюри присяжных»
  — редкий пример почти нулевого по стоимости подхода, доступного маленькой команде без
  бюджета на анализ.
- spieleprogrammierer.de (общий тред про cheat-protection в браузерных играх):
  «самый надёжный метод — записывать все инпуты игрока вместе с заявленным
  счётом/временем и передавать на сервер» (по сути replay-верификация) — концептуально
  совпадает с французской находкой ниже, но без технических деталей реализации.

Оценка: XOR/двойная-переменная — не то, что нужно Cosmogram (опять же — угроза не
«читер живьём модифицирует память во время полёта», а «подделанный итоговый submit»),
но сам факт, что немецкая хобби-сцена по умолчанию отвергает «просто доверять URL» и
явно проговаривает необходимость хоть какого-то секрета/подписи при отправке — полезное
подтверждение базовой гигиены.

## 🇫🇷 Франция — мало технической глубины, но одна ценная цитата из практики

Поиск (5+ отдельных формулировок: geimdev-форумы, itch.io на французском, AFJV,
jeuxvideo.com, Zeste de Savoir) **не дал ни одной статьи с реальным кодом или конкретной
архитектурой** от французского инди-разработчика. Основной массив результатов —
AAA-новости (EA Javelin/Vanguard/VAC), которые не относятся к малым командам.

### 8. Zeste de Savoir — форумная дискуссия «La triche dans les jeux solo»
zestedesavoir.com/forums/sujet/6362 (Zeste de Savoir — известное французское
сообщество программистов/энтузиастов, обсуждение не рекламное, живое)

Единственная содержательная находка на французском — реальный, названный по имени
пример провала антифрода даже в известных играх с лидербордом:

> «il y a bien des gens qui ont des temps de 0.01s, ce qui est bien entendu impossible»
> (в TrackMania и TrialFusion встречаются времена 0.01 сек — очевидно невозможные)

Это прямое подтверждение того, что даже широко известные игры с онлайн-рекордами
допускают явно абсурдные значения в лидерборде — то есть простая **проверка на
правдоподобность (sanity check по физическим границам)** — то, что уже частично
делает Cosmogram — это не «слабая» защита, а именно тот минимум, которого не хватает
даже некоторым коммерческим играм; отсутствие даже такой базовой проверки — заметный
провал, а не мелочь.

Второй тезис из того же треда, ближе к предложению, чем к готовой технике:
«игра в одиночку с лидербордом — плохая идея, если только партия не переигрывается
на сервере для проверки, было ли читерство» — то есть **replay-верификация** снова
всплывает как «идеальный, но дорогой» ответ — то же самое, от чего Cosmogram
сознательно отказывается по бюджету, что и обозначено в задаче.

испанских/португальских находок от малых команд нет**, только общие принципы,
уже известные из английских/японских/корейских источников выше.

## Синтез: что реально применимо к Cosmogram без бюджета на анти-чит

Все найденные подтверждённые техники сходятся к одному и тому же узкому набору,
доступному маленькой команде — независимо от языка источника:

1. **Server-side range/sanity-check** (уже есть у Cosmogram) — корейский пример
   (stroop-game) и французская цитата (TrackMania 0.01s) подтверждают: это не
   «слабая» защита, а минимум, отсутствие которого заметно даже в популярных играх.
2. **Не через GET/query string, подпись+timestamp+nonce для submit** (японский
   RESTful-гайд) — если Cosmogram ещё не подписывает сам запрос отправки счёта
   отдельно от initData-подписи входа, это дешёвый апгрейд.
3. **IP/паттерн-эвристика вместо полной server-side симуляции** (японский Spicy Soft
   пример: дата-центры/Tor/прокси-листы + троттлинг генерации ID) — реалистично на
   уровне Edge Function.
4. **Ручной репорт + постфактум-модерация вместо предотвращения** (японский
   соло-крейтор) — самый дешёвый по инфраструктуре слой, уже частично в духе
   существующих в проекте механик жалоб.
5. **Честно признать потолок** — сразу три независимых источника (японский, корейский,
   немецкий) прямым текстом говорят: полная защита невозможна на этом бюджете, и это
   нормально — важно не бороться за «неприступность», а не давать читерству разрушать
   ощущение честности у обычных игроков.

Что НЕ применимо напрямую (специфично для угрозы «модификация памяти во время игры»,
не «подделка итогового submit»): XOR-шифрование переменных в реальном времени
(корейский DCInside-приём), двойная-переменная-обфускация (немецкий GameMaker-форум) —
это защита от Cheat Engine в live-игре без сервера, а не от подделки итогового счёта,
который Cosmogram и так не строит full-trust на клиенте.
