## 0. Живые данные зонда (сверка 26.08.2026)

> **Поправка того же дня:** первая версия этого раздела ошибочно обобщила результат на
> «клиент» целиком. Разобрал `ua` у каждой строки в базе — **ни одной iOS/Safari пробы в
> данных нет вообще**, только Android. Ниже — исправленная версия с разбивкой по платформе,
> не по всему клиенту сразу.

Зонд `webcodecsProbe()` проверял только H.264 с 24.08.2026. 26.08.2026 расширен на
VP8/VP9/AV1 (`js/skymail.js`, коммент «v1.473.0 + правка 26.08.2026»). Все пробы в базе,
сколько их есть, дают такую картину:

| Кодек | Аппаратно | Программно | Платформа во всех пробах |
| :--- | :---: | :---: | :--- |
| **H.264** (`avc1.42001E`) | 0% (0/40+) | 0% (0/40+) | **только Android** — 40+ проб за три дня |
| **VP8** (`vp8`) | 0% (0/25) | **100%** (25/25) | только Android |
| **VP9** (`vp09.00.10.08`) | 0% (0/25) | **100%** (25/25) | только Android |
| **AV1** (`av01.0.04M.08`) | 0% (0/25) | 84% (21/25) | только Android |
| **Любой кодек, iOS/Safari** | **нет данных** | **нет данных** | ни одной пробы за всё время |

**Разбор выборки по `ua` (26.08.2026), чтобы не повторить прошлую ошибку молча:**
- Реальные Android-устройства в пробах: минимум 6 разных моделей — Oppo CPH2565 (основной
  источник, много проб), Pixel 8, Samsung SM-A032F (несколько заходов, разные браузеры),
  Meizu Mblu 21, Xiaomi 22101316UG, Tecno KM6. Разные чипсеты, разные Android 10-15 — H.264=0%
  на Android держится широко, не на одном образце (прошлая версия раздела ошибочно писала
  «похоже, одно устройство» — неверно, я не проверил `ua`).
- В той же выборке есть тестовый трафик, не игроки: `Claude/1.37937.1 ... MSIX` (это моя
  собственная сессия — заходы через встроенный браузер Claude Code сегодня) и
  `HeadlessChrome` (мои же прогоны `tests/guard.mjs` через Playwright). Оба варианта —
  desktop Windows Chromium, не мобильные устройства; исключены из выводов выше, но физически
  лежат в той же таблице `beacons` вперемешку с настоящими игроками — при следующей сверке
  фильтровать по `ua not like '%Claude%' and ua not like '%HeadlessChrome%'`.
- **iOS не проверялся ни разу** — не потому, что там подтверждена та же беда, а потому что в
  выборке физически нет ни одного iPhone/iPad/Safari. Аппаратный H.264-энкодер через
  WebCodecs на iOS/Safari у Apple исторически работает надёжно (VideoToolbox) — это общее
  знание о платформе, не измерение в этом проекте. Убирать H.264 из плана для iOS на
  основании android-only данных значило бы додумывать за него.

**Что это значит для плана ниже:**
1. H.264 подтверждённо мёртв **на Android** (аппаратно и программно, широкая выборка
   устройств) — VP8/VP9 программно работают там стабильно (100%), AV1 менее надёжен.
2. На iOS ничего не измерено. Пайплайн должен ветвиться по платформе, а не выбирать один
   кодек на всех: пробовать H.264 первым (может сработать на iOS и на части Android, где
   зонд ещё не был), и только при явном отказе `isConfigSupported()` переходить на VP8/VP9.
   Зонд для этого и существует — `isConfigSupported()` в реальном коде пайплайна должен
   зваться так же, а не полагаться на жёсткий список «этот кодек для этой платформы».
3. Открытый вопрос остаётся: как довести VP8/VP9-видео до формата, который требует Stories
   (H.264-контейнер) на устройствах, где H.264-кодирование недоступно — см. раздел 3. Для
   iOS этот вопрос, скорее всего, не встанет вовсе.
4. «До 10× быстрее реального времени» (раздел 1) подтверждено данными только там, где есть
   аппаратный H.264 — то есть пока нигде, зонд аппаратного успеха не зафиксировал ни разу.

## 1. Концепция Replay Camera против Screen-Record

| Параметр | Запись экрана (Screen-Record) ❌ | Кино полёта (Replay-to-Video) ✅ |
| :--- | :--- | :--- |
| **Кадрирование** | Привязано к форме экрана игрока (узкое/широкое) | Эталонный вертикальный формат 9:16 (1080×1920) |
| **Скорость экспорта** | 1:1 в реальном времени (60с = 60с) | До 10× быстрее реального времени через WebCodecs |
| **Чистота кадра** | Захватывает интерфейс, табло, лаги FPS | Чистый кинематографический кадр без мусора |
| **Детерминизм** | Зависит от просадок кадров устройства | Байт-в-байт идентичный рендер из `seed + input log` |

## 2. Пайплайн генерации видео

**Черновик ниже устарел на шаге кодирования** (раздел 0) — не потому, что H.264 плох сам по
себе, а потому что жёсткий выбор одного кодека на всех не переживает реальность: H.264
подтверждённо мёртв на Android (широкая выборка устройств), но не измерялся на iOS, где
исторически работает надёжно. Шаг 3 должен ветвиться по факту, не по платформе на глаз —
через тот же `isConfigSupported()`, что уже используется в зонде:

```text
┌─────────────────────────────────────────────────────────────┐
│            Детерминированная лента (Seed + Input)           │
└─────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────┐
│  Headless симуляция в OffscreenCanvas(1080, 1920) (Worker)  │
└─────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────┐
│  isConfigSupported(H.264) → да: аппаратный/программный H.264  │
│  isConfigSupported(H.264) → нет (подтверждено на Android):    │
│  VP8/VP9 программно на клиенте — дальше см. открытый вопрос   │
│  ниже про формат, который требует Stories (раздел 3)          │
└─────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────┐
│     Упаковка в MP4 (mp4-muxer) → Upload CDN → shareToStory  │
└─────────────────────────────────────────────────────────────┘
```

Живые данные (раздел 0) не дают выбрать между «кодировать VP8/VP9 и сервером перегонять в
H.264» и «ждать более широких данных, включая iOS, чтобы понять, для какой доли парка вообще
нужен обходной путь» — это отдельный вопрос с явными компромиссами (сложность, стоимость
транскода на сервере, охват устройств), не додумывается здесь.

## 3. Требования Telegram Stories (`shareToStory`)

- **Формат:** MP4 (H.264 / AAC), 30 FPS, разрешение 1080×1920 (9:16). Это требование самого
  Telegram, не наш выбор. На Android, где H.264-кодирование подтверждённо недоступно
  (раздел 0), это создаёт разрыв — на iOS, судя по общей истории платформы, разрыва скорее
  всего не будет вовсе, но прямых данных пока нет. Смотри раздел 2.
- **Безопасные зоны (Safe Zones):**
  - Верхние 14% (~250 px): аватар и индикаторы историй.
  - Нижние 20% (~340 px): поле ввода ответа и реакции.
  - Центральная активная зона: 1080×1330 px.
- **Интеграция:** Метод `Telegram.WebApp.shareToStory(media_url, params)` принимает HTTPS URL с CDN.
