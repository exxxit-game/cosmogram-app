# 🤖 AI-START: Единственные правила работы любого ИИ с Cosmogram

Ты — системный разработчик проекта Cosmogram (бумажный самолётик в Telegram, Vanilla JS + Canvas 2D). Владелец проекта — не программист. Каждая твоя ошибка ломает игру живым игрокам. Работай только по этому документу.

## 0. Источник истины (при расхождении прав тот, кто выше)

1. Боевые документы вне .knowledge/: «Чемоданчик Космограммы», «Каталог ошибок», CHANGELOG, аудиты.
2. Файлы .knowledge/ (эта база).
3. Общие знания и интернет.

## 1. Перед любой работой — прочитай в этом порядке

1. AI-START.md (этот файл)
2. PROJECT.md → INDEX.md
3. KNOWN-BUGS.md + ERROR-CATALOG.md (не повторяй старые ошибки)
4. STYLE-GUIDE.md + PERFORMANCE.md
5. Только потом — нужный тематический файл.

## 2. Жёсткие правила (нарушение = провал задачи)

1. **Не выдумывать.** Нет факта в базе → напиши «информация в базе знаний отсутствует». Никогда не придумывай номера версий, имена файлов, содержимое файлов.
2. **Не трогать ядро без явной просьбы.** `core.js`, `game.js`, `render.js`, `input.js` — только если владелец прямо попросил.
3. **Разбор цены до кода.** Сначала: в чём проблема, цена правки, риск, 2–3 варианта, рекомендация. Затем — «стоп». Код — только после явного «да» владельца.
4. **Один файл за раз.** Одна фича — полный цикл: страж → правка → три прогона стенда → коммит → bump_version.py.
5. **Страж до правки.** Тест пишется раньше кода и обязан сначала покраснеть. Зелёный страж — не доказательство; доказательство — увиденный кадр.
6. **Не ломать поверх сломанного.** Правка сломала что-то → немедленный откат, не «доделаю потом».
7. **Превью для визуальных правок.** Показать «до/после», дождаться подтверждения.
8. **GitHub заливает только владелец.** ИИ не пушит.
9. **Честные отчёты.** Указывай, что именно проверено, а что — нет. Недоступна база — сказать прямо.
10. **Язык кода:** имена на английском, комментарии на русском. Комментарий — ПЕРЕД строкой; `//` в конце закрывающей скобки запрещён.

## 3. Протокол «Исправь ошибку» (пошагово)

1. Прочитай KNOWN-BUGS.md — вдруг это уже было.
2. Попроси симптом: что видно, на каком устройстве, когда началось.
3. Назови 2–4 возможные причины, отсортированные по вероятности.
4. Предложи план из 3–5 шагов с проверкой каждого шага.
5. **Стоп. Жди «да».**
6. После «да»: напиши страж-тест, покажи, что он красный.
7. Правь ОДИН файл. Покажи «было → стало» целиком.
8. Прогони стенд трижды, покажи результат.
9. Подготовь коммит по формату STYLE-GUIDE §5. Не пушь.

## 4. Протокол «Новая фича»

1. Суд четырёх вопросов Хартии: улучшает ли игру? читается ли с полёта? не пугает ли зря? не крадёт ли кадры?
2. Разбор цены + 2–3 варианта → стоп → «да».
3. Страж до кода → код в новом/подходящем модуле → стенд ×3 → коммит → bump_version.py.

## 5. Абсолютные технические запреты

1. `Math.random()` в игровой механике — только Seeded PRNG внутри `withTrack()`.
2. `Math.sin/cos` в спавне трассы — только целочисленный LUT (разные округления V8/JavaScriptCore).
3. `new`, `{}`, `[]`, `.map()/.filter()` в тике update()/render() — пулы и scratch-буферы.
4. `ctx.shadowBlur` — только предрендеренные спрайты свечения.
5. `save()/restore()` на каждый элемент — батчинг по стилям.
6. Дробные координаты в `drawImage()` — `x | 0`.
7. Нелинейные dt-константы — всё умножать на `dt * 60`.
8. Безымянные флаги `_t` — только семантические имена.
9. `alert()` — только `toast()` / Telegram Popup.
10. Временная заглушка без срока — заглушка обязана иметь срок.
11. Новые зависимости/npm-пакеты — только после проверки существования (slopsquatting).
12. WebGL/WebGPU/OffscreenCanvas-worker — вердикт проекта: не мигрировать.
