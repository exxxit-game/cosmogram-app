### 1. Девять премиум-скинов пересобирают и (в одном случае) пересортировывают статичный массив клеток КАЖДЫЙ кадр — тот самый паттерн, который сосед по файлу явно чинит на 09.09.2026, но здесь пропущен (`js/render.js`)

**Кто задет:** только игроки, которые купили и НАДЕЛИ один из этих девяти скинов (все
`extra:true, price:100`, покупка за внутриигровую валюту) — не все игроки. Внутри этой
группы — задеты и слабые, и сильные устройства, но по-разному: GC-паузы от частых мелких
аллокаций массивов бьют по слабому Android (Samsung A03 Core — собственный эталон
проекта) заметно больнее, чем по десктопному V8 с прогретым JIT.

**Механизм.** `drawPremiumFx2()` (`render.js:1063-1070`) — единая точка входа для всех
премиум-эффектов скина, вызывается из `drawPlane()` (`render.js:5599`) КАЖДЫЙ отрисованный
кадр полёта (`loop()` → `draw()` → `drawPlane()`, до `Q.fps`, то есть вплоть до 120 Гц на
устройствах с высокой частотой обновления — PERFORMANCE.md отдельно отмечает, что WKWebView
троттлит до 60, но Android WebView такого потолка не документирует). Комментарий прямо над
вызовом (`render.js:5591-5598`, датирован 09.09.2026, «Скины не должны жрать зря,
стратегический итог») говорит: качественный порог (`if(hq)`, раньше резавший узор на «дне»)
СНЯТ ПОЛНОСТЬЮ, включая `Q.level===0` — по прямой просьбе владельца проверить на реальном
Samsung A3 Core. Тут же честно признаётся: **«Замера с реального слабого устройства ещё
нет — следующий шаг именно он»**. То есть код уже допускает: измерение «максимум ~0.18мс»
могло не покрыть каждую из 44 функций поровну.

Действительно не покрыло. В тот же день (09.09.2026) заметная часть соседних функций получила
чистку — статичные позиции клеток вынесены в модуль-level кэш с построением один раз

зерна… раньше пересчитывались заново… для всех до 220 зёрен каждый кадр — теперь считаются
один раз и кешируются»). Тот же приём применён к `nacreRowPathsBuild` (2147-2162),

**Масштаб честно:** 121-250 коротких (2-3 поля) временных объектов в секунду при 60 FPS —

признано проектом достаточным поводом для фикса на других объектах. Одной живой цифры с
A3 Core по этой конкретной группе функций в коде нет — комментарий сам называет это
следующим шагом. Не переоткрываю уже решённое: 35 из 44 премиум-функций (по числу записей в

### 2. `corrScrollTick()` пишет CSS custom property в `documentElement.style` каждый кадр — задевает только широкий вьюпорт (планшеты/десктоп/альбомная ориентация), без тир-гейта (`js/render.js:5672-5676`)

**Кто задет:** НЕ узкие телефоны (там `fieldL()===0`, полоса коридора вовсе не показывается,
см. ниже) — это специфически проблема сильных/широких устройств: планшеты, десктопный
браузер, любой альбомный режим, где коридор уже вписан с полями по бокам. Частота эффекта
растёт с частотой обновления экрана устройства (60→120→144 Гц), то есть буквально хуже
именно на топовых мониторах/планшетах, не на слабом телефоне.

**Механизм.** `corrScrollTick(dt)` вызывается из `loop()` (`render.js:5702`,
`if (corrShown) corrScrollTick(dt);`) каждый кадр, пока видна полоса коридора. Само тело:
```js
function corrScrollTick(dt){
  corrScrollY=(corrScrollY+dt*S.speed*S.timeScale*10)%96;
  document.documentElement.style.setProperty('--corrScrollY',corrScrollY.toFixed(2)+'px');
}
```
`--corrScrollY` читается в `index.html:1197` как `background-position:0 var(--corrScrollY, 0px)`
у элементов `.corrEdgeL`/`.corrEdgeR` — `background-position` не композитится бесплатно
(в отличие от `transform`/`opacity`), это свойство репейнта. Запись custom property на
корневой `documentElement` (а не на сами два маленьких элемента-полоски) означает, что браузер
должен пересчитать каскад для `:root`, а затем инвалидировать всех потребителей переменной —
в данном случае только два элемента, так что видимый репейнт дёшев по площади, но сама запись
происходит БЕЗУСЛОВНО каждый кадр, без проверки «изменилось ли достаточно, чтобы иметь
значение» (в отличие от HUD, где есть явный гейт `if(sc!==lastScoreShown)`), и без единого
quality-тира — на «Ультра»/120Гц тот же код пишет DOM в среднем вдвое чаще, чем на «Дне»/60Гц,
хотя видимая польза (плавность мелкого скролла текстуры-полосы) не растёт пропорционально.

**Кто НЕ задет — проверено, не гипотеза:** `wide=fieldL()>0` (`core.js:1511`) — на узком
телефоне (полноэкранный canvas без полей) `corrWideOk` никогда не становится `true`,
`corrShown` остаётся `false`, `corrScrollTick` не вызывается вовсе (ранний `if(corrShown)`
в `loop()`). То есть это НЕ баг «общий для всех телефонов» — категория «сильное устройство
с широким вьюпортом», ровно то разделение, которое просило задание.

**Второй заход (масштаб):** запись `setProperty` на двух маленьких DOM-узлах — не в одном
ряду по цене с полным layout thrash (не читается `getBoundingClientRect` следом, нет
принудительного синхронного reflow), поэтому это не «критический» тормоз, скорее
малозаметная постоянная нагрузка на композитор/рендерер именно на устройствах, где полоса
вообще показывается — и именно этот тип устройств (планшет/десктоп) обычно жалуется на
частоту кадров иначе, чем телефон (тайлинг/энергосбережение другое). Дешёвый фикс без
изменения видимого поведения существует (писать `style.setProperty` на сами `l`/`r`
элементы из `corridorEdgesSync`, а не на `documentElement`, или квантовать запись, как уже
сделано для `bgGradient`/градиентов), но это уже решение, не входит в рамки read-only аудита.

### 3. (минорная, для полноты) `obstacles.indexOf(o.pairMate)` — O(n) поиск на каждого спаренного «ловца», без тир-гейта, но реальный масштаб пренебрежимо мал (`js/game.js:2230`, `js/render.js:3409`)

Дважды в кодовой базе (физика — `game.js:2230`, каждый физический тик 60Гц, для КАЖДОГО
спаренного ловца, и без того И ведущего, И ведомого; отрисовка — `render.js:3409`, каждый
рендер-кадр, но только для ведущих) есть `obstacles.indexOf(o.pairMate)===-1` — линейный
поиск по всему списку препятствий (`POOL_CAP=64`), чтобы проверить, жив ли партнёр по паре.
Это буквально «стоимость растёт с числом объектов на экране, без тир-гейта» — формально
подпадает под категорию, которую просило задание, поэтому фиксирую. НО второй заход
(обязательный по методу этого аудита) показывает: реалистичный потолок одновременных
спаренных ловцов на экране — единицы (не десятки), значит худший правдоподобный случай —
что-то вроде 5-10 спаренных ловцов × 64 сравнения ссылок = 320-640 сравнений за тик/кадр,
то есть десятки тысяч простых `===` в секунду, не миллионы — на три порядка ниже бюджета
кадра (4мс на физику). Не переквалифицирую в «настоящую» находку с рекомендацией чинить —
привожу для полноты списка «сканировано и явно найдено, но отклонено по масштабу», как
требует метод «второй проверочный заход» этого аудита.

## Проверено и НЕ находка (второй заход подтвердил, что уже решено правильно)

- **Пулы объектов** (`poolOb`/`poolStar`/`poolPow`/`poolPart`/`poolPop`, `game.js:25-29`) —
  `take()`/`give()`, `killIdx()` — swap-remove без `splice`, без аллокаций в горячем пути.
  Соответствует Zero-GC закону PERFORMANCE.md §2.19 дословно.
- **Path2D астероидов** (`render.js:3343-3393`) — кэшируется на `o._path` при спавне,
  инвалидируется явно при возврате в пул (комментарий сам указывает на исторический баг
  v1.282.14 и его фикс) — ровно рекомендация PERFORMANCE.md §2.12, уже выполнена.
  То же для спрайтов обломков/спутников (`bakeDebrisSprite`/`bakeSatSprite`,
  кэш-проверка `o._sprite && o._spritePx===px`).
- **`trailHistBuf`/`echoBuf`** (`render.js:3547,3685`) — капы 28/40 с `.shift()`, живой
  замер худшего следа (Кельтская коса) уже в комментарии: 0.166мс при бюджете ~10мс,
  запас ×60 — измерено, не гипотеза, оставлено осознанно.
- **`celticTwist`/`celticBraid`** (`render.js:3661-3682`) — да, строит `strands=[]` и
  сортирует его каждый сегмент каждый кадр, но это тот же измеренный случай выше (n≤28,
  входит в тот же живой замер 0.166мс) — не отдельная находка.
- **`gradCache`** (`render.js:2645-2646`) — капается по счётчику (>400 → полный сброс),
  бюджет-осознанный, не растёт бесконечно.
- **HUD** (`game.js:2434,2436`) — запись в DOM только при изменении значения
  (`lastScoreShown`/`lastDistShown`), не каждый кадр.
- **Слушатели событий** (`grep addEventListener` по всем трём файлам) — все регистрируются
  один раз на уровне модуля при загрузке (`window.addEventListener('resize',…)` и т.п.),
  ни одного паттерна «подписка внутри функции, вызываемой повторно, без снятия» не найдено
  ни в `render.js`, ни в `game.js`; в `core.js` — обёртка `tg.onEvent`/`tg.offEvent`
  (`core.js:49-73`) явно синхронизирует подписку/отписку через `cb.__cgWrap`.
- **`qualityTick()`** (`render.js:43-96`) — метрика снимается только в реальном полёте
  (проверено через `inGameNow` в `loop()`), карантин/потолок-памятка предотвращают
  «качели качества», уже описанные и решённые в v1.284.22.
- **`isLowPowerDevice()`** (`render.js:2706-2713`) — мемоизирована на 1.5с, не читает
  `navigator`/DOM каждый кадр.
- **`Store.get()` внутри `qThr()`** (`render.js:24`) — вызывается не каждый кадр (только
  раз в секунду внутри `qualityTick`), и сам `Store.get` — чтение JS-объекта в памяти после
  первой ленивой загрузки, не синхронный `localStorage.getItem` на каждый вызов.
- **Звёзды фона (`bgStars`)** — плотность по тиру (`STAR_TIER=[90,140,180]`, ультра — весь
