## 0. Зачем отдельный документ, а не просто PERFORMANCE.md

PERFORMANCE.md описывает движок целиком (частицы, звёзды, препятствия, пулы).
Скины — отдельный, узкий, но частый источник новой геометрии: каждый новый скин —
это новая функция `fx<Имя>(ctx,sk,nowMs)`, которую пишут с нуля, глядя на существующие.
Если в момент написания под рукой нет готового набора «вот так дёшево, а вот так дорого
конкретно для скинов» — новый скин с высокой вероятностью повторит уже решённую ошибку.
Этот файл — готовый набор образцов на будущее, не теория.

## 1. Как измерять (без этого числа — шум, не факт)

**Наивный замер (один проход, N=200) даёт ложные выбросы.** Первая попытка в этом
проходе показала `culPersianIsfahan` 53мс и `illOrigami` 71мс — оба абсурдны и
противоречили прямому чтению кода (например, три «персидских» скина зовут ОДНУ и ту же
функцию с разницей только в оттенке — не могут стоить по-разному на порядки). Причина —
случайная пауза GC/JIT совпала по времени с конкретной функцией в цикле прогона.

**Рабочая методика:**
1. Прогреть 5–10 итераций (даём JIT скомпилировать горячий путь).
2. Прогнать **7 РАУНДОВ** по N=50–60 итераций каждый.
3. Взять **МЕДИАНУ по раундам** (не среднее одного прогона).

```javascript
function bench(fn){
  for(let i=0;i<8;i++) fn(); // прогрев
  const rounds=[];
  for(let r=0;r<7;r++){
    const t0=performance.now();
    const N=50;
    for(let i=0;i<N;i++) fn();
    rounds.push((performance.now()-t0)/N);
  }
  rounds.sort((a,b)=>a-b);
  return rounds[3]; // медиана из 7
}
```

Проверка метода: три скина, зовущие идентичную `culPersianCity()` с разным `medHue`,
после честного замера показали практически одинаковую стоимость — ровно то, что
ожидается по чтению кода. Наивный замер до этого показывал их как разные на порядок.

**Инструмент:** Playwright MCP (`browser_evaluate`) прямо в живой странице игры —
`drawPremiumFx2(ctx, skin, fx, nowMs)` можно вызывать напрямую на тестовом
`<canvas>` в отрыве от игрового цикла.

## 2. Чёрный список дорогих canvas-примитивов (проверять в КАЖДОМ новом скине)

Это не про кэш геометрии (раздел 3) — это про операции, дорогие сами по себе,
независимо от того, кэширована форма или нет.

| Примитив | Почему дорого | Статус в скинах на 09.09.2026 |
|---|---|---|
| `ctx.shadowBlur` | Свёртка размытия каждый кадр, квадратично растёт с DPR | Убран из проекта раньше (см. PERFORMANCE.md §2.13); в fx-скинах не встречается |
| `ctx.filter='blur(...)'` | Та же категория, что shadowBlur — на слабых Android часто НЕ аппаратно ускорен (в отличие от десктопного Chrome, который его ускоряет — замер на десктопе может ЛГАТЬ) | Был один живой вызов — `culTnalak` (id84), убран 09.09.2026, см. раздел 4 |
| `getImageData`/`putImageData` | На порядки медленнее `fillRect`/`drawImage` (см. PERFORMANCE.md §2.21) | Не используется ни в одном fx-скине |
| `createPattern` пересоздание каждый кадр | Если паттерн статичен — пересоздание объекта на каждый вызов лишнее | Не используется |
| `createLinearGradient`/`createRadialGradient` **без** повторного вызова `fill` на большой площади | Само создание объекта градиента дешёвое — это НЕ входит в чёрный список; дорога сама заливка, которая стоила бы столько же и без пересоздания объекта | Используется широко, кэшировать сам объект градиента не имеет смысла (доли микросекунды) |

**Урок 09.09.2026 (Т'налак):** десктопный замер `ctx.filter='blur(1.5px)'` показал
0.033мс — дёшево. Но десктопный Chrome ускоряет `filter` через GPU, а Samsung A3 Core
(целевое слабое устройство владельца) может не ускорять. **Правило:** если примитив уже
признан рискованным в проекте для ОДНОГО случая (`shadowBlur`) — тот же риск для
однотипного примитива (`ctx.filter`) не отменяется хорошим числом на десктопе. Проверять
по чёрному списку категорий, не только по замеру на своей машине.

## 3. Шесть приёмов кэширования — когда какой

Разные скины анимированы по-разному: у одних движется ВСЁ (цвет, форма, поворот), у
других — почти ничего. Кэшировать нужно РОВНО ту часть, которая не меняется, и не
трогать ту, что меняется по-настоящему — иначе получится либо неработающая
оптимизация (кэш ничего не экономит), либо визуальный баг (кэш заморозил то, что
должно двигаться).

### 3.1 Offscreen-спрайт (полностью статичная форма)
Форма/цвет НЕ зависят от времени вообще (или зависят только через `drawImage` с
готовым битмапом). Рендерим один раз на отдельный маленький `<canvas>`, каждый кадр —
только `ctx.drawImage()`.

```javascript
let mySprite=null;
function buildMySprite(){
  if(mySprite) return mySprite;
  const S=4; // супервыборка для чёткости (принято в проекте — см. saturnRingSprite)
  const c=document.createElement('canvas'); c.width=W*S; c.height=H*S;
  const x=c.getContext('2d'); x.setTransform(S,0,0,S,0,0);
  /* рисуем один раз здесь */
  mySprite={c,W,H};
  return mySprite;
}
// в кадре: ctx.drawImage(buildMySprite().c, x, y, W, H);
```
**Применено:** `cosSaturn` (каждое кольцо — свой спрайт + независимый живой поворот —
работает ТОЛЬКО потому что у Сатурна равномерный масштаб `COS_SCALE`; для сплюснутого
аккреционного диска этот приём НЕ годится, см. 3.3), `culCintemani` (мотив на 100%
статичен, `culCintemaniUnit` даже не принимает `nowMs`), `culTnalak` и `cosQuasi`
(09.09.2026, см. раздел 4), общая карточная функция `culPersianCity` (кэш по `medHue` —
один спрайт-кэш работает сразу на 5 скинов).

### 3.2 Path2D с живым цветом/трансформом
Геометрия статична, но цвет или позиция реально меняются каждый кадр.
Путь строится один раз, `ctx.fill(path)`/`ctx.stroke(path)` — каждый кадр с новым
`fillStyle`/`ctx.translate+rotate` вокруг неизменного пути.

**Применено:** `matWootz` (19 волнистых строк, форма не зависит от времени — только
`shine`-цвет), `matNacre` (все прямоугольники строки — один batched `Path2D` на
строку, т.к. цвет одинаков для всех ячеек строки одновременно), `cosGalaxy` (оба
спиральных рукава — один статичный путь, крутится целиком через `ctx.rotate`),
`cosPlateau` (3-лучевая геометрия ячейки статична, честная иризация цвета живая).

### 3.3 Path2D-форма, поворот/цвет — живые, БЕЗ спрайта
Похоже на 3.2, но конкретно для случая, когда общий контекст использует
**неравномерный масштаб** (`ctx.scale(9,2.6)` и подобное). Тут спрайт-с-поворотом
(3.1) визуально ЛОМАЕТСЯ — поворот уже сплюснутой картинки «кувыркается», а не
вращается как надо. Кэшируем ТОЛЬКО форму (Path2D), поворот и цвет остаются живыми.

**Применено:** `cosAccretion` (11 колец — форма кольца зависит только от радиуса,
кэширована; `ctx.rotate(speed*p)` и цвет — по-честному живые каждый кадр, ровно как
до правки).

### 3.4 Кэш параметров, не картинки (для честно-случайных/по-индексных узоров)
Каждый элемент выглядит «случайным», но на самом деле детерминирован (фиксированный
seed через `mulberry32` или формула по индексу). Дорогая часть — сами вычисления
(вызовы RNG, `Math.hypot`, сборка строки цвета) — считается ОДИН раз в массив,
дешёвая часть (покачивание/прозрачность по времени) — остаётся честно живой.

```javascript
let cache=null;
function buildCache(){
  if(cache) return cache;
  cache=[];
  for(let i=0;i<N;i++){
    const rnd=mulberry32(SEED)(); // дорого — считаем один раз
    cache.push({x:.., y:.., style:'hsla(...)'}); // готовая строка цвета, не собирать заново
  }
  return cache;
}
// в кадре: cache.forEach(p=>{ const sway=Math.sin(now*k+p.x); /* дёшево, живое */ });
```
**Применено:** `culRyijy` (169 ворсинок — позиция/цвет/дрожь кэшированы, покачивание
(`sway`) — честно живое, каждая ворсинка колышется по-своему), `cosPhyllo` (220
позиций семян по формуле Фогеля — `sqrt`+`trig`+хью зависят только от индекса,
кэшированы; какие семена уже показаны и их прозрачность-по-свежести — живые).

### 3.5 Кэш тригонометрического базиса (для «дышащих» силуэтов)
Форма реально меняется каждый кадр (не поворотом — самими координатами), но через
один и тот же непрерывный масштабный коэффициент. Кэшируем дорогие `sin/cos/pow`
базисные термы по углу один раз, каждый кадр — только дешёвое умножение на живой
масштаб.

**Применено:** `cosNebula` (32 угла — `{sinA,cosA,pow(|cosA|,.35)}` кэшированы;
`grow`/`viewSquish` — живые, финальная точка `r*sinA` считается по кадру дёшево).

### 3.6 Запечённый трансформ в Path2D (`Path2D.addPath` + `DOMMatrix`)
Развитие приёма 3.2 — когда `ctx.save/translate/rotate/restore` вокруг каждого из
МНОГИХ элементов сам по себе заметен в профиле. Трансформ каждого элемента
запекается ПРЯМО в его собственный Path2D один раз через
`path.addPath(basePath, new DOMMatrix().translate(x,y).rotate(a))` — в кадре не
остаётся ни одного `save/translate/rotate/restore`, только `fill`/`stroke`.

```javascript
const cellPath=new Path2D();
cellPath.addPath(baseShape, new DOMMatrix().translate(cx,cy).rotate(angle));
// в кадре: ctx.fill(cellPath); ctx.stroke(cellPath); — без save/restore вообще
```
Проверено через WebSearch: `Path2D.addPath` с `DOMMatrix` — «доступно во всех
браузерах с января 2020», подтверждено живьём (`typeof DOMMatrix==='function'`).

**Применено:** `culJamdani` — второй, более глубокий заход (09.09.2026, после
прямого вопроса владельца «с этим ещё что-то можно?»): 0.148 → 0.127мс первым
проходом (Path2D + живой трансформ), затем этим приёмом — трансформ запечён,
`save/translate/rotate/restore` на ячейку убраны полностью.

## 4. Что нашлось и исправилось 09.09.2026 (второй проход, после «нашёл максимум?»)

Первый проход (разделы 1–3) закрыл кэширование геометрии. Второй проход — отдельная
проверка по чёрному списку дорогих ПРИМИТИВОВ (раздел 2), не геометрии:

- **`culTnalak` (id84):** живой `ctx.filter='blur(1.5px)'` каждый кадр — та же
  категория риска, что `shadowBlur`. Заменён на приём 3.1: блюр запечён в
  offscreen-спрайт один раз (форма и радиус размытия неизменны, меняется только
  alpha полосы). Замер: 0.033 → 0.018мс (десктоп; на слабом Android разница в
  категории риска больше, чем в этом числе).
- **`cosQuasi` (id58):** 40 живых `createRadialGradient`+`fill` каждый кадр для
  точек дифракции, хотя все 40 позиций неподвижны (меняется только момент появления
  и краткая вспышка). Заменён на приём 3.1 (8 уникальных спрайтов: 4 радиуса ×
  обычный/вспышка) + кэш позиций (приём 3.4, без повторных `pow/cos/sin`). Замер:
  0.16 → 0.053мс.

Оба — визуально проверены скриншотом на увеличенном отладочном канвасе до и после,
узор не изменился (это перформанс-правка, не редизайн — макет не требовался).

## 5. Порог включения по уровню графики (Q.level) — решено 09.09.2026

**Было:** премиум fx-паттерны рисовались только при `Q.level>=2` (`hq`) — на
среднем и низком тире («дно») скин показывал только плоский цвет без узора вообще.

**Стало:** после переписывания всех 44 на дешёвые приёмы выше, вызов
`drawPremiumFx2()` в `drawPlane()` (render.js) сделан безусловным — узор рисуется
на ВСЕХ уровнях, включая `Q.level=0` («дно», самый слабый тир). Обоснование: после
оптимизации худший из 44 замеров — 0.164мс (`culRyijy`) при бюджете кадра 16.666мс
(PERFORMANCE.md §1) — с большим запасом даже без дополнительного тир-гейта.

**Не решено на 09.09.2026:** это подтверждено настольным замером (Chromium),
не на реальном слабом устройстве. Финальная проверка — Samsung A3 Core владельца
вживую. Если реальное устройство покажет, что даже эти цифры дают просадку —
возвращать тир-гейт по факту его чисел, не по десктопному замеру.

## 7. Почему `culRyijy` остаётся дороже всех — и это осознанный выбор, не недоработка

Финский рюйю — длинноворсовая текстура, где КАЖДАЯ из ~169 ворсинок покачивается
по-своему (не общей волной). Это не декоративная деталь, а суть узора («длинный
ворс честно покачивается» — из факта скина). Полное кэширование картинки убило бы
именно то, ради чего скин существует. Кэшировано всё, что можно было (позиция,
цвет, дрожь — приём 3.4), живым честно осталось только покачивание. Владелец дважды
проверял, не сдался ли я рано на этом и трёх похожих случаях («только 4 из 44?») —
после повторного разбора для всех четырёх нашлись частичные, но реальные приёмы
(3.3, 3.4, 3.5); дальше в рамках сохранения самого узора двигаться некуда без
потери того, что делает скин узнаваемым.

## 10. Бонус для Ультра — приём, который ДОБАВЛЯЕТ богатство сверху (09.09.2026)

Отдельная задача от раздела 5: раз после оптимизации худший из 44 замеров —
0.164мс при бюджете рендера ~10мс, резать под слабые уровни почти нечего — у них
и так есть запас. Реальный резерв — наоборот, наверху: на Ультра можно ДОБАВИТЬ
эффект поверх уже готового кэша почти бесплатно (лишний `drawImage`/`stroke` того,
что уже посчитано), не трогая три нижних уровня.

**Пилотная проверка (3 скина, макет одобрен владельцем 09.09.2026):**
- `cosSaturn` — мягкое гало вокруг колец (два дополнительных `drawImage` того же
  кэш-спрайта, крупнее и почти прозрачно, `lighter`) — как на реальных снимках Кассини.
- `cosQuasi` — на каждой точке тёплая/холодная кайма (переиспользование готового
  спрайта со сдвигом ±0.2 и `lighter`) — настоящая хроматическая дисперсия,
  физически в тему самого явления (дифракция).
- `cosPhyllo` — тонкая спиральная Path2D-трасса через уже посчитанные 220 точек
  (путь строится один раз из уже готового массива `phylloSeedsBuild()`).

Итог по всем трём: ноль новых вычислений, только повторное использование уже
оплаченного кэша с других offset/alpha/composite — конкретно то, ради чего
кэш строился в разделе 3, только развёрнутое в другую сторону (не «дешевле», а
«красивее за ту же цену»). Дальнейшее применение к остальным 41 скину — по
семействам, не поштучно (см. таблицу §6): металл/полировка → блик-волна, кость/
перламутр/шёлк → перелив, космос-свечение → своя физика на каждый феномен,
волокно/нить → блеск кончика. Форсировать бонус там, где ему по-честному неоткуда
взяться — запрещено (правило владельца: «не выдумывать ради количества»).

## 11. Чеклист для НОВОГО скина (используйте этот файл раньше, чем пишете fx-функцию)

1. Анимировано ли ВСЁ, или только часть (цвет/позиция/поворот)? Если только часть —
   не кэшировать всю функцию как один спрайт, кэшировать только неизменную часть.
2. Равномерный масштаб контекста (`ctx.scale(k,k)`) или сплюснутый
   (`ctx.scale(a,b)`, a≠b)? При сплюснутом — приём 3.1 (спрайт+поворот) визуально
   ломает форму, использовать 3.2/3.3.
3. Элементы «случайны», но на самом деле по фиксированному seed/формуле от индекса?
   → приём 3.4, не пересчитывать RNG/тригонометрию по кадрам.
4. Есть ли в функции `ctx.filter`, `ctx.shadowBlur`, `getImageData`? → раздел 2,
   чёрный список, искать замену ДО первого коммита, не после жалобы на слабом
   устройстве.
5. Замерить приёмом из раздела 1 (7×50, медиана) — не доверять единичному
   `performance.now()` до/после.
6. Ориентир по бюджету: **всё, что дороже ~0.1мс на десктопном замере — кандидат на
   разбор** (это не жёсткий порог, а сигнал присмотреться, т.к. слабое устройство
   может показать хуже, особенно для `ctx.filter`/`shadowBlur`, см. §2).
