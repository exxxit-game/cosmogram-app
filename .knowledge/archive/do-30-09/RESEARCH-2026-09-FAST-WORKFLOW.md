# Исследование: почему рабочий цикл был медленным и что изменено (16.09.2026)

Владелец: «туда-сюда гонять стражей по 50-100 раз из-за мелкой правки — тупой подход, нужно
быстро». Ниже — разбор причины и что реально изменено в коде по итогам, не только теория.

## Что на самом деле было медленным (по факту этой сессии, не по догадке)

1. **Полный прогон 257 стражей — раньше строго по одному** (`for(...) await g(browser)`).
   Каждый страж сам открывает свой `browser.newContext()`/`newPage()` — то есть 257 полных
   загрузок игры подряд, одна за другой. Источники (Playwright docs, BrowserStack,
   TestDino, кейс PayPay Card — 30 мин → 11 мин на параллелизации) сходятся: `newContext` —
   дешёвая операция (общий процесс браузера), тяжёлая часть — сама загрузка страницы. Раз
   каждый страж уже изолирован в своём контексте и НИ ОДИН страж не пишет на диск (grep по
   всему файлу подтвердил — только чтение статики), гонки исключены, и стражи можно гонять
   пачками одновременно, а не по одному.
2. **Я сам гонял стражей и скриншоты после каждой мелкой CSS-правки** — не техническая
   проблема, а решение о процессе. Правило (уже было в памяти: «guard.mjs usage» — `--only=`
   для изоляции, весь набор один раз перед закрытием) в этой сессии не соблюдалось.
3. **Зависание ноутбука** — не из-за самого параллелизма, а из-за того, что несколько прогонов
   стражей накладывались друг на друга: предыдущий фоновый прогон не был завершён/убит, когда
   стартовал следующий. Источники (Chromium issue tracker, PandaStack, webscraping.ai)
   подтверждают: headless Chromium — не один процесс, а дерево (браузер + GPU + network +
   по renderer'у на вкладку), холодный старт — уже 50-150 МБ ДО открытия хоть одной страницы.
   Несколько живых инстансов одновременно (а не один с несколькими вкладками) — вот что
   реально ест память, не число вкладок внутри одного инстанса.
4. **Версия игры поднималась вручную в 3 места** (core.js, 23 хвоста `?v=` в index.html,
   sw.js) — три отдельных Edit/sed-вызова на каждую правку игрового файла.

## Что изменено в коде

- **`cosmogram-crew/tests/guard.mjs`**: сеймы стражи теперь идут пачками — `runPooled()`,
  по умолчанию 3 одновременно (`GUARD_CONCURRENCY`, можно поднять переменной окружения на
  машине помощнее). Было 8 при первой попытке — уронил до 3 после жалобы на зависание.
- **Лок-файл** (`tests/.guard.lock`): второй параллельный запуск, пока жив первый, сразу
  отказывает с понятным сообщением вместо того, чтобы тихо запустить ещё один Chromium поверх
  уже работающего — это и есть настоящая причина прошлого зависания, не сам параллелизм.
- **`cosmogram-app/tools/bump-version.mjs`**: один вызов (`node tools/bump-version.mjs`)
  поднимает версию во всех трёх местах разом и печатает старое→новое, вместо трёх ручных правок.

## Что не стал делать сейчас (дороже/рискованнее, не первоочередное)

- **Живой CSS без reload через `chrome://inspect`** (adb forward tcp:9222 →
  `chrome_devtools_remote`, Chrome DevTools подключается к реальному телефону, правки в
  Styles-панели видны мгновенно без перезагрузки страницы) — реальная техника, подтверждена
  официальной документацией Chrome for Developers, но требует поднятого Chrome DevTools GUI и
  постоянного USB/адб-туннеля; не поднимал сейчас, чтобы не плодить ещё один параллельный
  процесс сразу после жалобы на зависание. Кандидат на следующий заход, если ручная adb-проверка
  (screencap) всё ещё будет ощущаться медленной.
- **scrcpy** (зеркалирование экрана телефона в реальном времени, 30-60 fps, задержка 35-70мс,
  официальный опенсорс от Genymobile) — полезен в первую очередь ВЛАДЕЛЬЦУ, чтобы смотреть
  вживую без ожидания скриншота от меня; мне самому это не ускоряет проверку (я всё равно вижу
  только дискретные снимки через инструмент). Предложить, если понадобится показывать процесс
  живьём, не как первоочередной технический фикс.

## Правило на будущее

Перед КАЖДЫМ запуском полного прогона стражей — проверить, что предыдущий прогон точно
завершился (лок-файл теперь делает это автоматически и откажет сам, если нет). Полный прогон —
один раз перед коммитом, не после каждой правки. Во время правок — `--only=<номер>` на
конкретный изменённый страж, если вообще нужно проверять мгновенно.

## Часть 2 (тот же день, позже): «какие плагины/скрипты убирают у тебя ошибки автоматически»

Прямая просьба владельца — исследовать, как построить инструменты, которые устраняют лишние
действия и ошибки САМИ, не полагаясь на то, что я вспомню правило в нужный момент. Реальный
источник (несколько статей 2026 года про Claude Code hooks, плюс общее «guardrails» исследование
по AI-агентам, en/de/zh/ja): **детерминированные хуки решают другую задачу, чем промпт** — промпт
это вероятностная подсказка модели, хук это жёсткий барьер уровня рантайма, который не зависит от
того, вспомнила модель правило или нет («neurosymbolic»: нейросетевое рассуждение + недоступные
для переопределения символьные правила). Практический вывод оттуда же: «если типизировала одно и
то же правило в CLAUDE.md/памяти и всё равно нарушила — это ровно кандидат на хук, не на более
громкую формулировку текстом».

**Что уже было в проекте** (`protect-core.sh`, `version-guard.sh`, `guard-deploy-content.sh`) —
хороший, работающий паттерн: PreToolUse, парсинг JSON через `node -e` (jq на машине не стоит,
уже дважды больно ловили этот факт), `permissionDecision: deny/ask`. Все новые хуки сделаны
в том же стиле, не изобретался новый.

**Построено сегодня, проверено живьём (не просто «должно работать» — реальный ввод через файл+cat,
не через echo: у echo в этом Git Bash обнаружилась своя особенность — интерпретирует `\t`/`\b`
как управляющие символы даже без `-e`, один ложный «баг» хука на этом словил и сама, важно помнить
при следующем тестировании хуков в этом окружении):**
1. `no-double-background.sh` — отказ, если команда с `run_in_background:true` сама ещё раз
   заканчивается на `&` (ровно баг, повесивший ноутбук сегодня).
2. `no-broad-git-add.sh` — отказ на `git add -A/--all/.` (было только текстовым правилом
   CLAUDE.md, теперь техническое ограничение, тот же перевод, что уже сделан для ядра/версии).
3. `syntax-check-js.sh` (PostToolUse на Edit|Write) — `node --check` на любой изменённый .js
   сам, без необходимости помнить об этом руками («Smoke-check after bulk edit» — было только
   в памяти текстом, теперь автоматически).
4. `no-secrets-in-commit.sh` — лёгкий regex-сканер staged diff перед `git commit` (AWS-ключ,
   PEM-приватный ключ, JWT-похожее, GitHub/Slack/Stripe-подобные токены). Не замена настоящему
   gitleaks (~60+ сигнатур, отдельный бинарник) — сознательно НЕ ставился новый бинарник без
   обоснования (закон проекта «чистый JS», плюс install нового ПО — решение владельца, не моё
   единоличное). Это последний рубеж на самые частые/уверенные сигнатуры, не полное покрытие.

**Что рассмотрено и сознательно НЕ построено:**
- ESLint/Prettier auto-fix хуки — потребовали бы новых npm-зависимостей + конфигурации,
  которых в проекте принципиально нет («никакого билд-пайплайна»); `node --check` даёт
  синтаксическую проверку без единой новой зависимости, этого объёма достаточно для целей.
- gitleaks (полноценный бинарник) — см. выше, установка нового ПО — решение владельца.
- Хук-«напоминалка» на полный прогон стражей без `--only=` — это решение о МАСШТАБЕ проверки,
  не деterministic факт («иногда полный прогон реально нужен») — попытка захардкодить его в
  хук либо будет постоянно мешать легитимным полным прогонам, либо ничего не поймает; уже
  прикрыто с другой стороны — лок-файл `.guard.lock` не даёт запустить ВТОРОЙ прогон поверх
  первого, что и было настоящим источником вреда, не сам факт частых прогонов.
