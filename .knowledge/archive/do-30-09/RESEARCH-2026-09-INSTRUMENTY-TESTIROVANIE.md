# Инструменты для меньшего числа багов и тестирования на разных устройствах (17.09.2026)

По прямому запросу владельца: не абстрактные принципы, а конкретные программы/приёмы,
которые снизят число ошибок и позволят проверять игру на разных устройствах лучше, чем
сейчас (сейчас — фактически один реальный Android-телефон владельца + браузерная панель
здесь). Рамка та же, что весь вечер: не тащить на платный/сложный сервис, если бесплатный
и уже доступный вариант решает задачу не хуже.

## A. Сделано прямо сейчас (без риска, без правки игровых файлов)

**`jsconfig.json` в корне репозитория** — включает для VS Code (и любого TypeScript-
инструмента) проверку типов в обычном JS БЕЗ единого билд-шага и без единой новой
зависимости — этот файл никогда не грузится игрой, не влияет на неё вообще, чисто
инструмент редактора. По умолчанию `checkJs:false` — ничего не включается массово по всей
базе сразу (иначе на 20+ больших файлах без единой JSDoc-аннотации могло бы посыпаться
тысячи шумных предупреждений). Включается ТОЧЕЧНО: строка `// @ts-check` первой строкой в
конкретном файле — тогда именно в этом файле VS Code сразу подсвечивает явные ошибки типа
(например, передал строку туда, где ожидается число/массив) прямо во время правки, до того,
как страж вообще запущен. Можно пробовать по одному файлу за раз, когда я активно с ним
работаю — не обязательство сразу на всю базу.

Источники: [Type Checking Vanilla JS with JSDoc and TypeScript](https://salomvary.com/type-checking-vanilla-js-with-jdsoc-and-typescript.html),
[VS Code supports JSDoc-powered type checking](https://www.stefanjudis.com/today-i-learned/vs-code-supports-jsdoc-powered-type-checking/)

## B. Реальный прямой доступ к отладке на настоящем телефоне владельца (Android)

Сейчас разбор живых багов идёт по скриншотам — работает, но медленно и теряет детали
(текст ошибки, состояние сети). Есть штатный, бесплатный способ получить НАСТОЯЩИЙ
Chrome DevTools прямо на реальном запуске игры в Telegram на телефоне владельца:

1. В Telegram на телефоне: Настройки → прокрутить в самый низ → 2 раза нажать и удержать
   на номере версии → появится Debug Settings → включить **Enable WebView Debug**.
   ([источник](https://pixelplex.io/blog/how-to-create-telegram-apps/))
2. Включить USB-отладку на телефоне (стандартная настройка Android для разработчиков).
3. Подключить телефон к компьютеру кабелем, на компьютере в Chrome открыть
   `chrome://inspect/#devices` — запущенная в Telegram игра появится там, открывается
   полноценный DevTools (консоль, сеть, элементы) — совсем как у меня в браузерной панели,
   только это НАСТОЯЩИЙ телефон владельца, не эмуляция.

Это не срочная задача, а штатная возможность — стоит держать в уме на случай следующего
живого бага, который тяжело понять по одним скриншотам.

## C. Лёгкий встроенный отладочный консоль — Eruda

[Eruda](https://github.com/liriliri/eruda) — маленькая бесплатная библиотека, показывает
консоль/сеть/DOM прямо ПОВЕРХ игры на телефоне, без компьютера вообще — владелец сам может
открыть и увидеть текст ошибки на своём экране, не пересказывать её словами/скриншотом.
Не предлагаю подключать сейчас без обсуждения (это правка реального игрового файла,
через макет/явное «да», как и всё визуальное) — просто держу в поле знаний как готовый
вариант на случай, если разбор багов по скриншотам продолжит буксовать.

## D. Проверка на РАЗНЫХ устройствах, не только на одном телефоне владельца

- **TestMu AI (бывший LambdaTest)** — бесплатный план без карты: 100 минут автоматизации,
  2 параллельных сессии, 2000 скриншотов — достаточно для редких точечных проверок «как это
  выглядит на iPhone/на старом Android», не для постоянного CI.
- **Firebase Test Lab** — бесплатная ежедневная квота настоящих Android-устройств в облаке
  Google, без карты для базового бесплатного использования.
- И то, и другое — именно для «глянуть разок на другом экране», не для постоянного
  автопрогона (та роль уже занята `guard.mjs`/Playwright, который уже здесь есть).

## E. ESLint — второй бесплатный слой поверх jsconfig.json, без билд-шага

[eslint.org — no-unused-vars](https://eslint.org/docs/latest/rules/no-unused-vars),
[ICS MEDIA — using ESLint effectively](https://ics.media/en/entry/260410/)

Другой класс ошибок, чем проверка типов (пункт A) — ловит неиспользуемые переменные,
недостижимый код, `==` вместо `===`, необъявленные переменные. `eslint:recommended` —
готовый набор правил «сигнал без шума», можно запускать как отдельный CLI-инструмент,
без единого билд-шага и без изменения того, как грузится игра — ровно тот же принцип, что
и у jsconfig.json. Не установлен сейчас (это новый инструмент разработки, отдельное
решение) — держу как готовый, проверенный вариант на будущее.

## F. Playwright «визуальная регрессия» — САМАЯ ценная находка этого захода, уже есть инфраструктура

[BrowserStack — Playwright Visual Regression Testing](https://www.browserstack.com/guide/visual-regression-testing-using-playwright),
[dev.to — How we catch UI bugs early with visual regression testing and Playwright](https://dev.to/subito/how-we-catch-ui-bugs-early-with-visual-regression-testing-and-playwright-5h2a)

**Важно: это не новый инструмент — Playwright уже используется в проекте (`guard.mjs`
работает именно на нём).** У Playwright есть встроенная (без сторонних сервисов, без
доплаты) проверка `toHaveScreenshot()` — делает скриншот экрана, сравнивает попиксельно
с сохранённым эталоном, явно показывает, если что-то ПОЕХАЛО визуально — даже то, что
функциональный страж (проверяет текст/классы/размеры) может не заметить, если правка
задела совсем другой, не связанный на первый взгляд экран (тот самый класс багов, который
уже несколько раз ловился только по живому скрину владельца — общий CSS-класс
непреднамеренно поехал в другом месте).

**Почему это ценно именно для этого проекта:** сегодняшний вечер несколько раз упирался
именно в это — правка одного экрана (например, `.pill`/`.pin` в Конструкторе) теоретически
могла задеть другой, использующий тот же общий класс, и узнать об этом можно было только
когда владелец заметил на своём телефоне. Скриншот-страж на ключевые экраны (Играть,
Конструктор→Карта/Цвет, Достижения и т.д.) ловил бы это АВТОМАТИЧЕСКИ при каждом полном
прогоне стражей — не заменяет функциональные стражи, а закрывает ровно тот класс багов,
которые они физически не видят (форма/цвет/расположение).

Это НЕ решение, принятое за владельца — просто отмечаю как готовую, проверенную, бесплатную
возможность на существующей инфраструктуре, ждёт отдельного явного «да», как и любая другая
правка тестовой системы.

## G. Соло-разработка — общая практика (Indie Hackers, специализированные QA-блоги)

[QA for indie game studios: a practical guide](https://gamestudiounlocked.substack.com/p/qa-for-indie-game-studios),
[Indie Game QA on a Budget](https://bugnet.io/blog/indie-game-qa-on-a-budget)

- **Масштабировать QA под РИСК, не одинаково для всего проекта** — независимое подтверждение
  того же принципа probability×impact×detectability, найденного в предыдущем заходе
  ([[RESEARCH-2026-09-AI-ENGINEERING-EKSPERTY]]).
- **Bugnet** — бесплатный уровень автоматических отчётов о падениях (стек вызовов,
  информация об устройстве) специально для соло-разработчиков — альтернатива/дополнение
  к уже существующим `js/skymail.js`/`js/blackbox.js` этого проекта. Не предлагаю менять
  существующую самописную телеметрию — просто держу в знании, что есть готовый вариант,
  если когда-то самописного решения станет не хватать.

## Вывод

Единственное, что сделано без обсуждения — `jsconfig.json` (нулевой риск, не игровой файл,
ничего не меняет по умолчанию). Всё остальное (B/C/D) — варианты, которые можно включить,
когда захочется, каждый — отдельным явным «да», как и заведено в этом проекте.
