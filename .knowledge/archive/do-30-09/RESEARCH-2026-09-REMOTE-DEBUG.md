## Часть 0. Главная находка — рамка вопроса в запросе не совсем совпадает с реальностью

Запрос сформулирован из предположения «я работаю в облаке/на сервере Anthropic, физически
разные машины — я и телефон/компьютер владельца». Это предположение **проверено прямо в этой
сессии и оказалось неточным** для среды, в которой сейчас идёт работа.

Bash-доступ этого агента — не абстракция. Живая проверка в этом же ходу:

```
$ adb devices -l
* daemon not running; starting now at tcp:5037
* daemon started successfully
List of devices attached
(пусто — ни одно устройство сейчас не подключено)

$ where adb.exe
C:\adb\platform-tools\adb.exe
C:\Program Files\platform-tools\adb.exe
```

Это означает: агент (в конфигурации «Claude Code / Claude Agent SDK desktop-приложение»,
именно в ней сейчас идёт работа) выполняет Bash **не на сервере Anthropic, а на реальной
Windows-машине** — той же, где лежит рабочая копия репозитория (`C:\Users\admin\Documents\
GitHub\cosmogram-app`, Windows 10 Pro 10.0.19045). На этой машине уже кем-то ранее
установлен Android SDK platform-tools (`adb` версии 36.0.0) — то есть либо владелец, либо
более ранняя сессия уже настраивали Android-разработку на этом самом компьютере.

Следствие: сценарий «ИИ-агент физически на той же машине, к которой подключён телефон» —
**не гипотетический, а буквально текущее положение дел**, при одном условии: телефон
владельца нужно подключить (кабелем или по Wi-Fi) именно к **этому** компьютеру — тому, на
котором открыт Claude Code. Это отдельный факт, который стоит явно спросить у владельца
(в `.knowledge/RESEARCH-2026-09-NONCODER-AI-GAPS.md` §2.2 уже отмечалось «машина на Windows»
при разборе iOS/Mac — здесь та же машина подтверждена предметно и для Android-сценария).

Это не отменяет вывод предыдущего исследования («без физического участия владельца в моменте
отладки — никак, и это правильно») — участие по-прежнему нужно. Но меняет **стоимость** этого
участия: не «раз на каждый баг открой игру, найди диагностическую строку, сфотографируй,
пришли», а «один раз подключи телефон к этому ПК — дальше живой DOM/консоль/сеть/скриншоты на
всю сессию, пока телефон подключён».

## Часть 1. Что технически возможно между агентом и реальным телефоном

### 1.1 Chrome DevTools remote debugging (`chrome://inspect`) — реалистично именно здесь

Официальный путь Google: USB debugging включается на Android один раз, дальше соединение
можно держать либо по USB, либо (Android 11+) полностью по Wi-Fi без кабеля — «Беспроводная
отладка», спаривание 6-значным кодом один раз командой **`adb pair ip:port`** (14.09.2026,
поправка после проверки: прежняя версия называла эту же команду `adb connect` — это
отдельная, ПОСЛЕДУЮЩАЯ команда для самого подключения, на другом порту, не для спаривания),
пока телефон и компьютер в одной Wi-Fi-сети (Chrome for Developers, [Remote debug Android
devices](https://developer.chrome.com/docs/devtools/remote-debugging); подробности пары —
[Android Developers, adb](https://developer.android.com/tools/adb), инструкция шаг-в-шаг —
[Gadget Hacks](https://android.gadgethacks.com/how-to/set-up-wireless-debugging-android-11-send-adb-commands-without-usb-cable-0302898/)).
Важная оговорка про VPN/AP-isolation (ниже) — практическое наблюдение, не нашедшееся дословно
ни в одном из трёх указанных источников при повторной проверке; помечаю как правдоподобную,
но не подтверждённую именно этими ссылками. Беспроводная отладка ломается VPN на любой из сторон и
AP/client isolation на роутере — если что-то не подключится, первым делом проверять именно
это, не переустанавливать всё с нуля.

**Специфично для Cosmogram — Telegram уже официально поддерживает именно этот путь.**
Официальная документация Telegram Mini Apps: включить USB-debugging на Android, в самом
Telegram — Settings → прокрутить в самый низ → 2 раза нажать-удержать номер версии → в Debug
Settings включить «Enable WebView Debug» → подключить телефон к компьютеру → на компьютере
открыть `chrome://inspect/#devices` → приложение появится в списке ([Telegram Mini Apps
Docs, Debugging](https://docs.telegram-mini-apps.com/platform/debugging)). Это ровно тот же
WebView, что рендерит игру — никакого обхода нет и не нужен.

**Дальше — конкретно для агента, не для человека у экрана.** `chrome://inspect` — это
интерфейс для человека, но под капотом он просто открывает CDP-сокет через `adb forward`.
Официальный MCP-сервер Google `chrome-devtools-mcp` документирует именно этот мостик:

```
adb forward tcp:9222 localabstract:chrome_devtools_remote
```
— и дальше MCP-сервер, запущенный с флагом `--wsEndpoint=ws://127.0.0.1:9222/devtools/browser/`,
подключается к реальному WebView на реальном телефоне так же, как к обычной локальной вкладке
([ChromeDevTools/chrome-devtools-mcp, debugging-android.md](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/debugging-android.md)).
Официальная оговорка в том же файле: «experimental feature, Puppeteer официально не
поддерживает Chrome on Android как target» — то есть путь рабочий, но не обещан на 100% для
любых версий/устройств.

Практическая тонкость: этот флаг — параметр **запуска** MCP-сервера, а не параметр отдельного
вызова инструмента внутри уже идущей сессии — то есть переключение «обычный режим (тестирую
игру в своём Chrome)» ↔ «режим отладки телефона владельца» требует перенастройки MCP-сервера
между сессиями, не мгновенного переключения посреди разговора. Обходной путь без этой
перенастройки — не трогать MCP-сервер вообще, а маленьким Bash/Node-скриптом (встроенный
`fetch`/`WebSocket` в современном Node, без новых npm-зависимостей) сходить на
`http://localhost:9222/json` за списком целей и говорить с CDP WebSocket напрямую — это и есть
официальный, задокументированный Chrome DevTools Protocol, тот же протокол, которым сам Chrome
разговаривает с `chrome://inspect`, просто без прослойки в виде MCP-сервера. Такой скрипт даёт
то же самое: live DOM, `console.log`, сетевые запросы, `Page.captureScreenshot` — то есть
настоящий скриншот с настоящего телефона, а не тот, что пришлёт владелец сам.

**Итог 1.1:** реалистично, не гипотетически — но с условием (телефон физически/по Wi-Fi
подключён к этой конкретной Windows-машине) и с оговоркой (нужен один раз пройденный чеклист
на телефоне владельца, см. Часть 3).

### 1.2 MCP-серверы и cloud-фермы устройств «дай агенту доступ к СВОЕМУ телефону через интернет»

Как и в предыдущем исследовании (§2.1 `NONCODER-AI-GAPS.md`) — прямого готового
«привяжи свой телефон к облаку, агент получает доступ» в чистом виде для тестовых ферм не
нашлось. Уточнения этого захода:

- **BrowserStack / Sauce Labs / AWS Device Farm / Firebase Test Lab** — фермы **чужих**
  устройств в облаке. У BrowserStack есть Enterprise-предложение «Private Device
  Cloud»/«Custom Device Lab» — 14.09.2026, поправка после проверки: прежняя версия утверждала
  «организация присылает СВОИ устройства физически BrowserStack» — источник этого не
  подтверждает; по факту это устройства САМОГО BrowserStack, зарезервированные эксклюзивно
  под клиента («exclusive real devices reserved on our cloud»), не устройства, присланные
  клиентом. Те же зарезервированные устройства монтируются в инфраструктуру BrowserStack и
  доступны через тот же интерфейс, что и к чужим
  устройствам ([BrowserStack, Private Device
  Testing](https://www.browserstack.com/guide/private-device-testing), [Custom Device
  Lab](https://www.browserstack.com/custom-device-lab)) — то есть технически «привязать свой
  телефон» существует, но это B2B-контракт с отправкой физического устройства в чужой
  дата-центр, а не «поставь приложение и телефон остаётся у тебя дома». Для одного владельца
  с одним телефоном, на котором он ещё и живёт (личный Telegram-аккаунт, не тестовый) — не
  подходит категорически.
- **Appium** — протокол (WebDriver поверх HTTP), не сервис; `agent-device` (Callstack) — CLI/
  MCP-обёртка для AI-агентов поверх Appium/Detox/иных драйверов, но по её же документации
  三 варианта: «свой прокси», «облачная ферма (BrowserStack/AWS/Limrun)» или «обратиться в
  Callstack за QA» ([callstack/agent-device на
  GitHub](https://github.com/callstack/agent-device)) — то есть тот же выбор между
  чужим устройством и своим протоколом настройки, ничего третьего не добавляет.
- Готовых MCP-серверов вида «свяжи МОЙ Android-телефон с облаком, агент подключается через
  интернет» (в духе того, как ngrok связывает локальный сервер с интернетом) под конкретно
  этот сценарий — не нашлось нигде на всех пяти языках. Ближе всего — комьюнити ADB-based MCP
  (`android-mobile-mcp`, `phone-mcp`), уже разобранные в §2.1 предыдущего файла с оговоркой
  про низкую оценку безопасности у одного из них (35/100). Для Cosmogram путь 1.1 (голый adb +
  официальный CDP) строго безопаснее: не устанавливает стороннего кода на телефон и не даёт
  третьей стороне произвольный shell-доступ — только forward одного порта.

### 1.3 Screen-mirroring / remote-control (TeamViewer, AnyDesk, Chrome Remote Desktop, scrcpy)

Технически и принципиально другой класс инструментов — **пиксели, не DOM**. Chrome DevTools
Protocol отдаёт агенту DOM/консоль/сеть/JS-исполнение программно; TeamViewer/AnyDesk/Chrome
Remote Desktop отдают человеку видеопоток экрана и управление мышью/клавиатурой — этого
достаточно для поддержки живого человека, но не для программного чтения `console.error` или
значения CSS-переменной. Разница подтверждена явно (ndurner, разбор нового
[Chrome-с-AI-агентами интерфейса](https://ndurner.substack.com/p/google-chrome-with-direct-ai-agents),
противопоставляющий именно CDP-доступ и pixel-only screen-sharing).

Единственное, чем screen-mirroring теоретически мог бы быть полезен здесь: если на этом же
Windows-компьютере запущено окно с зеркалом экрана телефона (например, через встроенное
Android-зеркалирование в TeamViewer QuickSupport), а не в браузере — агент **в принципе** мог
бы сделать скриншот всего рабочего стола Windows (например, через PowerShell) и увидеть
картинку телефона без участия владельца в моменте съёмки скриншота. Это не заменяет DOM/
консоль/сеть, экономит только «человек делает и присылает скриншот» — то есть уже
существующий рабочий паттерн, просто без ручного шага. Отдельная, не проверенная сейчас идея,
не рекомендация — упомянута для полноты, не тестировалась вживую.

### 1.4 Telegram Mini Apps — встроенный debug/canary-режим

Отдельного «транслируй консоль владельца куда-то, откуда её видит сторонний наблюдатель»
(аналог Metro/Flipper у React Native/Expo) у Telegram Mini Apps нет. Есть две вещи, которые
иногда путают с этим:

- **«Enable WebView Debug»** (см. 1.1) — это не трансляция, это just включение штатного
  Chrome remote-debugging сокета внутри Telegram-приложения; без `chrome://inspect`/CDP-моста
  с ним всё равно ничего не сделать.
- **Eruda / vConsole** — не платформенная фича Telegram, а сторонняя JS-библиотека,
  подключаемая внутрь самой игры (`<script>` с CDN или npm), рисует накладную консоль поверх
  страницы — владелец видит логи прямо на экране телефона, без компьютера вообще ([Eruda,
  официальный сайт](https://eruda.liriliri.io/); vConsole — официальный debug-инструмент
  WeChat Miniprograms, тот же класс инструмента). Для Cosmogram это означало бы: (а) добавить
  видимый на экране элемент в боевую игру — то есть **правка, подпадающая под правило
  «Всё визуальное — только через макет»**, не default-действие без отдельного явного
  разрешения; (б) при выключенном режиме отладки — просто мёртвый код на странице. Не
  внедрено, не рекомендуется как первый шаг именно из-за пункта (а) — но зафиксировано как
  существующий вариант на будущее, если понадобится диагностика без компьютера рядом вообще
  (например, баг воспроизводится только когда владелец физически не у ПК).

## Часть 2. Индустриальная практика — как реальные команды отлаживают баги «только на
реальном устройстве далёкого пользователя»

- **Sentry Session Replay (mobile)** — снимки view hierarchy + скриншот раз в секунду,
  сшитые в видео-сегмент, потом просматриваемые в консоли Sentry. Прямо описано как **replay
  постфактум**, не живой канал ([Sentry Docs, Session Replay for
  Mobile](https://docs.sentry.io/product/explore/session-replay/mobile)).
- **LogRocket** — единственный из проверенных инструментов, у которого есть заявленная
  **почти-живая** функция: кнопка «Go Live» появляется у активно пишущей сессии, таймлайн
  подтягивается к последним событиям с задержкой обычно «менее 10 секунд», включая живые логи
  консоли и сетевые запросы ([LogRocket Docs, Using LogRocket
  Live](https://docs.logrocket.com/docs/using-logrocket-live)). Это ближе всего в индустрии к
  запрошенному «живому доступу», но требует: (1) вшить LogRocket SDK в игру постоянно — новая
  зависимость + отправка данных сессии на сторонний сервер, что напрямую конфликтует с
  памятной записью «Telemetry: bugfix only purpose — every new BEACON field must justify
  itself» и с принципом «никакого билд-пайплайна/новых зависимостей без отдельного
  обоснования»; (2) это канал только для **читающего человека** в веб-консоли LogRocket, не
  готовый MCP/API для программного агента «зайди и прочитай DOM прямо сейчас» — то есть даже
  вшив SDK, агенту всё равно нужен отдельный мост к API LogRocket, которого готового под MCP
  не нашлось.
- **FullStory, Bugsnag** — тот же паттерн, что Sentry: recording + постфактум-просмотр,
  никакого «прямо сейчас, живьём» канала для стороннего процесса (в т.ч. ИИ-агента) не
  нашлось.
- **TeamViewer for customer support / AnyDesk** — индустриальный стандарт именно для
  «разработчик синхронно смотрит на экран далёкого пользователя с его добровольного
  согласия», но: (1) это attended-режим — пользователь должен открыть приложение и продиктовать/
  подтвердить код сессии каждый раз, никакой постоянной привязки «моё устройство ⇄ моя
  учётка» бесплатно нет (в бесплатном/личном тарифе — сессионный код, не постоянный пин); (2)
  как и 1.3 — это пиксели+управление, не DOM/консоль. Годится технически как ещё один способ
  показать экран живьём человеку-эксперту, не программному агенту напрямую.

Вывод части 2: индустрия в основном отвечает на запрос «баг только на реальном устройстве
далёкого пользователя» через **recorded replay** (Sentry/FullStory/Bugsnag) или через
**человек смотрит на пиксели живьём с согласия пользователя** (TeamViewer/AnyDesk); прямого
«программный агент получает живой DOM/консоль удалённого чужого устройства через SaaS,
без физического/локально-сетевого моста» никто не строит — и (см. вывод предыдущего
исследования) это не случайность, а сознательное ограничение индустрии по приватности.

## Часть 3. Реалистичность для владельца — что требует технической грамотности, а что можно
свести к чеклисту

Владелец — не технарь, сам ADB/ngrok не настроит. Разложение найденного по уровню сложности:

**Можно свести к «сделай эти шаги один раз по пунктам» (не требует понимания, что такое ADB):**
1. На телефоне: Настройки Android → (обычно) «О телефоне» → 7 раз нажать «Номер сборки» →
   появится «Для разработчиков» → зайти туда → включить «Отладка по USB» (или «Беспроводная
   отладка», если телефон и этот компьютер в одном Wi-Fi).
2. В самом Telegram на телефоне: Настройки → прокрутить в конец → 2 раза нажать-удержать
   номер версии → в открывшемся меню включить «Enable WebView Debug».
3. Подключить телефон к **этому конкретному компьютеру** — тому, где открыт Claude Code —
   кабелем USB (или один раз ввести код спаривания для беспроводной отладки).
4. Сказать в чат «подключил» — дальше агент сам проверяет `adb devices`, настраивает
   `adb forward`, читает живой DOM/консоль/сеть/делает реальные скриншоты.

Это реалистично для нетехнического человека **при условии**, что шаги 1–3 сделаны один раз
под диктовку с точными названиями пунктов меню (они отличаются по вендорам — Samsung/Xiaomi/
Pixel по-разному называют путь к «Для разработчиков»; шаг «сделать под диктовку» тут не
дороже, чем то, что уже применяется на других экранных задачах в проекте).

**Требует реальной технической грамотности (не отдавать владельцу):**
- Настройка `adb forward`/CDP-моста, запуск/чтение WebSocket-протокола — делает агент сам,
  не владелец.
- ngrok/туннель за пределы локальной сети (см. ниже) — не автоматизировать без отдельного
  явного разговора о риске.

**Постоянно ли телефон должен быть физически рядом с этим ПК, или подключение «через
интернет» без Wi-Fi возможно?** Технически возможно прокинуть `adb`/CDP-порт наружу через
ngrok/remote.it — тот же класс инструмента, что уже разбирался у самого Cosmogram применительно
к другим системам. Однако: (1) 14.09.2026, поправка после проверки — прежняя версия
приписывала статье Huntress конкретные утверждения про TLS и приманку для сканеров, которых
в реальной статье нет (та статья — про то, как атакующие, УЖЕ взломавшие систему,
используют ngrok для закрепления/эксфильтрации через RDP/VNC, не про голые TCP-туннели или
открытые порты вообще). Само общее опасение («открытый наружу отладочный порт — лишняя
поверхность атаки, закрывать сразу после использования») остаётся разумной технической
осторожностью, но не подкреплено именно этим источником — не выдаю за подтверждённый факт;
(2) это ровно тот класс риска, для которого в правилах Cosmogram уже действует повышенная
осторожность к «любой записи/доступу в живую внешнюю систему». Рекомендация — **не
автоматизировать по умолчанию**: если бага можно поймать, когда владелец дома на той же
Wi-Fi, что и этот ПК (обычный сценарий для «телефон + компьютер лежат в одной комнате, пока
идёт работа над игрой») — этого достаточно, и ngrok не нужен вовсе. Заводить туннель наружу —
отдельный разговор с явным «да», не default-настройка.

## Часть 4. Синтез и честная рекомендация

**Идеального «нажми одну кнопку — и я всегда вижу твой телефон живьём» не существует нигде в
индустрии** — ни у одного вендора, не только у Claude Code; это подтверждает и предыдущее
исследование, и этот заход независимо. Причина не техническая, а сознательная: постоянный
доступ ИИ к чужому устройству без синхронного участия владельца был бы дырой в приватности,
и никто в индустрии не строит это как продукт.

**Но самый близкий к «живому доступу» путь, доступный именно здесь и сейчас — реальный, не
гипотетический**: этот агент технически работает на том же Windows-компьютере, где уже
установлен `adb`. Если владелец один раз (по диктуемому чеклисту из Части 3) включит
USB/Wi-Fi debugging на телефоне + «Enable WebView Debug» в Telegram и подключит телефон к
этому ПК — агент получает официальным путём Google/Telegram (`chrome://inspect`-мостик,
`adb forward` + голый CDP) **настоящий живой DOM, консоль, сетевые запросы и реальные
скриншоты с реального телефона в реальном Telegram**, без единой строки диагностики,
добавленной в игру, и без цикла «спросил → он посмотрел → он ответил». Это не отменяет
присутствия владельца (телефон физически у него, подключение — его действие), но резко
снижает цену каждого следующего бага в рамках одной такой подключённой сессии.

**Стоит ли овчинка выделки по сравнению с уже работающим паттерном
«диагностическая строка + скриншот»?**
- Для **разового** визуального бага (как сегодняшний `safe-area-inset-top`) — та же цена:
  всё равно нужно один раз попросить владельца сделать несколько шагов на телефоне. Разница
  не в первом баге, а в том, что дальше не нужно трогать код игры и ждать нового скриншота на
  каждый следующий вопрос — можно самому покликать/поизмерять живьём.
- Для **серии** связанных с устройством багов в рамках одной рабочей сессии (что как раз
  типично для Cosmogram — «телефон vs широкий монитор», «Telegram vs браузер», разные
  устройства из `DEVICE-MATRIX.md`) — да, овчинка стоит выделки: один раз подключить телефон
  дешевле пяти циклов «правь → присылай → жди».
- **Рекомендация**: не заменять существующий паттерн полностью, а предложить владельцу
  подключение по чеклисту именно в те моменты, когда предстоит несколько итераций подряд по
  одному и тому же device-specific багу (что уже и так требует его присутствия по правилу
  «один шаг — одна проверка»/«визуальный баг под устройство — сначала доказательство»). Для
  единичных редких вопросов — оставить как есть, не создавать лишнего ритуала на каждый чих.

## Что не нашлось (честно)

- Готового официального MCP или SaaS-продукта «свяжи СВОЙ телефон с облаком, дай ИИ-агенту
  постоянный доступ через интернет, без физической/Wi-Fi близости к какому-либо конкретному
  компьютеру» — не существует нигде, ни на одном из пяти языков.
- Прямого подтверждения (или опровержения) того, что Telegram-приложение на iOS даёт то же
  «Enable WebView Debug» переключение, что на Android — в этом заходе искалось предметно для
  Android (устройство владельца — Android, по контексту задачи), iOS-путь уже разобран в
  `NONCODER-AI-GAPS.md` §2.2 отдельно (там же зафиксирован официальный обходной путь без
  Mac — `iwdp-mcp`).
- Китайских/японских/корейских источников про именно «AI-агент + adb forward + чужой Android
  WebView в реальном времени» — конкретно в этой связке материал нашёлся почти исключительно
  на английском (официальная документация Google/Telegram); незападные источники по теме
  «remote debugging Android» массово пересказывают тот же официальный ADB-путь, не добавляя
  новых техник сверх найденного на английском.
- Живого измерения задержки/стабильности связки `adb forward` + CDP именно с Telegram
  Android WebView конкретно на телефоне владельца — не проверялось вживую в этом заходе (нет
  подключённого устройства прямо сейчас, см. вывод `adb devices` выше), только подтверждена
  сама механика по официальной документации. Первое реальное подключение стоит рассматривать
  как проверку гипотезы, не как гарантированно готовое решение.
