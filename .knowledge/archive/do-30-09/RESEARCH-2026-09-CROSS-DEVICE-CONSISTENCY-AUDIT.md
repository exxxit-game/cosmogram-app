## Находки

### 1. `--sar` (safe-area-inset-right) вычисляется, но нигде не применяется — правая защита HUD от «⌄/⋮» Telegram сейчас никем не используется (`index.html:203`, `js/core.js:942-951`)

```css
/* index.html:203 */
--sar:max(env(safe-area-inset-right), var(--tg-safe-area-inset-right,0px),
          var(--tg-content-safe-area-inset-right,0px), var(--js-sar,0px));
```

```js
// js/core.js:942-951 — «Жизни за родными кнопками», часть 2 (27.08.2026)
// правый инсет Telegram часто отдаёт «мёртвый ноль» (та же беда, что и у верха) —
// назначаем честный запас 44px под кнопку «⌄»/«⋮», когда мост рядом и не в fullscreen
if (t && !cgFs && ('ontouchstart' in window) && right<24) right=44;
```

`grep -n "var(--sar)" index.html` — **ноль совпадений во всём файле**. Переменная объявлена,
JS честно считает под неё живое (или подстраховочное 44px) значение — но ни один CSS-селектор
её не читает. Единственный когда-то существовавший потребитель прямо назван в соседнем
комментарии и сам себя объясняет как снятый:

```
/* index.html:1164 */
#livesCanvas { width:66px; height:24px; margin-top:24px; }
/* свечение рисует сам canvas — только живым жизням; 28.08.2026: было margin-right (--sar) —
   владелец на устройстве: сдвиг вбок сталкивал жизни с «Расстояние»/«Плавность» по центру,
   кнопка Telegram перекрывает СВЕРХУ ВНИЗ, не сбоку. 24px — измерено владельцем на реальном
   устройстве, живой замер (cycleSadDbg) снят */
```

**Почему это находка, а не гипотеза**: комментарий сам подтверждает, что `--sar` когда-то
применялась и была снята с ЭТОГО конкретного элемента по конкретной живой жалобе («сталкивала
жизни с текстом по центру») — но взамен нигде больше не поставлена. Это не «баг никогда не
существовал», а «фикс одного столкновения тихо снял единственного потребителя защитной
переменной, не найдя ей новое место». Комментарий у `--js-sar` в `core.js` по-прежнему пишет
«Жизни в правом углу HUD остались под ⌄/⋮» настоящим временем — т.е. сам код признаёт проблему
открытой, просто механизм её решения сейчас не подключён никуда.

**Второй заход**: `grep -rn "\-\-sar\b" index.html js/*.js` — три совпадения: объявление (203),
мёртвый комментарий (1164), и диагностическая строка `skymail.js:73` (`sar:'+v('--sar')`) —
переменная попадает только в телеметрию писем об ошибках, не в вёрстку. `guard.mjs`
(`cosmogram-crew`) — `grep -in "sar\b"` ни разу не встречает переменную ни в одном из 329
стражей. Не задокументировано в `KNOWN-BUGS.md`.

**Кого это касается**: телефон в Telegram (не fullscreen, WebView без API-инсетов или с
«мёртвым нулём» у right) — правый угол HUD (счёт/жизни/телеметрия колонны, `#scorePack`,
`#topHud`) при определённых сочетаниях ширины экрана может уходить под нативную кнопку «⌄»/«⋮»
без какой-либо защиты, хотя код к этой защите готов на 90% (расчёт значения есть) — не хватает
одной строки `padding-right:var(--sar)`/`right:var(--sar)` на реальном элементе (какой именно —
решение владельца по свежему живому скрину, не додумываю).

### 2. Нет `--sal` (safe-area-inset-left) вообще — асимметрия top/bottom/right vs left, а альбомная ориентация — не гипотетический, а штатно поддерживаемый режим (`index.html`, весь файл; `js/core.js:1107-1137`)

`grep -n "env(safe-area-inset" index.html` — четыре совпадения: `-top` (160, 178), `-bottom`
(191), `-right` (203). **`-left` не встречается ни разу** — ни как CSS-переменная, ни как
inline-стиль, ни как JS-инсет (`core.js` считает `top`/`bot`/`right`, не считает `left`).

Это не абстрактный риск: `tgOrientLock()` (`core.js:1107-1137`) замыкает экран в портрет только
если игра ОТКРЫТА в портрете, и только когда мост/браузер вообще поддерживают
`lockOrientation`/`screen.orientation.lock`:

```js
// core.js:1107-1113
function tgOrientLock(){
  const portret = window.innerHeight >= window.innerWidth;
  const t=tgApp();
  if(t && tgVerAtLeast(t,'8.0') && t.lockOrientation){
    if(portret){ try{ t.lockOrientation(); }catch(e){} }
    return; // мост справился — второй замок ни к чему
  }
  // ...screen.orientation.lock('portrait') как запасной путь, тоже условный на portret
```

Сам проект уже держит целую страховочную CSS-секцию именно на случай, когда замок не сработал:

```css
/* index.html:3470-3475 */
/* ============ v1.75.0: альбомная страховка HUD ============
   Замок Telegram (core.js) не даёт экрану лечь; это — для оставшихся путей:
   открыли сразу в альбоме, старый клиент без замка, обычный браузер. */
@media (orientation:landscape) and (max-height:540px){ ... }
```

То есть landscape — задокументированный, штатно обрабатываемый (пусть и редкий) путь, а не
теоретическая крайность. У телефонов с вырезом/камерой в углу экрана (punch-hole) или чёлкой,
повёрнутых в альбом, эта деталь физически оказывается СБОКУ — слева при одном повороте, справа
при другом. Правый край хотя бы имеет объявленную (пусть и неприменённую, см. находку 1)
переменную `--sar` — левый не имеет ничего: ни объявления, ни расчёта в `core.js`, ни единого
`env(safe-area-inset-left)` в CSS. `.menuBack` (кнопка «назад» почти на каждом экране меню)
стоит на фиксированных `left:16px` (`index.html:1016`) без какой-либо поправки на инсет.

**Второй заход**: `guard.mjs` — `guardLandscapeBoot`, `guardLandscapeSpeaksTruth` (стражи о
самом появлении альбомной страховки и текста «поверните телефон») проверяют ТОЛЬКО высоту/текст
подсказки, ни один не мерит горизонтальные safe-area отступы. `guardIslandNeedsRealNotchOrFullscreen`
проверяет вырез только в портретной раскладке (`safeAreaInset.top`). Ни один из 329 стражей не
трогает `left`. Не задокументировано в `KNOWN-BUGS.md`.

**Честная оговорка о серьёзности**: это асимметрия готовности инфраструктуры (`--sat`/`--sab`
полностью подключены, `--sar` посчитан, но не подключён, `--sal` не существует вовсе), а не
подтверждённый живой скрин конкретного перекрытия — по правилу проекта «сначала доказательство
на реальном устройстве» это гипотеза о пробеле в защите, не диагноз конкретного визуального
бага. Но сам пробел (отсутствие переменной там, где её симметричные соседи есть и активно
используются) — не гипотеза, а проверенный факт кода.

### 3. Геймпад сбрасывает `input.keyL/R/U/D`, принадлежащие клавиатуре, когда его собственный стик возвращается в нейтраль — кросс-инпут «липкая честность» наоборот (`js/input.js:735-757`, опрос `render.js:5690` каждый кадр на любом экране)

```js
// js/input.js:743-753
if(!gp){ padPrev.a=padPrev.st=false;
  if(padOwn.l){input.keyL=false;padOwn.l=false;} if(padOwn.r){input.keyR=false;padOwn.r=false;}
  if(padOwn.u){input.keyU=false;padOwn.u=false;} if(padOwn.d){input.keyD=false;padOwn.d=false;}
  return; }
const ax=gp.axes[0]||0, ay=gp.axes[1]||0;
const L=ax<-PAD_DZ||btn(14), R=ax>PAD_DZ||btn(15), U=ay<-PAD_DZ||btn(12), D=ay>PAD_DZ||btn(13);
if(L){input.keyL=true;padOwn.l=true;} else if(padOwn.l){input.keyL=false;padOwn.l=false;}
if(R){input.keyR=true;padOwn.r=true;} else if(padOwn.r){input.keyR=false;padOwn.r=false;}
if(U){input.keyU=true;padOwn.u=true;} else if(padOwn.u){input.keyU=false;padOwn.u=false;}
if(D){input.keyD=true;padOwn.d=true;} else if(padOwn.d){input.keyD=false;padOwn.d=false;}
```

`padOwn` существует именно затем, чтобы геймпад не трогал флаги, которые поставил не он (сосед-
комментарий: «свои флаги помечает — чужие (клавиатура) не трогает»). Но проверка сделана только
в одну сторону: `padOwn.l` фиксируется в `true` при ЛЮБОМ кадре, где стик/D-pad влево активны —
**даже если в этот же момент `input.keyL` уже был `true` от настоящей клавиатуры** (клавиатурный
`keydown`, `input.js:826`, пишет в тот же самый флаг напрямую, без какой-либо метки владения).
Сценарий: игрок держит клавиатурное «влево» (`input.keyL=true`, клавиатура не отмечает владение
нигде), одновременно у него подключён/лежит рядом геймпад (браузер видит его после ЛЮБОГО
первого нажатия на нём, не обязательно намеренного — сам код это и объясняет: «браузер отдаёт
геймпад только после первого нажатия на нём»), и геймпад-стик/D-pad ТОЖЕ на миг случайно
отклоняется влево (`padOwn.l=true`, `input.keyL` остаётся `true` — визуально ничего не
меняется) — а затем стик возвращается в нейтраль. Следующий кадр:
`else if(padOwn.l){input.keyL=false;padOwn.l=false;}` — геймпад «отпускает» флаг, **обнуляя
`input.keyL`, хотя клавиша всё ещё физически зажата**. Руль обрывается посреди полёта без того,
чтобы игрок отпускал клавишу — источник обрыва (геймпад, не клавиатура) не соответствует
причине, которую игрок увидит на экране (палец на клавише, самолёт перестал слушаться).

Опрос происходит **каждый кадр на любом экране** (`render.js:5690`: «опрос каждый кадр — руль и
кнопки на любом экране»), не только во время полёта — то есть окно для гонки открыто всю
сессию, не только в момент старта забега.

**Почему это находка, а не гипотеза**: код читается однозначно, логика детерминирована (не
нужен живой девайс, чтобы предсказать исход — это чистая функция состояния, не сенсорный шум,
где нужна живая проверка по правилу проекта про визуальные баги под конкретное устройство).
`padOwn` — это ЯВНО признанная владельцем/автором кода необходимость разводить владение флагом
между источниками (сам факт существования структуры доказывает, что проблема «чужой источник не
должен трогать чужой флаг» уже была понята и решена — только НЕ симметрично, у клавиатуры нет
зеркальной метки владения `keyOwn`, и геймпад не проверяет её перед сбросом).

**Второй заход**: `grep -in "gamepad\|geymped\|штурвал.*клав" cosmogram-crew/tests/guard.mjs` —
единственный гейм-контроллер-страж (`guardGamepadRumblesOnEveryCollision`) проверяет вибро-
рядом-с-коллизией, не пересечение с клавиатурой. Ни одного стража на сценарий «два источника
руля одновременно» нет. Не задокументировано в `KNOWN-BUGS.md` (там есть отдельный пункт про
`elMH._t`/`_t2` — безымянные флаги другого модуля, не про это).

**Реалистичность**: узкий сценарий (нужен одновременно подключённый геймпад И активная
клавиатура — десктоп-кейс, не телефон/Telegram), но именно тот класс, который просило задание:
«переключение метода ввода посреди полёта оставляет протухшее состояние от предыдущего метода» —
здесь ровно наоборот и ровно это: НЕйтральный сигнал одного метода стирает АКТИВНОЕ состояние
другого.

## Уточнение к уже открытому исследованию (не новая находка, а сужение вывода)

### DPR-потолок (`dprCap`) не пересчитывается при переносе окна между мониторами разного DPI — `.knowledge/RESEARCH-2026-09-CANVAS2D-DESKTOP-NOUTBUK.md §2.2` закрыл вопрос слишком широко

Существующее исследование (`§2.2`, эта же неделя) разобрало ровно тот вопрос, что просило это
задание («перенос окна между мониторами с разным DPI»), процитировало MDN («`devicePixelRatio`
обновляется автоматически… можно слушать `resize`») и сделало вывод: «по устройству кода эта
ситуация уже должна закрываться без правок», с честной оговоркой «не проверено на живом
двух-мониторном стенде».

Вывод верен для ЖИВОГО `window.devicePixelRatio` (`core.js:1421`: `const nextDpr =
Math.min(window.devicePixelRatio||1, dprCap)` — читается заново на каждый вызов `resize()`, не
кэшируется, `resize()` подписан на `window.addEventListener('resize', ...)`) — но не для
`dprCap`, потолка поверх него. `dprCap` — отдельная переменная, которую считает `gfxCap()`
(`core.js:1351-1377`) из `raw = window.devicePixelRatio` **в момент своего вызова**, а не заново
при каждом `resize()`:

```
grep -n "gfxCap()" index.html js/*.js
js/ui.js:3380,3533,4649 — смена графической настройки/восстановление при загрузке
js/render.js:57,92     — авто-понижение/авто-повышение качества (порог fps)
js/core.js:1571        — самый первый вызов при старте
```

Ни одно из мест повторного вызова `gfxCap()` не привязано к `window.addEventListener('resize')`
или к `orientationchange` — то есть при переносе окна с 1×-монитора на 3×-монитор
`window.devicePixelRatio` в `resize()` честно вырастет, но в режиме `gfx:'auto'` (умолчание,
никем не тронутое большинством игроков) `dprCap` — уже посчитанный при `raw=1` на СТАРОМ
мониторе, скорее всего в нижней ветке (`t===0`/иначе `1.75`, см. `core.js:1372-1374`) — останется
прежним, пока авто-качество или ручная смена настройки его не пересчитают. `nextDpr =
min(3, 1.75) = 1.75` — игра не воспользуется более чёткой матрицей нового монитора, хотя
`devicePixelRatio` сам факт переноса честно увидел. Обратное направление (высокий DPI → низкий)
безопасно само по себе: `min()` всегда берёт меньшее, лишний запас в `dprCap` не создаёт
артефакта.

**Степень**: только потеря чёткости (картинка чуть мягче, чем могла бы быть на новом мониторе),
не поломка геометрии/вёрстки/ввода — ниже порога находок 1-3 выше, поэтому вынесено отдельным
разделом, не в общий список. Существующий research-файл стоит дополнить этой оговоркой при
следующем заходе туда же (не делаю правку сам — angle 3 читает, не пишет чужие файлы без явной
договорённости об объёме).

## Проверено и НЕ является находкой (второй заход)

- **`remapAxes()`/поворот экрана и калибровка гироскопа** (`input.js:218-224, 587`) —
  `orientationchange` вызывает `calResetDebounced(...,'orientation')`, оси гироскопа
  пересчитываются по `screen.orientation.angle`/`window.orientation` живьём на каждый пакет —
  ровно тот путь, которым и должна лечиться смена координат при повороте. Работает.
- **Переключение тач ↔ мышь ↔ клавиатура при потере фокуса/уходе курсора** (`input.js:706-723`)
  — `blur`/`mouseleave`/`visibilitychange` разом чистят мышь (`mouseRelease`), клавиатуру
  (`keysRelease`) и тач (`touchEnd`) — все три источника явно перечислены в одном и том же
  комментарии 18.09.2026 («тот же класс бага... но для касания») — уже целиком починено сегодня,
  до начала этого аудита. Не переоткрываю.
- **Тач ↔ гироскоп mid-flight** — `onTilt()` продолжает обновлять `input.tiltX/tiltY` фоном,
  даже пока палец рулит (ветка `touchX!=null` в `game.js` просто не читает их) — когда палец
  отпускают, гироскоп подхватывает уже свежим значением, не протухшим. Работает как задумано.
- **PWA install/update, первая установка vs апдейт** (`sw.js`, регистрация в `index.html:5134-

## Честный итог

Три реальные находки, все — конкретные пробелы в коде (не устройство-специфичные гипотезы,
кроме честной оговорки у находки 2), плюс одно уточнение к уже открытому research-выводу той же
недели (`dprCap` не то же самое, что живой `devicePixelRatio` — существующий вывод «уже
закрыто» верен только частично). Находка 1 (`--sar` посчитан, но не подключён) и находка 3
(геймпад стирает клавиатуру) — чистое чтение кода, воспроизводимо без живого устройства.
Находка 2 (нет `--sal` вообще) — структурный пробел, подтверждён отсутствием переменной/кода,
но требует живого альбомного скрина с реальным вырезом слева для перевода из «пробел защиты» в
«подтверждённый визуальный баг», как и требует правило проекта про устройство-специфичные баги.
Полей, где было МНОГО кода и НИЧЕГО не нашлось (поворот экрана+гироскоп, тач↔мышь↔клавиатура на
blur, PWA install/update, видео через SW) — большинство, потому что сегодняшняя серия правок
(18.09.2026, «делай», «сквозная проверка») уже прошлась по значительной части этого же
пространства перед стартом этого audit-захода.
