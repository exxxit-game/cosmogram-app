# Исследование: как сделать методику поиска багов на порядок лучше (13.09.2026)

> Источник: 5 параллельных исследовательских агентов, каждый копал свой угол на
> нескольких языках (английский + минимум 2 из русского/японского/китайского/
> корейского/немецкого/французского/испанского). Задача владельца: «сделать подход
> самым передовым... подумай очень хорошо, что нужно улучшить или добавить».
> Текущая база: `tests/guard.mjs` (~220 стражей, Playwright/Chromium, локально,
> без CI), `tests/tesnota.mjs` (обход экранов по вьюпортам), BEACON-телеметрия
> (`js/skymail.js`) + Supabase.

## Итог: пять углов, что реально нашлось

1. **Визуальная регрессия канваса** — Playwright Clock API + pixelmatch (оба УЖЕ
   внутри Playwright, ничего ставить не нужно). Проблема: не замораживает
   requestAnimationFrame-анимацию канваса сама по себе — нужен свой хук.
2. **Fuzzing/monkey-testing** — случайные тапы+таймингы через page.evaluate,
   без новых зависимостей. fast-check (property-based) — единственная НОВАЯ
   библиотека во всём исследовании, и то опционально, только в tests/.
3. **Телеметрия → находка багов сама** — сейчас BEACON шлёт письмо на КАЖДЫЙ
   репорт; Sentry/Tencent CrashSight группируют по fingerprint, шлют раз.
4. **Кросс-устройства** — в guard.mjs УЖЕ разбросаны 6+ вьюпортов ad hoc
   (никем не названных) — сначала навести порядок в существующем, не изобретать.
5. **ИИ как второй ревьюер** — свежий агент БЕЗ общего контекста с тем, кто писал
   код, явно спрошенный про конкретные классы багов (не «проверь на баги» вообще) —
   реально ловит то, что генерик-промпт пропускает (яп. источник: 0 из 2 багов
   на генерик-промпте → 2 из 2 на явном «проверь параллельность»).
6. **UX-занозы и доступность** — размер тач-зон (44×44), обрезание текста в
   5 языках, контраст ВНУТРИ канваса (axe-core канвас не видит вообще) —
   всё это можно автоматизировать поверх уже существующего tesnota.mjs.
7. **Память/производительность** — в guard.mjs УЖЕ есть один страж (108,
   guardFrameCostsNothingExtra), проверяющий что спрайт кэшируется, а не течёт
   при ресайзе — это правильный паттерн, просто разовый, не общий. Развернуть
   его в переиспользуемый инструмент: счётчик DOM-узлов/слушателей до/после
   20 кругов «полёт→меню» (не сырые байты кучи — они шумные между прогонами),
   плюс обёртка методов CanvasRenderingContext2D счётчиками вызовов (ловит
   утечки, которые не видны в JS heap — WebGL/canvas-память живёт частично
   в GPU/native-памяти драйвера, невидимой для performance.memory). CPU-throttling
   через CDP — годится ТОЛЬКО как относительный сигнал «стало медленнее, чем
   в прошлом коммите», не как доказательство реального поведения на Redmi 9A
   (тепловой троттлинг реального железа не воспроизводится статическим
   множителем — кит. кейс Tencent WeTest: 47→16.9 fps от перегрева, чего
   throttling не поймает).

## Приоритизированный список (что добавлять и в каком порядке)

### Уровень 1 — почти бесплатно, ничего нового не ставить, делать первым
1. Страж со случайными тапами/таймингами на реальном полёте — ловит NaN/краши,
   которые никто не догадался явно затестить.
2. Страж размера тач-зон + пересечения интерактивных зон — переиспользует цикл
   экранов/вьюпортов из tesnota.mjs, порог 44×44px.
3. Страж обрезания текста во всех 5 языках — переиспользует существующий
   SUPPORTED_LANGS-цикл, проверка scrollWidth<=clientWidth.
4. Свежий агент-ревьюер перед показом владельцу — с явным чек-листом классов
   багов (переиспользованная переменная, не обновлённое второе место вызова,
   инвертированное условие, off-by-one), не генерик «проверь код».
5. Канвас-диффинг через Playwright Clock API + pixelmatch, с заморозкой RNG
   игры через уже существующий seed-механизм (Speedrun SSG).
6. Обёртка методов CanvasRenderingContext2D (createLinearGradient/save/restore
   и т.п.) счётчиками вызовов — расширение уже существующего паттерна стража
   108 на весь render.js, без CDP, без новых зависимостей.

### Уровень 2 — недорого, но требует немного настройки
6. SQL-дедупликация BEACON-репортов по fingerprint (signal+context), письмо
   только на новый/каждый десятый повтор — не читать один баг 500 раз.
7. ✅ СДЕЛАНО (13.09.2026, страж 198) — именованная матрица вьюпортов
   (`VIEWPORTS` в guard.mjs, 7 имён, все значения — уже использовавшиеся в
   файле литералы, не выдуманы заново) + широкий страж по HUD (#scorePack/
   #topHud не срезаны за край, не перекрываются) на всей матрице разом.
8. Контраст-сэмплер для отрисованного на канвасе текста/иконок (getImageData +
   формула WCAG) — единственный способ проверить контраст ВНУТРИ канваса.
9. Счётчик DOM-узлов/слушателей до/после 20 кругов «полёт→меню» (Performance.
   getMetrics() через уже используемый в guard.mjs CDP-сеанс) — ловит утечку
   «старый экран не убрал за собой DOM/слушатели».
10. Страж долгих задач (PerformanceObserver('longtask') во время синтетического
    N-секундного полёта, сумма превышений — прокси Total Blocking Time).

### Уровень 3 — на будущее, когда дешёвые находки иссякнут
9. fast-check для геометрии/физики (property-based, авто-минимизация примера).
10. Mutation testing (Stryker, раз в несколько недель) — находит не баги, а
    ДЫРЫ в существующих стражах (страж проходит, но не проверяет то, что думает).
11. Статистические аномалии (z-score) по fps/frame-time между сборками.
12. Delta-debugging — автоматическое сжатие упавшей случайной последовательности
    до минимального воспроизведения (строить только после того, как п.1 реально
    что-то нашёл).

### Сознательно НЕ делать сейчас
Percy/Chromatic/BackstopJS/reg-suit (SaaS или дублирующий инструмент), облачные
device farms сверх бесплатного пробного тарифа, готовые автономные ИИ-браузер-
агенты (у нас уже есть тот же Playwright под рукой), Applitools-класс платформы,
ML-кластеризация крэшей (KabOOM-класс — преждевременно при таком объёме).

## Дополнение (второй заход, 13.09.2026): как ловить СВОИ ошибки за секунды

Владелец справедливо указал: список выше — про то, как находить БОЛЬШЕ багов в уже
написанном коде. Он не отвечает на другой, более острый вопрос: как не терять час
на разматывание СВОЕЙ ЖЕ ошибки прямо во время работы (как сегодня с обрезанным
game.js). Отдельное исследование это подтвердило и нашло прямые прецеденты у других
ИИ-агентов (GitHub issue anthropics/claude-code#52881 — Edit-tool молча обрезает файл;
Zhihu — агент удалил 28 745 строк в 340 файлах и НАПИСАЛ правдоподобный отчёт об успехе;
Habr — агент удалил 700ГБ, переиспользовав одну переменную для «что проверяем» и «что
удаляем»). Урок один и тот же везде: опасная часть скрипта обычно написана верно —
ломается именно «безопасная»/соседняя часть, туда внимание само по себе не идёт.

**Новое правило (записано в память отдельно):** после ЛЮБОЙ скриптовой массовой правки
файла — `git diff --stat` ПЕРВЫМ действием (одна строка, `-1600` видно мгновенно),
плюс проверка размера/числа строк, встроенная В САМ СКРИПТ (не отдельным шагом после),
плюс `node --check` (обязательно, но НЕ достаточно — обрезанный файл часто синтаксически
валиден). Для по-настоящему крупных правок — писать во временный файл, проверять, потом
атомарно переименовывать, а не редактировать боевой файл на месте.

**Побочная находка (охват регионов вне уже опрошенных языков):** практики бразильских
инди-разработчиков и польских/турецких/итальянских инди-сообществ сходятся почти дословно
(Discord-плейтесты, itch.io как биржа тестеров, тиры багбаунти) — отдельной «региональной
философии QA» не нашлось. Два реально новых пункта: бразильская эвристика «намеренно
сочетай две механики, тестированные по отдельности, друг с другом и с краями коллайдера —
баги живут на стыках» (простой чек-лист для ручной проверки/написания стражей); модель
Crowdin — фанаты голосуют за переводы + доверенный «Proofreader»-фильтр — годится, если
когда-нибудь появятся сторонние переводчики (сейчас i18n.js ведут только владелец и я).

## Дополнение (третий заход, 13.09.2026): пять углов, о которых ещё не спросили

Владелец: «переверни весь интернет... с разных углов и взглядов» — доисследовал то,
что первый заход не покрывал вообще.

**Безопасность/анти-чит** (в игре настоящая валюта — звёзды и Stars). Реальный
прецедент: у Megabonk (Steam) читеры залили таблицу лидеров невозможными очками —
почин не «продвинутый анти-чит», а обычная серверная проверка диапазона. Корейский
LINE-инженерный блог: сверяют WIN-лог с детальным лог-полётом (WIN без трассы —
подделка), засекают прохождение уровня за 5 секунд. Ранжированные стражи для
guard.mjs: (1) дублирующий/параллельный запрос на награду — Promise.all по одному
и тому же claim, должен начислиться РОВНО один раз (самый ценный — это ровно тот
класс гонки, что ломал реальные игры и платёжные системы); (2) невозможный счёт —
отправить значение выше физически достижимого, ждать отказ сервера; (3) подменённый,
но «похожий на подписанный» payload; (4) просроченная initData-подпись (AUTH_MAX_AGE_SEC
уже настроен под эту же угрозу — стоит стража, чтобы будущая правка константы не
расширила окно молча); (5) отрицательный/избыточный расход звёзд.

**Статический анализ без билд-пайплайна.** `npx eslint` с одним flat-config файлом
(no-undef ловит именно утечку в глобалы — актуально, т.к. без модулей все script-теги
делят один namespace), кастомный HTML-парсер (parse5/html-validate) вместо ручного
подсчёта тегов (прямая связь с уже пойманным багом — пропавший `</div>` прятал
экраны), `tsc --checkJs` точечно на 2-3 самых рискованных файла через `@ts-check`,
не на весь проект сразу (шум на нетипизированном легаси-коде — подтверждено
японским источником). `jscpd` — детектор копипаста, ловит «фикс применили к одному
месту вызова, ко второму — нет».

**Масштабирование стенда стражей** (223 сейчас, будет больше). Пул с ограничением
параллелизма поверх уже существующего паттерна «свой контекст на каждый страж» —
без переписывания на @playwright/test, без новых зависимостей, ~10-15 строк.
Явный список «известно нестабильных» стражей вместо памятки в файле. Тайминг
каждого стража в отчёте — чтобы видеть, что на самом деле медленно.

**Фрустрация игрока** (не баг, а «неприятный момент», прямо названный владельцем).
Двух новых событий достаточно, оба ложатся на уже существующие blackbox.js/
skymail.js: (1) «смерть в одном и том же месте 3+ раза за сессию» (тот же bucket
по mode+mission+округлённой дистанции); (2) «вышел из игры в течение 5с после
смерти» — комбинация двух вместе превращает шумный сигнал в настоящий. Требует
осторожности — телеметрия в проекте принципиально только для починки багов,
не превращать в трекинг ради трекинга.

**Как самому агенту (мне) ловить свои ошибки быстрее.** Официальный гайд Claude
Code (code.claude.com/docs/en/best-practices) называет именно то, что случилось
сегодня, «trust-then-verify gap» и прямо рекомендует то же лекарство, что уже
записано в память: доказательство вместо самоотчёта, встроенное в сам шаг правки,
а не отдельной проверкой после. Плюс Writer/Reviewer: свежий агент без памяти о
том, как писался код, ревьюит именно дифф — ловит слепые пятна пишущего контекста.
«Правило пяти попыток» проекта — тот же паттерн (bounded autonomy), что описан
независимо, не изобретение задним числом.

## Аудит честности начислений (13.09.2026, четвёртый заход)

После того как в `cosmogram-beacon` появилась денежная тревога (SEVERE_RE/
регресс — см. `js/beacon` часть кода и сам Edge Function), владелец спросил
«найди что-то ещё полезное» — логичным продолжением оказалось не строить
сигнализацию дальше, а проверить сам замок: 5 классов уязвимостей из
предыдущего исследования (дубль-клейм, невозможный счёт, подделанная
подпись, replay старой подписи, отрицательный баланс), которые раньше были
только идеей, не сверенной с реальным кодом. Сначала агент прочитал все
Edge Functions (`cosmogram-sync`, `cosmogram-daily`, `cosmogram-workshop`,
`cosmogram-beacon`) читай-только, затем я лично перепроверил его выводы
через прямой SQL-доступ к живой базе (agent не имел доступа к Supabase MCP
в своей среде) — тела RPC/триггеров и текущие значения config, которые
агент явно пометил «не проверено».

**Закрыто, подтверждено кодом+живой БД:**
- Дубль-начисление за один и тот же платёж Stars — `UNIQUE(telegram_charge_id)`
  в `premium_purchases`, код 23505 трактуется как «уже записано» (`cosmogram-sync`).
- Подпись Telegram initData/webAuth/сессии — настоящий HMAC-SHA256,
  XOR-сравнение без раннего выхода (устойчиво к timing-атаке), применяется
  системно перед каждым денежным/рекордным действием во всех проверенных функциях.
- Replay одного и того же забега — `public.check_and_use_nonce()` (тело
  прочитано напрямую): atomic insert в `used_nonces` с обработкой
  unique_violation — настоящая, не воображаемая защита.
- Понижение чужого рекорда гонкой двух запросов — `public.scores_guard()`
  (тело прочитано напрямую), триггер BEFORE UPDATE на `scores`: `if NEW.best
  < prev then NEW.best := prev` — рекорд физически не может уменьшиться,
  independent от порядка выполнения параллельных запросов. Плюс потолок
  прироста за одну запись (`step`) и абсолютный потолок (`cap`) — тем же
  триггером. Прямой доступ (`information_schema.role_table_grants`) к
  таблицам `scores`/`daily_runs`/`speedrun_runs`/`slalom_runs`/`biathlon_runs`
  у `anon`/`authenticated` отсутствует полностью — записать может только
  Edge Function (service_role), в обход Edge Function дыры нет.
- Отрицательный игровой баланс (✦) на сервере — `clampInt(raw.wallet, 0,
  100_000_000)` в `cosmogram-sync`, нижняя граница держит честно.
- Реальные деньги (Telegram Stars ⭐) — цена берётся ТОЛЬКО из серверной
  `PREMIUM_SKINS`, не из тела запроса игрока; само списание и его
  подтверждение — на стороне Telegram, локально подделать нечего.

**Открыто, подтверждено — два реальных пункта:**
1. **`cosmogram-daily` (Небо месяца/Спидран/Слалом/Биатлон) не проверяет
   физическую достижимость результата.** `cosmogram-sync` (основная таблица)
   сверяет счёт/дистанцию со временем забега (`score > sec*RATE_SCORE...`);
   `cosmogram-daily`'s `daily_submit`/`speedrun_submit`/`slalom_submit`/
   `biathlon_submit` только отсекают по фиксированному потолку диапазона
   (`SCORE_CAP`), без привязки ко времени — `time_sec:0.001` для Спидрана
   пройдёт как есть. Триггеров на `daily_runs`/`speedrun_runs`/`slalom_runs`/
   `biathlon_runs` в живой БД НЕТ (проверено `information_schema.triggers`) —
   единственная защита этих 4 таблиц — код внутри самой функции, и там её
   для времени/физики не оказалось.
2. **`config.replay_guard_strict` отсутствует в живой таблице `config`**
   (проверено `SELECT key,value FROM config WHERE key IN (...)` — вернулась
   только `score_strict='1'`). Код трактует отсутствие строки как «не
   strict» — значит клиент, не отправляющий `nonce`, сейчас реально (не
   гипотетически) не защищён от replay в течение окна свежести initData
   (5 минут) или срока сессии (7 дней, если использован `tgSess`). Это не
   баг кода — это включённое по умолчанию мягкое состояние, которое можно
   закрыть одной строкой в `config`, если владелец решит, что старый клиент
   без nonce уже не нужен.

**Побочная находка, не из пятёрки:** `cosmogram-beacon` не проверяет
initData вообще (осознанно — телеметрия до входа), и лимитер (`"beacon:"+anon`)
ключуется клиентским тегом, который клиент полностью контролирует — то есть
канал только что построенных денежных тревог (SEVERE_RE) можно тривиально
завалить поддельными «явлениями» нужного рода с разными anon-тегами и
вызвать ложные тревоги у владельца. DoS на систему алертинга, не финансовая
дыра — отдельный класс, стоит знать в контексте только что сделанной работы.

**Обновление (тот же день, после «исправляй всё по одному»):** пункты 1 и 2
закрыты. (1) `cosmogram-daily` — три дисциплины (Спидран/Слалом/Биатлон)
теперь отклоняют физически недостижимое время: нижняя граница построена не
из новой выдуманной формулы, а переносом уже владельцем утверждённых
RATE_SCORE=2000/RATE_DIST=120 из `cosmogram-sync` на фиксированные цели
трасс из `game.js` (SR_GOAL/SLALOM_DIST/BIATHLON_DIST) — числа не новые,
конкретику не додумывал. Страж 199 (`guard.mjs`) сверяет, что константы не
разошлись с первоисточниками. `daily_submit` («Небо месяца») остался
незакрытым — клиент не шлёт время забега вообще, нужна правка формата
посылки, отдельная задача. (2) `config.replay_guard_strict` включён (`'1'`)
— проверено, что текущий клиент (`js/ui.js`) всегда шлёт `nonce`, поэтому
включение не задевает ни одного честного игрока. Побочная находка про
`cosmogram-beacon` (DoS на канал алертинга) осталась не исправленной,
статус прежний.

**Порог тишины для регресса тоже больше не черновой.** `REGRESSION_QUIET_DAYS`
был поставлен как моё собственное черновое значение (7) при первом деплое —
без подтверждения, вопреки правилу «не додумывать конкретику». Задан явный
вопрос с вариантами (3/7/14/своё число), владелец выбрал **3 дня** —
задеплоено, сверено, живой вызов подтвердил.
