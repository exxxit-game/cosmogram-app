# Дифференциальная диагностика багов — частотная таблица по первопричинам (25.09.2026)

> Метод не изобретён с нуля — перенос двух реальных источников на свои же данные:
> дифференциальная диагностика в медицине (ранжировать конкурирующие гипотезы по
> частоте ДО проверки, не проверять в случайном порядке) и советская школа
> технической диагностики (Пархоменко, ИАТ АН СССР — минимальная последовательность
> проверок для локализации неисправности). Источник данных — не мнение, а честный
> подсчёт по `KNOWN-BUGS.md` (983 строки, ~80 записей) и `ERROR-CATALOG.md` (88
> строк, законы К1–К18), прочитанным целиком одним агентом, без выборки.

## Таблица — что проверять первым, по убыванию частоты

| Категория первопричины | Раз | Что проверить первым |
|---|---|---|
| **Устаревшая запись — баг уже починен в живом коде, трекер не обновлён** | **~25** | Прежде чем диагностировать — сверить текущее живое поведение/код с тем, что описывает запись. Высокий шанс, что закрыто более поздней правкой, просто не помечено. |
| Пробел в серверной валидации клиентских данных (анти-чит) | 9 | Есть ли у конкретной Edge Function реальная проверка правдоподобия значения, а не только `clampInt` по диапазону. |
| Жалоба не воспроизведена / нет улик с конкретного устройства | 5 | Сначала точное устройство/версия/шаг — подтвердить, что код вообще выполняется в этом контексте, не чинить по правдоподобной гипотезе из чтения кода. |
| Пробел в i18n/наполнении (нет перевода/названия/факта) | 5 | Проверить конкретный массив словаря на запись для этого id/языка — не искать баг рендера там, где просто нет данных. |
| Инструмент измерения сам был сломан/вводил в заблуждение | 5 | Неожиданно плоский/нулевой результат живого теста — сначала заподозрить сам замер (устаревший API, неверный ключ Store), не делать вывод «бага нет». |
| Ложная тревога — свой ранний вывод/внешняя критика не подтвердились живьём | 5 | Получить свежее живое число/скриншот СЕЙЧАС, прежде чем принимать чужой или собственный более ранний вывод как факт. |
| Правка не докатилась до всех «сестёр» (другая Edge Function/пункт каталога/репо) | 4 | Грепнуть по всем «братьям» того же семейства — почти наверняка нужно чинить не в одном месте. |
| Проглоченная ошибка (пустой catch, деструктуризация только `{data}`) | 4 | Искать место, где ошибка технически возвращается, но код её не читает — чаще объясняет «ничего не произошло», чем логика игры. |

## Длинный хвост (1-2 раза, отдельного быстрого правила не заслуживает)

Версионный порог Telegram Bot API блокирует функцию на старом клиенте (2); Service
Worker отдаёт устаревший контент (2 записи, но обе доказаны напрямую живым тестом —
по глубине недооценены самим счётом); источник времени в анимации без масштабирования
на `dt` (2); остальное — по одному разу (полный список в записи агента, не дублируется
здесь, чтобы не раздувать файл).

## Не диагностируемые баги

Часть записей `KNOWN-BUGS.md` — честно описанный design-gap/housekeeping backlog, не
воспроизводимый баг с механизмом (несогласованные потолки дистанции, единый тумблер
вибро без разделения по событиям и т.п.) — не пытаться натянуть их на категорию выше.

## Как использовать

При новом баге — перед тем как переходить к шагу 3 `bugfix`-скилла (ранжированные
причины), сначала пройти эту таблицу сверху вниз как чек-лист: совпадает ли симптом
с одной из частых категорий, начиная с самой частой (устаревший трекер). Не заменяет
`.knowledge/KNOWN-BUGS.md`/`ERROR-CATALOG.md` — дополняет их этим срезом «что чаще
всего оказывается настоящей причиной», которого сами файлы не показывают.
