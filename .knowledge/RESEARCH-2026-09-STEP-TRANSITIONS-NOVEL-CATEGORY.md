## РАЗДЕЛ А — переходы/анимация между единственным видимым шагом (мобильный контекст)

### А.1 Реальные паттерны перехода экран-к-экрану на мобильном

**iOS (Apple Human Interface Guidelines, официальный источник, содержание подтверждено
зеркалом-конспектом, не удалось получить сырой JS-рендер напрямую)**:
push-переход — новый экран **въезжает справа налево**, предыдущий уходит влево;
пространственная метафора — «глубже в иерархию = направо», «назад = налево».
Это ЖЁСТКО завязано на иерархическую навигацию (список → деталь), не на линейный
визард с фиксированным числом шагов — прямого 1:1 переноса на «шаг 1 из 3» нет, но
направление (вперёд — вправо, назад — влево) остаётся валидным языком.
— https://developer.apple.com/design/human-interface-guidelines/navigation-and-search
(конспект-зеркало с цитатами: https://codershigh.github.io/guidelines/ios/human-interface-guidelines/interaction/navigation/index.html)
Уверенность: высокая на факт паттерна, средняя на точность цитаты (зеркало, не сырой HIG).

**Material Design 3 (Google, официальный источник m3.material.io — контент не
рендерится в fetch-инструменте, поэтому ниже — через вторичные, но технически точные
источники: официальные Android Developers codelabs и открытый код
`material-components-android`)**:
Три паттерна перехода, официально названные и задокументированные:
- **Container Transform** — один элемент (карточка, FAB, чип) физически
  морфирует/растягивается в контейнер следующего экрана — это и есть формальное
  название «shared element transition» / «hero animation» у Google.
  Примеры из документации: список → страница деталей, FAB → тулбар, чип → плавающая
  карточка.
- **Shared Axis** — переход между экранами со **связью по иерархии/последовательности**
  (ровно наш случай «шаг 1 → шаг 2 → шаг 3») через общий сдвиг по оси X/Y/Z:
  вперёд = сдвиг в одну сторону, назад = сдвиг в другую (для X: вперёд — контент
  уходит влево, для Y: вперёд — вверх); каждая пара переходов обязана согласованно
  использовать один и тот же `forward`-флаг, иначе анимация «рассинхронизируется».
- **Fade Through** — для экранов БЕЗ прямой связи (не наш случай).
— https://developer.android.com/codelabs/material-motion-android ,
https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md ,
https://blog.stylingandroid.com/material-motion-shared-axis/
Уверенность: высокая (официальная терминология Google, широко переиздана в codelabs).

**Практический вывод для Конструктора**: Карта → Цвет → Сохранить — это именно
случай **Shared Axis**, а не Container Transform целиком (нет одного визуального
объекта, который морфирует через все три шага) — но ВНУТРИ перехода могут быть
точечные Container Transform-моменты (см. А.2).

### А.2 Shared element transition / hero animation — когда уместно, когда избыточно

**Формальное определение (Google, Container Transform)** — переход создаёт видимую
связь между двумя разными UI-элементами, «бесшовно трансформируя один элемент в
другой»; типовые случаи — карточка списка → страница деталей.
— https://developer.android.com/codelabs/material-motion-android

**Технические требования, без которых эффект ломается (Web Animation Patterns,
практический источник по View Transitions API, содержание технически совпадает с
Android-реализацией)**: у элемента должно быть стабильное «имя перехода»
(`view-transition-name` / shared element tag) на ОБОИХ экранах, и одинаковый
`backgroundColor` морфящегося контейнера — иначе браузер/платформа откатывается на
обычный кросс-фейд, и «сквозная нить» для взгляда пользователя теряется.
— https://animationpatterns.art/animations/shared-element-layout-transition/
Уверенность: средняя (практический источник, не официальный стандарт, но совпадает
с официальной механикой Android).

**Когда shared element уместен (сквозная линия из трёх источников — Google, китайский
UED-обзор vivo, независимо друг от друга)**:
1. Есть один смысловой «фокусный элемент», который пользователь должен продолжать
   узнавать после перехода (например: превью корабля/неба, которое видно на Карте,
   Цвете и Сохранении одинаково).
2. Элемент один, не несколько одновременно — «слишком много независимо двигающихся
   элементов рассеивает внимание» (vivo UED, практический вывод, не академический):
   держать число самостоятельно анимирующихся объектов на переходе минимальным.
3. Траектория фокусного элемента не должна пересекаться с траекториями остальных.
4. Если старый и новый элементы визуально сильно различаются — уместнее СМЕСТИТЬ по
   времени угасание уходящего и появление нового (не одновременно), чтобы не создавать
   визуальную кашу, а не пытаться их «слить» одной шейповой трансформацией.
— вторичный, но подробный разбор (企业 UED, vivo, площадка «人人都是产品经理»,
практика, не наука): https://www.woshipm.com/ucd/5740180.html
— официальная база терминов (Google): https://developer.android.com/codelabs/material-motion-android

**Когда shared element избыточен/вреден** — прямого «списка запретов» от Google/Apple
не нашлось (честный пробел), но сходящаяся рекомендация из нескольких источников:
- Material Design формулирует общий принцип уровнем выше конкретных паттернов:
  движение должно «информировать, а не отвлекать», использоваться экономно —
  это рамка, под которую подпадает и избыточный hero-эффект (источник вторичный,
  переиздание Material Motion принципов в нескольких codelabs/статьях, не найдена
  одна точная официальная страница с явным «не используйте hero здесь»).
- Практический критерий из Android-реализации: если у элемента НЕТ стабильной
  «идентичности» между экранами (это не тот же смысловой объект, а просто визуально
  похожий) — Container Transform создаёт ложную связь и вводит в заблуждение, лучше
  Shared Axis/Fade Through.
Уверенность: средняя — вывод собран из нескольких инженерных источников, а не из
одной декларативной страницы «anti-pattern».

### А.3 «Этот шаг завершён, работу нельзя потерять» — без слов, реальные примеры

**Формы/чек-ауты — базовый визуальный язык (широко задокументированная практика,
не одна конкретная компания)**: пройденный шаг — заливка сильным цветом + галочка,
текущий — выделен, будущие — нейтральный/приглушённый тон; галочка обычно
отрисовывается **обводкой линии** (stroke-dashoffset), то есть штрих физически
«дорисовывается» на глазах, а не появляется одним кадром — это и есть визуальное
«подтверждение», а не украшение.
— https://animationpatterns.art/animations/success-check-path-draw/ ,
https://www.uxpin.com/studio/blog/design-progress-trackers/
Уверенность: высокая (сходящийся паттерн, широко переиздан).

**Реальный, поимённый пример из банкинга — Monzo**: онбординг явно сообщает
«We'll save your progress as you go» и после раздела показывает **«That's 1 section
down, 3 to go»** — то есть у них это НЕ чисто безмолвно (есть микротекст), но структура
именно такая: числитель/знаменатель + утвердительная фраза сразу после завершения
шага, а не абстрактный прогресс-бар без слов.
— https://craftinnovations.global/banking-onboarding-best-practices-revolut-nubank-monzo/
Честная оговорка: это вторичный агрегатор-статья, а не официальный Monzo design-blog —
факт существования фразы подтверждён, но точная формулировка могла быть перефразирована
источником.

**N26** — прогрессивное раскрытие: не спрашивают весь профиль сразу, вводят
следующие функции (цели накоплений, бюджетирование) только после того, как человек
уже начал пользоваться базовым — это ближе к «шаг завершён = разблокирована следующая
дверь», чем к чек-листу.
— https://craftinnovations.global/banking-onboarding-best-practices-revolut-nubank-monzo/
Уверенность: средняя (тот же вторичный источник).

**Настройка нового устройства (аудитория «буквально все», включая пожилых)** —
Android Setup Wizard / iOS Setup Assistant: честный пробел — НЕ нашлось описания
конкретных визуальных средств (галочка/свечение) на уровне официальной документации
или разборов дизайна именно этих экранов; найдены только общие описания процесса
(«guides users through initial device configuration»), без деталей визуального языка
завершения шага. Отдельно подтверждено исследованиями по пожилым пользователям:
**большая зелёная галочка / красный крестик** как базовый принятый/отклонённый статус —
это єдиный конкретный визуальный факт, который нашёлся именно для аудитории «дети —
взрослые — пожилые».
— https://www.toptal.com/designers/ui/ui-design-for-older-adults
Уверенность: низкая на специфику Setup Wizard/Assistant (честно не нашлось), средняя
на «зелёная галочка / красный крестик» как универсальный accessible-паттерн.

**Итог для А.3**: подтверждённый, воспроизводимый БЕЗ-СЛОВный язык завершения шага —
(1) заливка сильным/акцентным цветом уже пройденного пункта прогресса, (2) галочка,
отрисовывающаяся линией, а не всплывающая, (3) визуальная смена состояния «активно
редактируется» → «зафиксировано» (приглушение/уменьшение интерактивных элементов
пройденного шага). Прямого академического источника именно про «глоу/свечение» как
специфический сигнал завершения — не нашлось, это дизайнерский приём без явной
цитируемой базы (честно помечаю, не выдаю за находку).

## РАЗДЕЛ Б — честный поиск структурно новой категории

Ниже — по каждому направлению, которое запросил владелец: что реально нашлось,
с какой уверенностью, и не является ли это просто вариацией уже описанных категорий.

### Б.1 Мультишаговая настройка ЧЕРЕЗ мини-игру, а не форму — **самая сильная находка раздела**

**Calibration Games (Flatla, Gutwin, Nacke, Bateman, Mandryk; UIST 2011, ACM,
рецензируемая публикация)** — формальная академическая работа именно про то, что
попросил владелец: конфигурация системы **не через меню параметров, а через игровой
акт**, из которого параметр вычисляется косвенно. Ядро идеи: интерактивные системы
часто требуют калибровки (цветовые пространства, ввод/вывод, чувствительность), но
сами процессы калибровки скучны и люди их избегают — авторы предлагают методику
превращения калибровки в игру и **дают проектные гайдлайны, которые сопоставляют типы
калибровки → базовые задачи → конкретные игровые механики** (не абстрактно, а как
таблицу переносимых паттернов).
— https://dl.acm.org/doi/10.1145/2047196.2047248 (DOI: 10.1145/2047196.2047248)
— цитируемость и разбор: https://www.researchgate.net/publication/220877091_Calibration_Games_Making_Calibration_Tasks_Enjoyable_by_Adding_Motivating_Game_Elements
Уверенность: высокая на существование и содержание (рецензируемая ACM-публикация,
подтверждена несколькими независимыми пересказами), низкая на прямое цитирование
(полный текст за пейволлом ACM, не удалось открыть — abstract и структура
подтверждены через вторичные пересказы, не выдаю пересказ за дословную цитату).

**Почему это структурно ДРУГАЯ категория, а не косметика поверх степпера**: вместо
«выбери значение X» пользователь выполняет игровое действие (целится, реагирует,
двигает), а система ВЫЧИСЛЯЕТ параметр из того, как он это сделал — источник истины
не явный ввод, а измеренное поведение. Прямого готового транспонирования на «Карту/
Цвет/Сохранить» не предлагаю (это отдельный, более узкий разговор), но это честно
единственная находка всей сессии (10+1 агентов), которая структурно НЕ является ни
визардом, ни степпером, ни единой лентой, ни Typeform-стилем, ни персонажным
конструктором, ни «контролы поверх превью» — источник настройки не форма, а
измеренное игровое поведение.

### Б.2 Генеративная случайность → точечная правка (владелец сам назвал направление)

Это НЕ единичный экзотический пример — а сходящаяся, широко воспроизведённая практика
в разных, взаимно независимых нишах (что само по себе честный сигнал силы паттерна):

- **Looka (генератор логотипов)** — ввод названия/индустрии/стиля → система выдаёт
  СРАЗУ готовый, полностью укомплектованный результат (не по шагам «сначала цвет,
  потом шрифт, потом иконка», а всё сразу) → дальше отдельный редактор точечно меняет
  цвета/шрифты/иконки/раскладку у уже готового результата.
  — https://looka.com/logo-maker/how-it-works/
- **Framer AI / бывший Wix ADI** — текстовый промпт («лендинг для крипто-кошелька») →
  полностью готовый многосекционный сайт с текстом и раскладкой → каждая секция
  редактируется отдельно точечно. Актуальный Wix (Aria) прямо оформлен как **свободное
  чередование** «попросить ИИ поменять» ↔ «руками подвинуть пиксель» в любой момент,
  не как одноразовый генератор с редактором «после».
  — https://www.wix.com/blog/wix-artificial-design-intelligence ,
  https://fritz.ai/framer-ai-review/
- **Picrew / «гача»-конструкторы персонажей (Япония)** — прямо заявленная опция:
  «сгенерировать случайно, выбрать руками, ИЛИ сгенерировать случайно и поправить
  только отдельные понравившиеся части» — все три пути равноправны в одном
  инструменте, не последовательные обязательные шаги.
  Уверенность: средняя (японские источники подтверждают паттерн, но это малые
  инди-инструменты, не крупная платформа с официальной документацией).
- **Академическая рамка для всего явления** — «mixed-initiative co-creativity» (HCI/
  computational creativity, живая область, статьи вплоть до 2025-2026): и человек, и
  система имеют инициативу, «generate-then-refine» — не разовый акт, а цикл, где
  предложения системы обновляются по мере правок человека. Это формальное название
  того самого паттерна, который владелец описал словами «сначала получи готовый
  случайный результат, потом дорабатывай».
  — https://arxiv.org/abs/2305.07465 ,
  https://dl.acm.org/doi/fullHtml/10.1145/3613905.3650929

**Честная оценка новизны**: это НЕ новая, никем не найденная категория — это активно
используемый, многократно независимо изобретённый паттерн (логотипы, сайты, японские
конструкторы персонажей, академическая рамка). Владелец прямо назвал направление
существующим, реальным термином не пользуясь — находка здесь не «это существует», а
что это ЕДИНСТВЕННЫЙ из всех направлений раздела Б, который одновременно (а) реален,
(б) массово воспроизведён независимо в нескольких культурах/индустриях, (в)
структурно отличается от всех уже описанных в сессии категорий (не форма, не
степпер, не персонажный конструктор с параметрами, не «контролы над превью с нуля»).
Прямого применения к «Карта/Цвет/Сохранить» не предлагаю без отдельного обсуждения.

### Б.3 Направления, которые честно проверены и НЕ дали структурно нового

- **Voice-driven настройка (Alexa Routines)** — реальна, задокументирована
  официально: можно голосом описать «что и когда», Alexa сама создаёт routine.
  — https://www.amazon.com/gp/help/customer/display.html?nodeId=TR10VgRL0uV9H384FM
  Но структурно это **тот же generate-then-refine** (Б.2) с голосовым вводом вместо
  текстового — не отдельная категория, а другой канал ввода для уже найденного
  паттерна. Честно: не новое.
- **Netflix Bandersnatch / интерактивные развилки** — реальный, задокументированный
  UX (два текстовых варианта + убывающая полоса-таймер 10 секунд, тестировали интервал
  3-5 минут между решениями).
  — https://uxdesign.cc/how-did-the-ux-design-team-prepare-us-for-the-new-black-mirror-bandersnatch-interactive-film-aa3373145e79
  Но это **branching narrative** — по структуре ближе к «Branching wizard» (уже
  описан в `RESEARCH-2026-09-WIZARD-CONTINUITY.md` как один из трёх типов степпера) —
  ветвящийся путь, не создание объекта. Честно: не новая категория, вариация уже
  названного типа.
- **Нест-термостат «Auto-Schedule» (обучение по наблюдению вместо настройки)** —
  реален: система НЕ спрашивает расписание явно, а несколько дней наблюдает за тем,
  как человек меняет температуру руками, и сама строит расписание.
  — https://support.google.com/googlenest/answer/9247510
  Структурно это ДЕЙСТВИТЕЛЬНО иная парадигма (конфигурация как побочный продукт
  использования, растянутая во времени, а не разовый флоу) — но требует дней
  наблюдения, физически несовместима с «создать одно небо за один присест» —
  честно фиксирую как реальную, но нерелевантную по формату находку, не притягиваю
  силой.
- **VR Guardian/Boundary (обвести границы, физически пройдя по комнате)** —
  реален и задокументирован (Meta Quest), но это **прямое манипулирование** (рисуешь
  границу тем же жестом, каким будешь двигаться) — концептуально то же самое, что уже
  подтверждённый в первой волне тап/драг на трассе, просто в другой физической
  модальности (контроллер в 3D вместо пальца на 2D-полосе). Не новая категория.
- **Tarot/оракул-раскладки** — специально искал: нашлись только эстетические/
  ритуальные описания приложений (анимация переворота карты, атмосфера), НИ ОДНОГО
  структурного паттерна «настройка через последовательное вскрытие карт» не нашлось.
  Честно: пусто, выдумывать мост не буду.
- **Spotify Wrapped** — генеративный **реveal без настройки вообще** (система решает
  всё сама, редактирования нет) — это не конфигуратор, а витрина; исключил из
  находок как нерелевантный (нет пользовательского выбора вообще).

### Б.4 Итоговый честный вердикт по разделу Б

Из всех проверенных нестандартных направлений **ровно одно** — Calibration Games
(Б.1) — структурно ново по отношению ко всем 10+1 категориям, описанным за всю
сессию: источник параметра не явный выбор пользователя, а измеренное игровое
поведение. Ещё одно — generate-then-refine (Б.2) — реально, массово воспроизведено,
но НЕ является «никем не придуманной» категорией: это активно используемый паттерн
с академическим именем (mixed-initiative co-creativity), просто владелец
переоткрыл его словами независимо. Остальные пять проверенных направлений (voice,
branching narrative, ambient learning, physical-guardian, tarot, Wrapped) — либо
честно пустые, либо оказались вариациями уже названных категорий, а не новыми.
Если владелец рассчитывал на десятую невиданную находку — её нет; две выше — это
максимум честного результата этого захода.
