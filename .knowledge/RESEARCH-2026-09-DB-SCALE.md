## 1. Supabase-специфика: пулинг, лимиты, реплики, партиционирование, реальные кейсы

### Supavisor vs PgBouncer, transaction vs session mode
Supavisor — мультитенантный shared pooler, включён по умолчанию в каждом проекте (заменил
самостоятельный PgBouncer как основной путь). Архитектурно написан на Elixir/BEAM в партнёрстве с
создателем Elixir Жозе Валимом — кластерный, умеет read-replica load balancing, в отличие от
классического PgBouncer (однопоточный C-демон, не cluster-aware).

- **Transaction mode** (порт 6543): соединение отдаётся клиенту только на время транзакции, потом
  возвращается в пул. НЕ поддерживает protocol-level prepared statements, НЕ сохраняет
  session-state между транзакциями (`LISTEN/NOTIFY`, temp tables, advisory locks, `SET`).
  Неиспользуемое backend-соединение закрывается через 5 минут. Режим для короткоживущих
  stateless-запросов — типичный профиль edge-function-трафика.
- **Session mode** (порт 5432): соединение закреплено за клиентом на всю сессию, поддерживает
  всё состояние сессии, но расходует connections так же, как direct-подключение — выигрыша в
  лимите не даёт.
- В официальном собственном стресс-тесте (не кейс клиента, бенчмарк Supabase) кластер из двух
  64-core Supavisor-узлов выдержал ~1 003 200 одновременных соединений и 20 000 QPS при медианной
  задержке 18.4 мс.
- Источники: supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits,
  supabase.com/docs/guides/troubleshooting/supavisor-and-connection-terminology-explained-9pr_ZO,
  supabase.com/blog/supavisor-1-million

### Партиционирование
Официальная позиция Supabase: партиционирование поддерживается (range/list/hash), ключ партиции
обязан входить в любой unique index/PK. Официальная поддержка `pg_partman` для автоматизации
ротации партиций через `pg_cron`. **Прямой рекомендации именно про leaderboard-таблицы в докс
Supabase не нашлось** — только общий принцип «не партиционировать, пока реально не упёрлись».
Источники: supabase.com/docs/guides/database/partitions,
supabase.com/docs/guides/database/extensions/pg_partman

### Read replicas
Доступны на **Pro, Team, Enterprise** (не на Free). Требования: проект на AWS, минимум **Small**
compute, Postgres 15+. Официальный критерий из блога «When to use Read Replicas vs. bigger
compute»: реплики имеют смысл, когда **чтения составляют 80%+ трафика** — прямое попадание в
профиль игрового лидерборда (читают на порядки чаще, чем пишут). Не помогают с записью — INSERT/
UPDATE/DELETE всегда на primary. Источники: supabase.com/docs/guides/platform/read-replicas,
supabase.com/blog/read-replicas-vs-bigger-compute

### Когда переходить на Team/Enterprise
Официальные пороги Supabase сформулированы **не через нагрузку на БД**, а через комплаенс и
организационные требования — SOC2/ISO 27001, HIPAA, SLA, доступ по ролям, приоритет поддержки.
Технический потолок масштабирования БД (до 16XL compute) общий для всех платных тарифов и не
требует перехода на Team. Честно: явного официального порога вида «при X connections/QPS
переходите на Team» не нашлось.

### Официальные кейсы клиентов на 100k–1M+ пользователей
Честно: **конкретных технических деталей изменения конфигурации БД в официальных кейсах не
нашлось.** Кейс Pebblely (1M+ пользователей за 7 месяцев) говорит только про переход авторизации
на Google+magic link, не про БД. Единственный материал с реальными инженерными числами о
масштабировании — это собственный бенчмарк пулера (см. выше), не кейс клиента.

## 2. Общие Postgres-паттерны для leaderboard-таблиц at scale

### Top-N и top-N-per-group
- Простой `ORDER BY score DESC LIMIT N` с B-tree индексом на `score` — планировщик читает индекс
  от максимума и останавливается на LIMIT, не сортируя всю таблицу.
- **Partial/covering индекс**, сформулированный под точную форму запроса, даёт «уже
  отсортированный» индекс и убирает heap fetch (Index-Only Scan).
- **BRIN vs B-tree**: BRIN эффективен только при физической корреляции столбца с порядком вставки
  (монотонный timestamp/ID). Для случайно распределённого `score` — B-tree однозначно лучше.
- **Top-N per group** (топ игрока в каждой категории/дне): три конкурирующих паттерна —
  `ROW_NUMBER()/RANK()` (window function), `LATERAL JOIN ... LIMIT`, `DISTINCT ON` (Postgres-
  специфика). Механика: window-function сканирует ВСЮ inner-таблицу и нумерует всё, `LATERAL`
  делает index-seek по группе с ранней остановкой. Правило выбора: LATERAL выигрывает при малом N
  и умеренном числе групп; `DISTINCT ON` с композитным индексом `(group_col, score DESC)` не
  требует отдельной сортировки вообще. Конкретных бенчмарков «во сколько раз быстрее at scale» не
  нашлось — нужен `EXPLAIN ANALYZE` на реальных данных проекта, когда они появятся.
- Источники: postgresql.org/docs/current/indexes-ordering.html, cybertec-postgresql.com (btree vs
  BRIN), sqlint.com/articles/top-n-per-group-in-sql, monpg.app/blog/postgresql-distinct-on

### Материализованные представления vs денормализованная таблица+триггеры
- `REFRESH MATERIALIZED VIEW CONCURRENTLY` не блокирует SELECT, но требует unique-индекс на MV и
  работает медленнее обычного REFRESH (диффит старую/новую версию). **Ключевое ограничение: ни
  обычный, ни concurrent refresh не инкрементальны** — каждый раз пересчитывает запрос заново.
  Trade-off: простая реализация, предсказуемая нагрузка по расписанию, но окно устаревания.
- Триггер + денормализованная таблица: инкрементальное обновление на каждую запись, более «живая»
  свежесть, но постоянный оверхед на КАЖДУЮ запись в `scores`. Официального «trigger on
  materialized view» в Postgres нет — это отклонённый feature request, не факт.
- Источники: postgresql.org/docs/current/sql-refreshmaterializedview.html,
  netguru.com (MV refresh via triggers)

### UNLOGGED tables
Данные не пишутся в WAL → быстрее (в бенчмарках разброс от ~23% до ~50% на вставке), меньше
нагрузка на vacuum. **Риски, подтверждённые официальной докс**: таблица автоматически
truncate'ится после краша/нечистого выключения; содержимое НЕ реплицируется на standby и
недоступно на репликах; индексы и sequences на unlogged-таблице тоже автоматически unlogged.
Годные use-case: временные/переходные данные, кэш/производные данные, которые можно пересчитать
при потере. Явного упоминания именно «rate limiting»/«nonce» как canonical use-case в источниках
нет — это логический вывод по критерию «regenerable, non-critical при краше», не прямая цитата.
Источники: crunchydata.com/blog/postgresl-unlogged-tables, postgresql.org/docs/current/sql-
createtable.html, pganalyze.com/blog/5mins-postgres-unlogged-tables

### Партиционирование по времени
Встроенное декларативное партиционирование (Postgres 10+) или `pg_partman` для автоматизации.
Порог «когда стоит того» — не найден как число строк ни в одном источнике, только качественный
ориентир: держать число партиций в пределах «нескольких сотен», свыше — измеримое замедление
планировщика. Русскоязычные источники (Хабр, включая разбор Wildberries) подтверждают тот же
паттерн для высоконагруженных систем и добавляют: сама вставка немного замедляется из-за routing
overhead; при hot-spot записи в «сегодняшнюю» партицию — вложенное партиционирование RANGE по
дате + HASH по внутреннему ключу (например player_id). Источники: pgxn.org/dist/pg_partman/doc,
crunchydata.com/blog/time-partitioning-and-custom-time-intervals-in-postgres-with-pg_partman,
habr.com/ru/companies/wildberries/articles/1000514

### Autovacuum-тюнинг под высокую частоту записи
Тюнить **per-table** (`ALTER TABLE ... SET`), не глобально. Конкретные цифры из источников:
`autovacuum_vacuum_scale_factor` дефолт 0.2 → для high-churn таблиц снижать до 0.01–0.02;
`autovacuum_vacuum_threshold` 500 вместо дефолтных 50; `autovacuum_vacuum_cost_limit` 1000 вместо
дефолтных 200 — снятие throttling. Правило по частоте: для таблиц с >1000 записей/минуту —
scale_factor 0.01, cost_delay 0. Отдельно: перевод таблицы в UNLOGGED сам по себе частично снимает
вопрос агрессивного autovacuum-тюнинга для неё (меньше WAL-оверхед). Источники: keithf4.com/per-
table-autovacuum-tuning, habr.com/ru/companies/otus/articles/845064 (настройка автовакуумирования)

## 3. Реальные постмортемы масштабирования (не общие статьи-списки)

### Discord — MongoDB → Cassandra → ScyllaDB
2015: рабочее множество MongoDB перестало влезать в RAM, каждое чтение уходило на диск,
непредсказуемая латентность. На Cassandra (2017→2022, 12→177 нод): «горячие партиции» —
непропорциональный трафик на маленьких нодах, каскадный рост латентности, долгие паузы GC с
ручным перезапуском узла. Починили переходом на ScyllaDB (C++, без GC): 177→72 ноды, p99 чтения
40–125мс → 15мс. Источник: discord.com/blog/how-discord-stores-trillions-of-messages

### Notion — прикладной шардинг Postgres-монолита (2020–2021)
После «5 лет и 4 порядков роста» — ежедневные CPU-спайки, ключевой триггер: `VACUUM` систематически
захлёбывался, что вело к риску TXID wraparound (Postgres останавливает ВСЕ записи целиком, чтобы
не повредить данные) — экзистенциальный риск для продукта. Починили прикладным шардингом: 480
логических шардов на 32 физических БД, партиционирование по workspace_id, миграция через
двойную запись + audit-log (логическая репликация не потянула объём). Вывод авторов: шардинг
нужно было начинать раньше, до того как проблема стала критической. Источник:
notion.com/blog/sharding-postgres-at-notion

### Games24x7 / My11Circle (индийская fantasy sports, мега-турниры до 20 млн участников) — лучшая находка по hot-partition в лидерборде
Leaderboard в Cassandra, партиционирование по `contest_id` — вся таблица результатов одного
контеста ложилась в одну партицию, разраставшуюся до 500–800 МБ (при рекомендуемом максимуме
~100 МБ), неравномерная загрузка нод (80% CPU vs 30–40%). Починили составным ключом
`(contest_id, bucket)`, `bucket = (rank/K)+1`, K подобран нагрузочным тестированием, раскатка
поэтапно через dual-write/dual-read сначала на малых матчах. Результат: средняя латентность
записи 2.209мс → 26мкс, макс. размер партиции 557МБ → 8.83МБ (в 63 раза меньше), расходы в пиковый
месяц −50%. Источник: games24x7.com/resource/beating-the-heat-how-we-cooled-down-cassandras-hot-
partitions-to-scale

### Общий паттерн hot-row contention (не привязан к одному инциденту, подтверждён многократно)
`UPDATE score = score+1 WHERE id=X` на одну строку счётчика создаёт очередь блокировок — латентность
растёт кратно. Стандартные лекарства: sharded counters (несколько строк-шардов + сумма при
чтении), append-only событийный лог с фоновой агрегацией, advisory locks для координации без
блокировки реальных строк.

### Connection storms в serverless (обобщённый механизм, не именной постмортем)
Разбор на примере booking-платформы: serverless-функция падает посреди транзакции → контейнер
убит, но TCP-соединение к Postgres висит «idle in transaction» и держит row lock ещё несколько
минут, пока не истечёт OS-таймаут. Симптом: конкурентность упирается в потолок, а CPU БД всего
8% (все ждут, никто не работает). Фикс — 4 настройки: `idle_in_transaction_session_timeout=10000`,
`statement_timeout=5000`, `lock_timeout=500ms`, ограничение reserved concurrency + вынос внешних
API-вызовов за пределы транзакции. Источник: dev.to/srinu_madhavvysyaraju_b9/connection-storms-
and-orphan-locks

### Японские источники (PingCAP-ивент, Cygames / Wonder Planet / Square Enix)
Три компании названы напрямую (материал про переход на NewSQL TiDB, но с конкретными цифрами
текущей боли): Cygames держит 300万 QPS (3 млн QPS) на 64 шардах (192 сервера), скейл-аут требует
2–3 месяца подготовки; Wonder Planet — при сотнях миллионов–миллиардах записей масштабирование
возможно только в плановые техработы, планирование одного окна — месяц; Square Enix (Aurora) —
обновления сервиса требуют перезапуска БД, подгонки под цикл техработ. Источник:
qiita.com/official-columns/event/202401-pingcap

### Честный список «не нашлось» по постмортемам
- Именного постмортема serverless connection exhaustion у конкретной игровой компании (с датами,
  числами, публичным названием) — не нашлось, только обобщённый механизм.
- PlanetScale/Statsig/Retool — только маркетинговые кейс-стади без описания поломки.
- Hypixel (Minecraft) — нет открытого инженерного постмортема про БД.
- Pokemon Go / Among Us / Wordle — подтверждены обвалы при взрывном росте, но без публичного
  технического разбора на уровне БД.
- Китайский сегмент (阿里云/腾讯云/CSDN/掘金) — не нашлось ни одного материала с названной
  компанией и точным разбором инцидента с числами и датами, только общие статьи-руководства по
  паттернам (分库分表 — шардинг, Redis ZSET-бакеты для лидербордов).

## 4. Deno Edge Functions + Postgres под нагрузкой

### Холодный старт
Официальный блог: среднее время холодного старта упало с ~870 мс до ~42 мс, P99 «под полсекунды»
после внедрения persistent storage для функций. Влияет размер бандла и объём зависимостей.
Источники: supabase.com/docs/guides/functions/architecture, supabase.com/blog/persistent-storage-
for-faster-edge-functions

### Самая важная находка раздела: архитектура проекта уже структурно защищена от «connection storm»
Проверено в коде (`cosmogram-sync`, `cosmogram-beacon`, `cosmogram-workshop`): весь доступ к БД
идёт через `createClient()` из `jsr:@supabase/supabase-js@2` — то есть через **PostgREST (HTTP
API)**, а не через прямое TCP-соединение (в коде нет `Pool`/`postgres.js`/`pg`). Официальная FAQ
Supabase прямо говорит: **«PostgREST does not use Supavisor»** — PostgREST держит собственный
фиксированный небольшой пул TCP-соединений к Postgres (настраивается в Dashboard → Database
settings → pool size), и этот пул НЕ растёт пропорционально числу параллельных Edge Function
вызовов. Классическая serverless-проблема «500 функций открывают 500 соединений и валят RDS»
(задокументированная для AWS Lambda + RDS, откуда и придумали RDS Proxy) **архитектурно не бьёт
по этому проекту напрямую** — она переносится на размер внутреннего пула самого PostgREST и на
конкуренцию за общий `max_connections` между PostgREST/Auth/Realtime/Storage/Supavisor
одновременно. FAQ рекомендует держать Supavisor в пределах 40–80% от доступных подключений.
Источники: supabase.com/docs/guides/troubleshooting/supavisor-faq-YyP5tI, dev.to/jeancy (Lambda+
RDS connection storm, аналогия)
Честно: точной официальной цифры дефолтного размера пула PostgREST по тарифам не нашлось — надо
смотреть в Dashboard проекта напрямую, не полагаться на докс.

### Rate limiting через `check_rate_limit` — уже сделано правильно
Уже реализованный в проекте паттерн (атомарный RPC на `INSERT ... ON CONFLICT DO UPDATE ...
RETURNING`, boolean-возврат, использован в `cosmogram-sync` и `cosmogram-beacon` с разными
ключами) подтверждён несколькими независимыми источниками как именно рекомендуемый race-free
подход для serverless на Postgres — **это НЕ нужно изобретать заново, оно уже сделано**.
Источники: neon.com/guides/rate-limiting, gist.github.com/ChinmayKuJena (пример того же паттерна).
Альтернатива «для полноты картины, не для внедрения»: Upstash Redis (HTTP/REST, официально
рекомендован самим Supabase для rate limiting именно в Edge Functions) — но добавляет внешнюю
зависимость, что противоречит принципу проекта «никакого билд-пайплайна, никаких новых
npm-зависимостей без отдельного обоснования».

### Официальные лимиты Edge Functions
14.09.2026, поправка после проверки: официальная страница `functions/limits` (проверена
дважды дословно) даёт **единую цифру памяти 256 MB без разбивки по тарифам Free/Pro** —
деление 150/400 относится к ДРУГОМУ лимиту (wall clock, секунды), не к памяти. Прежняя
версия («256 MB Pro / 150 MB Free») смешала эти два разных лимита — не опираться на неё,
перепроверить напрямую в Dashboard проекта перед решением, если точная цифра памяти важна.
CPU time на запрос — 2 сек, wall clock — 150 сек (Free) / 400 сек (платные), размер бандла —
20 MB (CLI) / 5 MB (Dashboard). При превышении 50% ресурса изолят
доедает текущий запрос и завершается; при полном исчерпании — немедленное завершение, ответ 546.
Честно: официального числа «максимум N одновременных инстансов при вирусном всплеске» не
нашлось — акцент докс на per-request лимитах, не на общем троттлинге входящих вызовов. Источники:
supabase.com/docs/guides/functions/limits, supabase.com/docs/guides/troubleshooting/edge-
function-546-error-response

## 5. Честная сверка с живой схемой проекта (MCP `execute_sql`/`get_advisors`, 14.09.2026)

### Уже структурно готово к росту
- **RLS включён на всех таблицах** — уже было известно, подтверждено заново. 14.09.2026,
  поправка после проверки: прежняя версия называла число «19» — на момент повторной проверки
  в public-схеме реально **20** таблиц, RLS включён на всех 20 (само правило верно, число
  устарело/было изначально сосчитано неточно — живые таблицы появляются/пересчитываются,
  сверять заново перед использованием точного числа, не брать из этого файла).
- **`check_rate_limit` — атомарный, race-free, уже правильный паттерн** (раздел 4) — не требует
  переделки при росте нагрузки.
- **Индекс под leaderboard уже правильной формы**: `scores_top_idx` — `(category, best DESC)` —
  ровно тот паттерн partial/covering-по-смыслу индекса, который раздел 2 называет оптимальным для
  `ORDER BY score DESC LIMIT N`. `daily_runs_day_score` — `(day, score DESC)` — то же самое для
  дневных забегов. Оба уже на месте, без правки.
- **`daily_runs` уже логически партиционирована по дню** (`day` как часть PK и большинства
  индексов) — готовый кандидат на физическое time-based партиционирование, когда/если до этого
  реально дойдёт по объёму (раздел 2) — сейчас 80 kB, дорасти до этого объёма ещё далеко.
- Replay-защита (`used_nonces`) и общий лимитер запросов (`rate_limits`) — уже сделаны на уровне
  Edge Function кода до этого исследования (не находка, а подтверждение уже принятого решения).

### Реальный риск/недоделка именно по архитектуре БД (не по коду Edge Functions)
- **Ни одна таблица не UNLOGGED**, включая `rate_limits` (64 kB, 88 строк) и `used_nonces` (120
  kB, 1 строка живых на момент проверки, но по природе — high-churn insert-only лог) — оба по
  критериям раздела 2 (regenerable, non-critical при потере в краше) логически подходят под
  UNLOGGED, но живут как обычные (WAL-логируемые) таблицы. Это НЕ баг — на текущем почти нулевом
  трафике разницы нет, но при высокочастотной записи (миллион игроков) это первый кандидат на
  пересмотр — решение и конкретные шаги отдельным вопросом владельцу, не в рамках этого
  исследования.
- **4 внешних ключа без индекса** (`biathlon_runs.player_id`, `forge_workshop_reports.reporter_id`,
  `slalom_runs.player_id`, `speedrun_runs.player_id`) — подтверждено официальным performance-
  advisor'ом Supabase (`unindexed_foreign_keys`, уровень INFO). На нынешнем объёме незаметно,
  но JOIN/DELETE CASCADE по этим FK при росте строк будет делать full scan вместо index scan.
- **Нет ни одной materialized view и ни одного read replica** — ожидаемо на текущем этапе (проект
  почти пустой), но раздел 1 прямо называет read replicas официально оправданными для профиля
  «чтения 80%+ трафика» — это будущая, не текущая, необходимость; доступны только с тарифа Pro.
- **Партиционирование нигде физически не включено** — логично для текущего объёма (крупнейшая
  таблица `players` — 96 kB), но при миллионной аудитории `scores`/`daily_runs`/`beacons` —
  реалистичные кандидаты по объёму записи в будущем.
- **Autovacuum не тюнингован per-table** (дефолтные глобальные настройки Postgres) — ожидаемо,
  пока нет высокочастотной записи, которая оправдывала бы отклонение от дефолта.
- Всё это — не блокеры сейчас (база почти пустая, 92 строки в самой большой активной таблице
  `beacons`), а карта того, куда именно в первую очередь смотреть, когда трафик реально начнёт
  расти — не список задач на сегодня.

## Честно: что не нашлось (сводный список по всему исследованию)
- Официальный порог Supabase «при такой-то нагрузке переходите с Pro на Team/Enterprise» — не
  сформулирован через технические метрики БД, только через комплаенс.
- Официальные Supabase-кейсы клиентов на 100k–1M+ с описанием ИМЕННО технических решений по БД
  (не только бизнес-метрик роста).
- Официальная рекомендация Supabase про партиционирование именно leaderboard-таблиц.
- Численный порог строк (не партиций), с которого партиционирование определённо оправдано.
- Прямая цитата источника, называющая rate-limit/nonce-таблицы canonical use-case для UNLOGGED
  (вывод по аналогии, не прямая находка).
- Именной постмортем serverless connection exhaustion у конкретной игровой компании.
- Официальная цифра дефолтного размера пула PostgREST по тарифам Supabase.
- Официальное число максимума одновременных Edge Function инстансов при резком всплеске трафика.
- Детальный китайский (阿里云/腾讯游戏) постмортем с названной компанией и числами — только общие
  статьи-руководства без привязки к конкретному инциденту.
