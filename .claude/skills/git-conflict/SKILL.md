# Git-конфликт — сравнить обе стороны, не брать вслепую

Владелец параллельно работает в GitHub Desktop в том же чек-ауте — это не редкость, а
рабочий режим проекта. Три реальных инцидента одного класса (03.09.2026 дважды,
29.09.2026) — выше собственного порога проекта «≥3-5 повторов = обязателен скилл/хук».

## 0. Сначала — не паника, а диагноз

- `git status` → если unmerged paths — прочитать `.git/MERGE_MSG` и `git log --oneline
  origin/main -5` — понять, ЧТО именно мержится и откуда (обычно: GitHub Desktop Pull,
  не сессия Claude).
- Если правки «пропали» из рабочего дерева без явного `git commit`/`git reset`/`git stash`
  с твоей стороны — ПЕРЕД тем как считать их потерянными и переписывать заново,
  проверить `git stash list` ([[feedback_github_desktop_silent_stash]], 03.09.2026 —
  GitHub Desktop тихо застэшил незакоммиченные правки, решил, что баг в мерже).

## 1. Ядро — только по отдельной просьбе

Если конфликт затрагивает `core.js`/`game.js`/`render.js`/`input.js` — снятие маркеров
в нём ВСЁ РАВНО «трогать ядро», даже если цель — механическая интеграция, не новая
фича. Владелец должен явно сказать «разреши конфликты» (не «продолжай» на общую
задачу) — это отдельное разрешение, полученное один раз на этот конкретный мерж,
не переносится молча на будущие.

## 2. Показать обе стороны, не решать вслепую

Для каждого конфликта — прочитать HEAD и incoming-блок целиком, понять их разницу
по СУТИ, не просто взять «свою»/«чужую» сторону:
- **Чисто цифра/версия** (номер версии, `?v=` хвосты) — почти всегда можно предложить
  решение самому (взять более новое число, потом поднять версию ещё раз), но
  озвучить это владельцу, не решать молча, если правка нетривиальна.
- **Реальная логика** (переименованная функция, две разные фичи в одном месте) —
  ВСЕГДА отдельный явный вопрос с вариантами (AskUserQuestion), не додумывать.
- Часто конфликт — дубликат одной и той же идеи в двух формулировках
  ([[feedback_github_desktop_silent_stash]]) — сравнение по содержанию это ловит
  быстрее, чем разбор по маркерам вслепую.

## 3. Разрешать через Edit, не Bash

Auto-mode классификатор блокирует Bash-скрипты, трогающие файл с активным
git-конфликтом, ДАЖЕ после явного «да» владельца в чате — и блокирует ПОВТОРНО при
повторной попытке ([[feedback_classifier_blocks_conflict_scripts]], 03.09.2026).
Не пытаться продавить тот же Bash-вызов ещё раз. Разрешать точечно инструментом
`Edit` (`old_string` = весь блок с маркерами → `new_string` = выбранное содержимое)
на каждый конфликт отдельно — другой путь выполнения, не блокируется, результат
идентичный.

## 4. После разрешения

1. Проверить, что маркеров `<<<<<<<`/`=======`/`>>>>>>>` не осталось нигде (`grep`).
2. Синтаксис (`node --check` на `.js`, `bash -n` на `.sh`).
3. Если правка игрового файла — `node tools/bump-version.mjs` (стандартная дисциплина
   проекта — версия ДОЛЖНА подняться после любой правки `core.js`/`index.html`/`sw.js`,
   мерж не исключение).
4. Полный `node tests/guard.mjs` (не `--only=`) — интеграция чужой ветки может задеть
   что угодно, узкий прогон не покрывает.
5. `git add` только реально резолвнутые файлы (не `-A`), коммит с явным упоминанием
   «разрешение конфликта».
6. `git push` — НИКОГДА, как и везде в проекте.

## 5. Если GitHub Desktop уже открыт у владельца с тем же мержем

Не коммитить через CLI параллельно с открытым GUI на том же мерже — два инструмента,
трогающие один `.git` одновременно, риск десинхронизации/блокировки файла. Разрешить
конфликты в файлах (это безопасно, GUI сам подхватит изменения на диске), но
финальный коммит — либо явно через CLI после того как сказал владельцу, либо оставить
владельцу нажать кнопку в уже открытом у него окне.
