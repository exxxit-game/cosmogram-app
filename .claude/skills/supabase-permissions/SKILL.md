# Права Supabase: success:true не значит, что легло туда, куда думал

Вызывать, когда создаётся новая функция или RPC, пишется миграция с `CREATE FUNCTION`, меняются права на существующей. Официальный плагин `supabase` этого урока не содержит (проверено 29.09.2026: `ALTER DEFAULT PRIVILEGES` и `REVOKE EXECUTE` в нём не упоминаются): это специфика проекта, три прокола за один вечер 06.09.2026. Хук `new-function-revoke-guard.mjs` страхует запись, но не заменяет проверку ниже.

## Три ловушки проекта

1. **`REVOKE ... FROM anon, authenticated` не срабатывает.** Реальный грант часто висит на псевдо-роли `PUBLIC`, и отзыв у конкретных ролей её не трогает. Правильно: `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`, все три явно.
2. **В проекте есть `ALTER DEFAULT PRIVILEGES`,** который сам выдаёт `anon` и `authenticated` новым функциям при создании. Для новой функции мало `REVOKE` потом: он пишется в той же миграции, что и `CREATE FUNCTION`, одним куском.
3. **Перевернуть умолчание для всей схемы разом получится только частично:** есть второй, не наш `pg_default_acl` (`supabase_admin`), который мы поменять не можем. Один общий `ALTER DEFAULT PRIVILEGES` не решает вопрос навсегда.

## Проверка после, всегда

После любого `REVOKE` или `GRANT`, даже при «успешно»:
1. Перечитать реальные права из `information_schema.role_routine_grants`, а не статус команды.
2. Подтвердить `curl` настоящим анонимным ключом: ждать `42501 permission denied`, а не просто отсутствие ошибки в ответе SQL.

## Формула для новой функции

```sql
create function public.my_new_function(...) ... as $$ ... $$;
revoke execute on function public.my_new_function from public, anon, authenticated;
```
Обе строки в одной миграции; шаги проверки выше в этом же ходу, не отложенным шагом.

## Ещё ловушки из официального руководства Supabase (при политиках и представлениях)

- Представления обходят RLS, если не созданы с `security_invoker = true`.
- `user_metadata` пользователь может менять сам: не использовать в политиках и проверках прав; брать `app_metadata`.
- Политике `UPDATE` нужны оба условия, `USING` и `WITH CHECK`; без `WITH CHECK` можно переписать владельца строки.
- `TO authenticated` без проверки владельца (`auth.uid() = user_id`) даёт читать чужие строки.
- `SECURITY DEFINER` в публичной схеме доступен всем ролям, пока не отозван `EXECUTE`; не добавлять его «чтобы заработало».
