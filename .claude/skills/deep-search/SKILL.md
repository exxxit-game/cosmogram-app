# Глубокий поиск — думать по-настоящему, не от балды

Владелец не хочет «первое пришедшее в голову стандартное решение» и не хочет, чтобы
параметр брался наугад. Он хочет: понять задачу до дна → перебрать РАЗНЫЕ семейства
решений, включая нестандартные → проверить цифрами → честно сказать, что не проверено.

## Реальные промахи, ради которых этот скилл существует (28.09.2026)

- Музыка на телефонах: три дня чинили синтезатор по кусочку, хотя с первого замера было
  видно, что сам ПОДХОД (сочинять звук на телефоне) не тянет слабое железо. Надо было
  сразу спросить «какие вообще есть семейства решений», а не «как облегчить этот».
- Сжатие: предложил 64/96/128 кбит/с «послушай, что лучше» — параметр от балды, без
  метода. Правильный путь нашёлся только после вопроса «из чего состоят НАШИ данные»:
  вся 6-минутная музыка — один круг из 8 тактов, значит хранить надо слои по 15 с, а не
  6 минут смеси → без потерь 24 МБ превратились в ~7 МБ.
- Раньше: «две разные песни» — усреднённое мерило сказало «похоже», ухо сказало «нет».
  Мерило выбирать под вопрос (такт-за-тактом, а не среднее по всему файлу).

## Порядок

### 0. Одна строка: что на самом деле нужно
Цель, жёсткие ограничения (из CLAUDE.md и слов владельца: без новых npm-зависимостей,
ядро только по просьбе, визуальное только макетом…) и **чем будем мерить «лучше»** — число.
Если мерило не придумывается — это вопрос владельцу, не додумывать.

### 1. Сначала — свои данные и своё устройство задачи (первые принципы)
Прежде чем искать снаружи: из чего состоит НАША вещь? Где скрытые повторы, симметрии,
линейность, детерминизм, что можно не хранить/не считать вовсе, что можно посчитать
заранее или в другом месте? Посчитать это коротким скриптом, а не на глаз.
Самые сильные решения обычно отсюда (пример выше: круг 8 тактов → слои).

### 2. Минимум 5 семейств решений, из них ≥2 нестандартных
Для каждой задачи пройти по списку и честно записать хотя бы по одной идее:
1. **Стандарт индустрии** — как это делает большинство (и почему у нас может не подойти).
2. **Как решают при жёстком ограничении** — демосцена (js13k, 4k/64k-интро), трекеры
   (MOD/XM), ретро-консоли, микроконтроллеры, спутники/космос, старые модемы.
3. **Соседние дисциплины** — кино/звукорежиссура, типографика, картография, сжатие
   данных, биология, логистика — где та же задача уже решена под другим именем.
4. **Убрать саму потребность** — можно ли сделать так, чтобы проблема не возникала
   (посчитать заранее, перенести работу на сервер/сборку/первый запуск, кэшировать).
5. **Гибрид / адаптация под устройство** — разное поведение для слабого и сильного железа
   по ИЗМЕРЕННОМУ признаку, а не по догадке.
6. **Обратная постановка** — что если перевернуть задачу (хранить не результат, а рецепт;
   не сжимать, а не создавать избыточность).

### 3. Поиск на всех языках мира — с родными терминами
- Искать не переводом английского запроса, а тем, как это называют носители:
  рус, англ, кит (中文), яп (日本語), кор (한국어), нем, фр, исп, порт, + язык той
  дисциплины, где задача сильнее всего развита (например, яп — для ретро-консолей и
  мобильных игр, нем — для инженерии, кит — для мини-игр и мини-приложений).
- Большая тема → параллельные фоновые агенты по языковым кластерам / по семействам из
  шага 2 (образец: `.knowledge/RESEARCH-2026-09-MULTILINGUAL.md`, 4 агента). Каждый обязан
  давать источник + дату на каждое утверждение.
- Честное «на этом языке ничего нового не нашлось» — нормальный результат, не натягивать.
- Утверждения о поддержке браузеров/API/устройств — только из первоисточника (спецификация,
  changelog, исходники движка, официальная документация). Не нашёл подтверждения — так и
  написать «не подтверждено, проверим живьём».

### 4. Цифры для каждого кандидата
Короткий скрипт → таблица: размер, нагрузка, время, качество (правильным мерилом под
вопрос), совместимость. Любую формулу/оценку — проверить численно до того, как она
попадёт в рекомендацию. Оценку помечать «оценка», замер — «замер».

### 5. Ответ владельцу
- Коротко, по-русски, без кода: что нашёл главное (1–2 фразы) → таблица кандидатов с
  цифрами → рекомендация и почему → честные минусы → что не проверено → источники ссылками.
- Каждый конкретный параметр (битрейт, порог, размер, длительность) — отдельным вопросом
  через AskUserQuestion с явными вариантами (владелец предпочитает всплывающее окно;
  он сам выбирает момент для голосовых). Ничего не вносить в игру без его слова.
- Если параметр нельзя выбрать «на слух/на глаз» честно — предложить МЕТОД выбора
  (например, слепой ABX-тест для качества звука), а не список чисел.

### 6. Сохранить
Большое исследование — в `.knowledge/RESEARCH-ГГГГ-ММ-ТЕМА.md` (источники с датами,
цифры, что отброшено и почему), чтобы следующая сессия не начинала с нуля.

## Не делать
- Не останавливаться на первом стандартном решении, даже если оно «правильное по учебнику».
- Не предлагать числа без метода выбора.
- Не доверять одному усреднённому мерилу; не утверждать по памяти то, что меняется
  (поддержка браузеров, API платформ, цены, лимиты).
- Не спешить: владелец явно просит «без спешки». Лучше на один шаг дольше, но с цифрой.
