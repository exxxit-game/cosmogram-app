# Непрозрачный/длинный блок — никогда руками, независимо от инструмента

Обобщение правила CLAUDE.md «Непрозрачный блок — никогда руками (30.08.2026)» — оно
родилось из деплоя Edge Function, но реально проявлялось **девять раз подряд**
([[feedback_manual_transcription_risk]], 03.09–26.09.2026) в разных инструментах:
деплой (8 случаев, включая настоящий base64-блоб картинки), а девятый — уже в
браузерной панели (`canvas.toDataURL()` → ручной `Write`). Риск не привязан к деплою —
он у ЛЮБОЙ передачи данных через модель-как-посредника, любым инструментом.

## Главный урок

Порог «файл/строка достаточно маленькие, можно напечатать по памяти» **не
существует** — риск не зависит от размера линейно, он есть при любой ручной
перепечатке уже существующего текста, включая читаемый код на ~500 строк (шестой
случай) и одно слово в комментарии (восьмой случай, под давлением реального
прод-инцидента — давление НЕ снижает риск, оно заставляет его игнорировать).

## 0. Первый вопрос — есть ли путь A→B напрямую, без прохода через текст

Прежде чем копировать что-либо руками, спросить: «есть ли инструмент, который
делает это напрямую, без перепечатки через меня?»
- Посмотреть на картинку/canvas в браузере → `computer{screenshot}`/`computer{zoom}`
  (изображение идёт в модель как картинка, не как текст для перепечатки), НЕ
  `canvas.toDataURL()` + ручной перенос base64.
- Задеплоить файл на живой Supabase → CLI-обход (временная зеркальная структура
  `<scratch>/supabase/functions/<name>/index.ts` + `cp`, механическая копия, не
  печать; `supabase functions deploy ... --workdir <scratch>`) — читает байты прямо
  с диска, ни один символ не проходит через контекст модели.
- Перенести файл между репозиториями → `cp`/`git`, не Read+Write.

Если такой прямой путь есть — он ВСЕГДА предпочтительнее любой, сколь угодно
аккуратной ручной перепечатки.

## 1. Если прямого пути нет — только программно

- Скрипт читает исходник → `JSON.stringify()`/эквивалент даёт уже экранированный,
  готовый текст — копировать этот результат в параметр, не набирать заново по
  памяти о недавнем чтении.
- Никогда не «пересказывать компактнее ради экономии» — решение сократить/упростить
  при переносе это самому себе придуманное разрешение нарушить правило, не рабочий
  компромисс (пятый случай — убрал часть комментариев при переносе, посчитав
  безопасным; владелец поймал не по багу, а по тому, что заметил стрижку).
- Настоящий opaque-блоб (base64 картинки, ключ, хэш) — если механического пути
  перенести целиком нет вообще, остановиться и сказать владельцу прямо, не
  пытаться быстрее руками.

## 2. Длинная строка без переносов — риск даже при программном переносе

Если один непрерывный кусок текста (комментарий, строка) длиннее ~90 символов без
внутренних переносов — сам факт длины повышает риск потери фрагмента при
формировании вызова инструмента, даже когда исходный текст уже экранирован
программно (второй случай, [[feedback_manual_transcription_risk]]). Переформатировать
такие места короткими строками перед переносом, если возможно.

## 3. Обязательная сверка после — всегда, без исключений

Побайтовая/sha256 сверка результата против источника — не формальность, а рабочий
последний рубеж, который реально ловил потерю в каждом из девяти задокументированных
случаев. Для очень больших файлов сверять программно (`node`/`diff`), не глазами —
даже чтение ответа инструмента может обрезаться по токенам.

## Под давлением — не быстрее, а строже

Момент реального прод-инцидента — не повод срезать путь. Цена ошибки в этот момент
максимальна (тот же урок, что уже в CLAUDE.md, 27.08.2026: «Паника чинить своё же —
повод притормозить, а не ускориться»), а сам безопасный путь (CLI-обход/скрипт) не
медленнее одного неудачного инлайн-переноса плюс сверки, которая всё равно
обязательна в обоих случаях.
